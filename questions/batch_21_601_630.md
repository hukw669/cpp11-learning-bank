# C++11 第二十一批题目（601–630）：标准 I/O 与分离编译基础

> 本批区分 C++11 标准流、实现相关文件行为，以及编译器和链接器工具链概念。

## 601【节点：IO-01】【C++11·标准库】流、设备和缓冲区怎样分层，为什么“写入流成功”不等于“数据已经落盘”？

**答案：** 流把数据抽象成有顺序的字符序列，格式层负责在 `int` 等对象和值的字符表示之间转换，`std::basic_streambuf` 管理字符缓冲，最下层设备可以是终端、文件或内存。相同的 `out << value` 因而可用于不同输出目的地。

缓冲会把多次小写合并，写入流对象只表示数据已被格式化并交给相应流/缓冲协议；即使 `flush()` 成功，也通常只到操作系统层。磁盘控制器缓存、文件系统日志和持久化屏障属于平台层，ISO C++11 不保证一次流写入已经抵抗断电。

## 602【节点：IO-02】【C++11·标准库】输入、输出、文件流和字符串流分别由哪些头文件提供？

**答案：** 常用 `char` 流类按能力和设备分层：

```cpp
#include <iostream> // istream、ostream、iostream、标准流对象
#include <fstream>  // ifstream、ofstream、fstream
#include <sstream>  // istringstream、ostringstream、stringstream
```

`istream` 输入、`ostream` 输出、`iostream` 双向；文件流关联文件，字符串流关联内存字符串。它们都是 `basic_*<CharT, Traits>` 模板的常用别名。不要依赖某个头文件偶然间接包含另一个完整定义；流对象一般不可复制，文件流和字符串流在 C++11 中支持移动。

## 603【节点：IO-03】【C++11·标准库】`cin`、`cout`、`cerr` 和 `clog` 的用途与刷新行为有什么区别？

**答案：** `std::cin` 和 `std::cout` 对应标准输入、输出；`std::cerr` 和 `std::clog` 通常写诊断信息。`cin` 默认绑定 `cout`，从 `cin` 读取前会刷新被绑定输出；`cerr` 默认设置 `unitbuf`，每次输出操作后触发刷新；`clog` 更适合缓冲日志。

```cpp
std::cout << "name? " << std::flush;
std::cin >> name;
std::cerr << "open failed\n";
```

把 `cerr` 简称为“绝对无缓冲”并不精确，底层重定向和实现仍可能有缓冲层。程序无需手工关闭这些标准对象。

## 604【节点：IO-04】【C++11·标准库】哪些输出格式状态会持续，为什么 `setw` 与 `setprecision` 不能按同一种方式理解？

**答案：** `<iomanip>` 提供格式操纵器：

```cpp
out << std::hex << 255
    << ' ' << std::dec
    << std::fixed << std::setprecision(2) << 3.5;
```

`hex/dec`、`fixed/scientific`、`setprecision`、`setfill`、`boolalpha` 等通常改变流的持续状态；`std::setw(n)` 只规定下一次格式化字段的宽度。默认浮点格式下 `setprecision` 表示有效数字，在 `fixed` 下表示小数位数。库函数若临时修改调用者的流，应按接口需要保存并恢复标志、精度和填充字符。

## 605【节点：IO-05】【C++11·标准库】格式化输入怎样同时完成解析和错误报告？

**答案：** 提取运算符依据目标类型解析字符，并在流状态中记录结果：

```cpp
int count;
if (in >> count) {
    use(count);
} else {
    handle_invalid_or_unavailable_input();
}
```

默认 `skipws` 会跳过前导空白，字符串读到下一空白，整数按当前进制规则解析；格式错误或超范围通常设置 `failbit`。多个提取可链式写 `if (in >> a >> b)`，任何一步失败都会使整体条件失败。它不是整行读取；要保留空白应选择 `noskipws`、无格式操作或 `getline`。

## 606【节点：IO-06】【C++11·标准库】`goodbit`、`eofbit`、`failbit` 和 `badbit` 分别表示什么？

**答案：** `goodbit` 表示没有错误位；`eofbit` 表示输入遇到序列末尾；`failbit` 表示格式或逻辑读取失败；`badbit` 表示更严重的底层 I/O 失败。`fail()` 在 failbit 或 badbit 出现时为真，`bad()` 只检查 badbit，`eof()` 只检查 eofbit，流的布尔条件表示没有失败状态。

```cpp
in.clear();
in.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
```

`clear()` 只重置状态，不会移走缓冲中的坏字符；恢复交互输入通常还要丢弃错误字段。EOF 常与 failbit 同时出现，必须判断本次读取，而不是提前检查 EOF。

## 607【节点：IO-07】【C++11·标准库】为什么正确输入循环是 `while (in >> value)`，而不是 `while (!in.eof())`？

**答案：** 正确形式先执行读取，再在成功时进入循环体：

```cpp
int value;
while (in >> value) {
    sum += value;
}
```

因此每次循环体都拥有刚读取的有效值，最后一次失败不会再次处理旧值。`eofbit` 只有在一次读取尝试实际遇到末尾后才设置，`while (!in.eof())` 会多进入一次；若失败原因是非法字符而不是 EOF，还可能不断失败形成死循环。循环结束后再用 `eof()/fail()/bad()` 区分正常结束、格式错误与设备错误。

## 608【节点：IO-08】【C++11·标准库】从 `operator>>` 切换到 `getline` 时为什么常读到一个空行？

**答案：** 格式化提取通常读完 token 后把终止换行留在输入缓冲；紧接的 `std::getline` 看见该换行，消耗它并返回空字符串。若协议要求丢弃当前行剩余内容，可写：

```cpp
in.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
std::getline(in, line);
```

需要 `<limits>`。`getline` 消耗但不保存分隔符。`std::getline(in >> std::ws, line)` 会跳过所有前导空白甚至空行，只有输入协议允许丢失这些内容时才能采用。

## 609【节点：IO-09】【C++11·标准库】文件流怎样体现 RAII，为什么重要输出仍可能需要显式 `close()`？

**答案：** `<fstream>` 的文件流可在构造时打开，析构时自动关闭：

```cpp
std::ofstream out("result.txt");
if (!out)
    throw std::runtime_error("open failed");

out << result << '\n';
out.close();
if (!out)
    throw std::runtime_error("write or close failed");
```

RAII 保证退出路径释放文件资源，但析构函数无法方便地向调用者报告最终刷新或关闭失败。对重要输出，应在仍能处理错误的位置显式 `flush`/`close` 并检查状态。`is_open()` 只表示是否关联文件，流的布尔状态才反映操作是否成功；路径编码由实现和平台约定。

## 610【节点：IO-10】【C++11·标准库】`app`、`ate` 和 `trunc` 三种文件模式有什么区别？

**答案：** 模式是 `std::ios_base::openmode` 位标志，可按位或组合：

```cpp
std::fstream file(
    "data.bin",
    std::ios::in | std::ios::out | std::ios::binary);
```

`app` 要求每次写都位于文件末尾；`ate` 只在打开后把初始位置放到末尾，之后仍可定位；`trunc` 在打开时截断既有内容。`in/out` 指定读写，`binary` 请求二进制模式。各流类型有默认模式，例如普通 `ofstream` 打开既有文件通常会截断；不支持或矛盾的组合可能打开失败。

## 611【节点：IO-11】【C++11·标准库/实现边界】文本模式和二进制模式的差别是什么，`binary` 为什么不是“可移植二进制格式”开关？

**答案：** 文本模式允许实现转换程序字符序列与外部文本表示；Windows 常见 `'\n'` 与 CRLF 转换，POSIX 实现中两种模式通常没有这种差别。二进制打开写：

```cpp
std::ifstream input(
    path, std::ios::in | std::ios::binary);
```

`binary` 只控制流的传输模式，不规定整数宽度、端序、浮点表示、结构体填充、字符编码或协议版本。图片、自定义字节协议应使用二进制模式，同时仍要由文件格式逐字段定义外部表示。

## 612【节点：IO-12】【C++11·标准库】怎样正确处理 `read()` 未读满请求长度的最后一块数据？

**答案：** `read(buffer, n)` 尝试取得恰好 `n` 个字符；到达末尾时可能同时设置 eof/fail，但 `gcount()` 会报告最近一次无格式输入实际提取量。复制循环可写：

```cpp
char buffer[4096];
while (input.read(buffer, sizeof buffer) || input.gcount() > 0) {
    output.write(buffer, input.gcount());
    if (!output)
        throw std::runtime_error("write failed");
}
```

循环后还应区分正常 EOF 与 `badbit` 等错误。`gcount()` 只描述特定的最近无格式输入；把非平凡 C++ 对象地址直接交给块读写会违反对象生存期或格式契约。

## 613【节点：IO-13】【C++11·标准库】`tellg/seekg` 与 `tellp/seekp` 为什么分成两组？

**答案：** 输入序列使用 get position，所以查询和定位是 `tellg/seekg`；输出序列使用 put position，对应 `tellp/seekp`：

```cpp
input.seekg(0, std::ios::end);
std::streampos end = input.tellg();
input.seekg(0, std::ios::beg);
```

位置类型是 `streampos`，不应无条件当成普通字节整数。流已到 EOF 或失败后，通常需先 `clear()` 再定位。文本模式的位置和任意偏移受实现限制；双向流在读写方向切换时还要遵守定位、刷新等同步规则。

## 614【节点：IO-14】【C++11·标准库/持久化边界】`'\n'`、`std::endl`、`std::flush` 和 `fsync` 分别做什么？

**答案：** `'\n'` 只插入换行字符；`std::endl` 插入换行并刷新 C++ 流；`std::flush` 只刷新，不插入字符：

```cpp
out << "ordinary line" << '\n';
out << "prompt: " << std::flush;
```

每行使用 `endl` 会造成不必要的刷新与系统调用压力。即使 C++ 流刷新成功，通常也只是把用户态缓冲交给更低层；POSIX `fsync` 等持久化接口不属于 ISO C++11，而且存储设备是否真正抗断电仍取决于平台协议。

## 615【节点：IO-15】【C++11·标准库】`tie()` 与 `sync_with_stdio(false)` 各自改变什么？

**答案：** `tie()` 让输入流在读取前刷新关联输出流，`cin` 默认与 `cout` 绑定。`sync_with_stdio` 控制八个标准 C++ 流与对应 C `stdio` 流的同步：

```cpp
std::ios_base::sync_with_stdio(false);
std::cin.tie(nullptr);
```

性能型设置应在任何标准 I/O 之前完成；开始 I/O 后再切换的效果由实现规定。解除绑定意味着交互提示要自行刷新；关闭 C/C++ 同步后交错使用 `printf` 和 `cout` 的顺序不能凭直觉判断。它们都不是让整行并发输出自动原子的接口。

## 616【节点：IO-16】【C++11·标准库】流异常掩码怎样把状态位转换为异常，设置掩码本身为什么也可能抛？

**答案：** 默认流通过状态位报告失败；`exceptions()` 可指定哪些状态置位时抛 `std::ios_base::failure`：

```cpp
input.exceptions(std::ios::badbit | std::ios::failbit);
try {
    input >> value;
} catch (const std::ios_base::failure& error) {
    handle(error);
}
```

状态位仍会保留供检查。设置新掩码时会立即依据当前 `rdstate()` 检查，若已有状态命中，新设置操作本身就可能抛。是否把正常到达 EOF 视为异常取决于掩码和读取协议；同一接口应一致选择状态式或异常式策略。

## 617【节点：IO-17】【C++11·标准库】字符串流怎样用于可靠解析，为什么读出一个值不代表整串合法？

**答案：** `<sstream>` 让字符串使用普通流的格式化与状态机制：

```cpp
std::istringstream input(text);
int value;

if (input >> value) {
    input >> std::ws;
    if (input.eof())
        accept(value);
}
```

只检查第一次提取会把 `"12junk"` 错当成完整整数输入；协议要求整串时还要确认只剩允许的空白并到达末尾。输出可用 `std::ostringstream` 后调用 `str()`。复用字符串流时，替换内容 `str(new_text)` 与清除旧错误状态 `clear()` 是两件事。

## 618【节点：IO-18】【C++11·标准库/编码边界】locale、字符类型和字符编码为什么不能混为一谈？

**答案：** locale 为数字格式、字符分类、排序和部分转换提供 facet；编码规定字节或码元如何表示文本。`char` 只是一个字节大小的字符类型，`wchar_t` 的宽度和表示由实现决定，它们都不自动等于“一个用户可见字符”。

```cpp
std::locale environment("");
stream.imbue(environment);
```

C++11 的 `u8"..."` 产生 UTF-8 编码的窄字符串字面量，但写入终端能否正确显示还取决于终端编码和字体。标准 locale 不是完整 Unicode 规范化、字素切分或大小写处理库；工程必须明确文件、终端和路径编码策略。

## 619【节点：IO-19】【工程概念】为什么 `out.write(reinterpret_cast<const char*>(&record), sizeof record)` 不能作为通用文件格式？

**答案：** 这段语法可以复制当前进程中的对象表示，但结构体可能含填充字节，成员宽度、端序、浮点表示和 ABI 会变化，指针值也只对当前地址空间有意义。增加成员或改变编译选项就可能改变布局。

即使 `Record` 是可平凡复制类型，也只说明按规则复制对象字节可行，不提供跨版本、跨编译器或恶意输入安全。文件格式必须独立规定外部字段；`memcmp` 同样不能普遍替代值相等。原始结构体转储最多适用于严格控制的同实现临时数据，并应明确限制。

## 620【节点：IO-20】【工程概念】一个可演进的显式序列化格式至少应规定哪些内容？

**答案：** 协议通常要规定魔数、版本、字段顺序或标识、整数宽度与端序、文本编码、长度表示、可选字段、最大尺寸和完整性校验。编码/解码接口可以是：

```cpp
bool encode(const Record& value, std::ostream& output);
bool decode(std::istream& input, Record& value);
```

但函数签名本身不定义协议。解码必须先验证长度上限和算术溢出，再分配内存；未知版本或字段要有明确策略。C++11 没有标准序列化框架，第三方库和网络字节序函数都必须记录版本与平台依赖。

## 621【节点：IO-21】【C++11·标准库】使用 `FILE*` 时怎样检查短读、错误和关闭责任？

**答案：** `<cstdio>` 提供 `std::fopen/fread/fwrite/fclose`。`fread` 返回成功读取的元素数，少于请求值时要用 `std::feof` 与 `std::ferror` 区分末尾和错误；`fwrite` 也可能短写，所有返回值都要检查。

可用自定义删除器表达唯一关闭责任：

```cpp
std::unique_ptr<std::FILE, int(*)(std::FILE*)> file(
    std::fopen("data.bin", "rb"), &std::fclose);
if (!file)
    throw std::runtime_error("open failed");
```

格式化函数的格式说明符必须与实参类型匹配，否则可能未定义；不能让两个包装器关闭同一 `FILE*`。

## 622【节点：IO-22】【版本边界】严格 C++11 为什么不能使用 `std::filesystem`，目录操作应怎样隔离？

**答案：** C++11 文件流能打开已知路径，却没有标准路径对象、目录遍历、权限、重命名和文件元数据 API；`<filesystem>` 与 `std::filesystem` 到 C++17 才标准化。编译器扩展即使在某台机器可用，也不是 ISO C++11 保证。

严格工程可在自定义平台接口后使用 Boost.Filesystem、POSIX 或 Win32：

```cpp
std::vector<std::string>
list_directory(const std::string& path);
```

业务层只依赖该接口，平台层处理分隔符、大小写、权限和路径编码差异，并在构建系统中选择实现。

## 623【节点：IO-23】【ISO C++11/POSIX 边界】C++ 文件流、`FILE*` 与 POSIX 文件描述符分别属于哪一层？

**答案：** `std::ifstream/ofstream` 提供 C++ 类型化格式和 stream buffer；`std::FILE*` 是 C 标准缓冲流；POSIX fd 是内核打开文件对象的整数句柄。ISO C++11 标准化前两层，不标准化 `open/read/write/close`、`fileno` 或 `fdopen`，也没有把 `fstream` 可移植转换为 fd 的接口。

多个缓冲包装器若指向同一底层 fd，会引入文件位置、刷新顺序、所有权和双重关闭问题。模块边界必须明确谁关闭哪一层资源；事件循环通常管理 fd，文本配置解析则更适合 C++ 文件流。

## 624【节点：BUILD-01】【C++11/工程概念】源文件、头文件、翻译单元和最终程序是什么关系？

**答案：** 工程通常把 `.cpp` 作为独立翻译输入，把共享声明和允许重复出现的定义放在头文件；`#include` 在预处理时把头文件文本纳入源文件，形成翻译单元。多个翻译单元及所需库最终链接成程序。

```cpp
// math.hpp
int add(int, int);

// math.cpp
#include "math.hpp"
int add(int a, int b) { return a + b; }
```

文件后缀和 `g++` 命令是工具链惯例，不是 ISO C++11 文件命名要求。头文件不会自动成为一个共享的独立编译模块。

## 625【节点：BUILD-02】【工具链】预处理、编译、汇编和链接各处理什么类型的问题？

**答案：** 预处理展开 `#include/#define/#if`；编译器解析 C++、做名字查找和类型检查并生成汇编表示；汇编器把汇编转成含机器代码和重定位的目标文件；链接器组合目标文件与库并解析跨文件符号。

GCC/Clang 驱动可分别观察阶段：

```text
g++ -E source.cpp -o source.ii
g++ -S -std=c++11 source.ii -o source.s
g++ -c source.s -o source.o
g++ source.o other.o -o app
```

这些选项不是 C++ 语法。缺头文件、类型错误、非法目标及未定义符号通常分别指向不同阶段。

## 626【节点：BUILD-03】【ISO C++11·概念】什么是翻译单元，为什么同一个头文件会被“编译很多次”？

**答案：** 翻译单元概念上是一个源文件经过预处理、文本包含和条件编译后的结果，是常见独立编译边界。两个 `.cpp` 都包含 `common.hpp` 时，各自的预处理结果都包含该头内容，不存在一个由所有源文件自动共享的“头文件目标文件”。

每个翻译单元独立做名字查找、模板实例化和代码生成，链接器之后才组合它们。宏只在当前预处理流程中生效；若不同源文件因宏而看到不同的公共类定义，可能违反 ODR，并且不一定得到诊断。

## 627【节点：BUILD-04】【ISO C++11·规则】声明、定义与 ODR 怎样共同保证跨文件实体一致？

**答案：** 声明引入名字和类型，定义还建立对象、函数体或完整类型：

```cpp
extern int total;                 // 对象声明
int add(int, int);                // 函数声明

int total = 0;                    // 对象定义
int add(int a, int b) { return a + b; } // 函数定义
```

被 odr-use 的普通非内联函数或变量通常必须在整个程序中有唯一外部定义。类、模板和 inline 函数可在多个翻译单元出现满足严格一致要求的定义。声明存在只保证当前单元能编译，不保证链接时一定找到定义；部分 ODR 违反无需诊断。

## 628【节点：BUILD-05】【ISO C++11·规则】内部链接、外部链接和无链接分别怎样影响跨翻译单元身份？

**答案：** 外部链接名字可让不同翻译单元的相容声明表示同一实体；内部链接实体只属于当前翻译单元；无链接的局部名字不能这样跨作用域关联。

```cpp
extern int shared;          // 头文件中的外部声明
static int internal;        // 命名空间作用域：内部链接
namespace { int hidden; }   // 内部链接

void f() {
    int local;              // 无链接
    static int calls;       // 无链接名字、静态存储期对象
}
```

存储期与链接不同：函数内 `static` 不会获得跨文件身份。命名空间作用域非 `extern` 的 `const` 对象默认具有内部链接。

## 629【节点：BUILD-06】【工程惯例】为什么公共头放声明、一个源文件放普通定义，并且实现文件也要包含自己的头？

**答案：** 头文件向所有调用方提供统一编译契约，一个 `.cpp` 提供非内联外部实体的唯一实现，可降低重编译范围和重复定义风险：

```cpp
// api.hpp
Result run(const Input&);

// api.cpp
#include "api.hpp"
Result run(const Input& input) { /* ... */ }
```

实现文件包含自己的公共头，编译器就能检查声明与定义是否一致。调用方包含头文件而不是 `.cpp`。模板、类定义、inline 函数等需要调用点可见或允许重复定义的内容是例外，不能机械套用“所有定义都放源文件”。

## 630【节点：BUILD-07】【C++11·语言/工程惯例】模板定义为什么通常必须放在头文件，何时可以只在源文件中生成实例？

**答案：** 模板在某个翻译单元针对实际实参实例化时，编译器通常必须看到完整定义。因此常把声明与定义一起放入 `.hpp`：

```cpp
template<class T>
T max2(T a, T b)
{
    return a < b ? b : a;
}
```

若只想支持固定类型，可在 `.cpp` 中保留定义并显式实例化，例如 `template int max2<int>(int, int);`，调用方还可配合 `extern template`。这会把支持类型变成需维护的封闭集合；其他类型调用通常得到未定义引用或无法实例化。
