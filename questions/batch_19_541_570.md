# C++11 第十九批题目（541–570）：RAII、智能指针与线程同步

> 本批以 ISO C++11 和 C++11 标准库为主；内存诊断命令明确标为具体工具链能力。

## 541【节点：MEM-13】【C++11/工程核心】一个资源所有类怎样用 RAII 明确取得、释放、复制和移动策略？

**答案：** RAII 类在构造时取得资源，在析构时无条件释放，并让类型本身规定所有权能否复制或转移。独占资源常采用：

```cpp
class Handle {
public:
    explicit Handle(Resource resource);
    ~Handle() noexcept;

    Handle(const Handle&) = delete;
    Handle& operator=(const Handle&) = delete;
    Handle(Handle&& other) noexcept;
    Handle& operator=(Handle&& other) noexcept;
};
```

若复制有明确含义，也可实现深拷贝或共享策略，而不是机械删除。关键是每个资源始终有可追踪的所有者，部分构造失败能由已构造成员自动回滚，析构不泄漏异常；这比在每条 `return` 和 `catch` 路径手工清理可靠。

## 542【节点：MEM-14】【C++11·标准库】`std::unique_ptr` 的所有权、移动、观察和放弃所有权接口分别是什么？

**答案：** `<memory>` 中的 `unique_ptr` 表达独占所有权，可移动但不可复制：

```cpp
std::unique_ptr<Widget> first(new Widget(1));
std::unique_ptr<Widget> second = std::move(first);

Widget* observed = second.get(); // 只观察，不转移
second.reset(new Widget(2));      // 删除旧对象并接管新对象
Widget* raw = second.release();   // 放弃管理，不执行 delete
delete raw;
```

移动后 `first` 不再拥有对象。`get()` 不转移所有权，不能据此创建第二个独立所有者；`release()` 会把释放责任交给调用者。动态数组应使用 `std::unique_ptr<T[]>`，它以 `delete[]` 清理并提供下标访问。

## 543【节点：MEM-15】【版本边界】严格 C++11 中怎样创建 `unique_ptr`，为什么不能默认使用 `std::make_unique`？

**答案：** `std::make_unique` 到 C++14 才进入标准库。严格 C++11 应先在简单、独立语句中直接构造：

```cpp
std::unique_ptr<Widget> widget(new Widget(arguments));
```

也可由项目自行实现一个 C++11 兼容辅助函数，但它不是 `std` 命名空间中的标准接口，必须清楚标明来源。不要为了“看起来现代”把 C++14 API 写进 C++11 题目；如果原始 `new` 被嵌进复杂的多实参表达式，还要特别审查 C++11 求值顺序和异常安全，优先先建立 RAII 对象再调用其他函数。

## 544【节点：MEM-16】【C++11·标准库】`std::shared_ptr` 的控制块保存什么，哪些线程安全性质不能由它推出？

**答案：** `shared_ptr` 通常由对象指针和控制块协作，控制块保存强/弱引用计数、删除器及可能的分配器信息。复制 `shared_ptr` 增加共享所有权，最后一个强所有者销毁时调用删除器：

```cpp
std::shared_ptr<Widget> first(new Widget);
std::shared_ptr<Widget> second = first;
first.reset();
```

不同 `shared_ptr` 对象共同管理同一控制块时，引用计数维护具备标准要求的线程安全性；这不使 `Widget` 的成员访问自动无数据竞争，也不允许无同步地同时修改同一个 `shared_ptr` 变量。共享对象状态仍需锁或合适的原子协议。

## 545【节点：MEM-17】【C++11·标准库】`std::make_shared` 相比 `shared_ptr<T>(new T(...))` 有什么优点和生命周期边界？

**答案：** C++11 可写：

```cpp
std::shared_ptr<Widget> value =
    std::make_shared<Widget>(arguments);
```

`make_shared` 通常把对象与控制块安排在一次分配中，减少分配次数，并且不会把新建裸指针暴露在调用表达式中。代价是对象和控制块可能位于同一分配块：最后一个强引用销毁对象后，只要仍有 `weak_ptr`，整块存储可能还不能释放。需要自定义删除器、接管既有裸指针或要求对象存储尽早释放时，应按需求选择其他构造方式。

## 546【节点：MEM-18】【C++11·标准库】`std::weak_ptr` 怎样打破共享环，为什么应直接检查 `lock()` 的结果？

**答案：** `weak_ptr` 观察控制块但不增加强引用计数，因此可把双向关系的一侧设为弱引用，避免两个对象互相拥有而永不销毁：

```cpp
std::weak_ptr<Node> parent = shared_parent;

if (std::shared_ptr<Node> locked = parent.lock()) {
    locked->visit();
}
```

`lock()` 在对象仍存活时原子地取得一个新的共享所有者，否则返回空 `shared_ptr`。单独先调用 `expired()` 再使用会产生检查与取得之间的竞态窗口，所以它主要适合观察或诊断，不能替代对 `lock()` 返回值的判断。

## 547【节点：MEM-19】【C++11·标准库】`unique_ptr` 和 `shared_ptr` 的自定义删除器为什么体现在不同位置？

**答案：** `unique_ptr` 的删除器类型属于智能指针类型本身：

```cpp
struct FileCloser {
    void operator()(std::FILE* file) const
    {
        if (file) std::fclose(file);
    }
};

std::unique_ptr<std::FILE, FileCloser> file(
    std::fopen("data.txt", "r"), FileCloser());
```

`shared_ptr<T>` 的删除器存放在控制块中，因此不同删除器通常仍表现为同一个 `shared_ptr<T>` 类型：`std::shared_ptr<T> p(raw, deleter);`。删除器必须与资源来源配对并可安全保存；同一个裸指针不能交给两个彼此独立的控制块，否则会重复释放。

## 548【节点：MEM-20】【C++11·标准库】`enable_shared_from_this` 解决什么问题，为什么构造函数中通常不能调用 `shared_from_this()`？

**答案：** 成员函数若需要返回一个与现有控制块共享所有权的“自身指针”，类可公开继承：

```cpp
class Session : public std::enable_shared_from_this<Session> {
public:
    std::shared_ptr<Session> self()
    {
        return shared_from_this();
    }
};
```

对象必须已经被合适的 `shared_ptr<Session>` 接管，基类内部弱引用才会关联控制块。在构造函数执行期间，这种共享所有权通常尚未建立，调用会抛 `std::bad_weak_ptr`。也不要写 `std::shared_ptr<Session>(this)`，那会创建第二个独立控制块并最终重复删除。

## 549【节点：MEM-21】【C++11·标准库】`allocator_traits` 为什么把“取得存储”和“构造对象”拆成两步？

**答案：** 容器需要分别控制原始存储和其中对象的生存期。`allocator_traits` 为不同 allocator 提供统一适配：

```cpp
std::allocator<T> allocator;
typedef std::allocator_traits<decltype(allocator)> Traits;

T* storage = Traits::allocate(allocator, count);
Traits::construct(allocator, storage, argument);
Traits::destroy(allocator, storage);
Traits::deallocate(allocator, storage, count);
```

`allocate` 只取得能容纳对象的存储，`construct` 才在指定位置开始对象生存期；`destroy` 结束生存期，`deallocate` 释放原始存储。真实代码必须跟踪已成功构造的元素个数，以便中途抛异常时逆序销毁并回收。

## 550【节点：MEM-22】【ISO C++11·语法】`alignof` 和 `alignas` 分别查询、约束什么？

**答案：** `alignof(T)` 产生类型 `T` 的对齐要求；`alignas` 给声明增加合法的对齐约束：

```cpp
std::size_t required = alignof(T);
alignas(64) unsigned char cache_slot[64];
alignas(T) unsigned char storage[sizeof(T)];
```

最后一个数组具有足以容纳 `T` 的大小和对齐，但其中还没有活动的 `T` 对象；仍需按生存期规则构造。`alignas` 不能用较弱对齐破坏类型自身要求，具体支持的扩展对齐上限由实现决定，不能把任意数值都假定为可接受。

## 551【节点：MEM-23】【C++11/版本边界】为什么 `alignas(64)` 的类型在 C++11 中动态分配时仍需检查实现？

**答案：** C++11 引入扩展对齐声明，但没有 C++17 的 `std::align_val_t` 版全局 `operator new`/`delete` 接口。自动、静态等声明对象的有效 `alignas` 约束由实现满足；对超过普通动态分配保证的过度对齐类型，直接 `new T` 的能力和细节需要核对所用实现。

工程上可使用成对的定制分配/释放函数或明确的平台对齐分配接口，再通过放置 new 建立对象。平台分配函数不能冒充 ISO C++11 接口，释放函数也必须与分配来源严格配对。

## 552【节点：MEM-24】【ISO C++11·对象模型】什么时候可以用 `memcpy` 复制对象，为什么 `memcmp` 不能普遍代替 `operator==`？

**答案：** 对可平凡复制类型，标准允许通过字符数组或 `std::memcpy` 保存、复制和恢复对象表示：

```cpp
static_assert(std::is_trivially_copyable<Record>::value,
              "byte copy requires a trivially copyable type");
Record destination;
std::memcpy(&destination, &source, sizeof destination);
```

对象表示可能包含填充字节，不同字节表示可能对应同一值，填充字节还可能具有未指定内容，所以 `memcmp` 不普遍等价于值比较。带指针的结构即使可按字节复制，也只复制地址值，不能形成可移植序列化；虚表、ABI、端序和版本差异同样不能靠 `fwrite(struct)` 解决。

## 553【节点：MEM-25】【ISO C++11·别名规则】怎样合法观察任意对象的字节，为什么不能随意把它转成无关类型指针后解引用？

**答案：** C++11 允许通过 `char` 或 `unsigned char` 类型的左值观察对象表示：

```cpp
const unsigned char* bytes =
    reinterpret_cast<const unsigned char*>(&object);
for (std::size_t i = 0; i < sizeof object; ++i)
    inspect(bytes[i]);
```

这不意味着可把地址转为任意 `U*` 并解引用。严格别名规则允许编译器依据访问类型推断哪些对象可能互相影响；通过不被允许的无关类型访问可能产生未定义行为和优化后错误。值传递应使用正确类型、明确转换，或在适用对象类别上使用 `memcpy`。

## 554【节点：MEM-26】【ISO C++11·语义】`volatile` 能保证什么，为什么它不能替代原子或互斥量？

**答案：** 通过 volatile 左值进行的访问属于实现必须按 volatile 规则处理的可观察副作用，常用于具体实现支持的内存映射设备或有限的信号场景：

```cpp
volatile unsigned int* device_register = address;
unsigned int status = *device_register;
```

ISO C++11 的 `volatile` 不保证操作原子性、不建立线程间 happens-before，也不提供互斥或复合操作不可分割性。两个线程无同步地读写同一 volatile 普通对象仍可能构成数据竞争。线程通信应使用 `std::atomic<T>`、互斥量或其他标准同步接口；设备语义还必须查平台和硬件文档。

## 555【节点：MEM-27】【工程诊断】常见内存错误各是什么，怎样从所有权和边界两方面预防？

**答案：** 高频错误包括泄漏、越界访问、重复释放、释放后使用、未初始化读取、错误的分配/释放配对，以及计算 `count * sizeof(T)` 时整数溢出。它们可能立即崩溃，也可能长期潜伏并在优化后表现不同。

预防应优先采用自动对象、容器和智能指针表达所有权；接口同时传递范围或容量，分配前检查乘法上溢，避免无约束裸指针别名。代码评审、边界测试和 Sanitizer/Valgrind 等工具用于发现遗漏，但“工具本次没有报告”不是不存在未定义行为的证明。

## 556【节点：MEM-28】【工具链边界】ASan、UBSan、LSan 和 Valgrind Memcheck 分别适合发现什么？

**答案：** AddressSanitizer 主要检测越界、释放后使用等内存错误；LeakSanitizer 检测泄漏；UndefinedBehaviorSanitizer 覆盖部分未定义行为；Valgrind Memcheck 通过动态翻译检测非法内存访问、未初始化数据传播和泄漏。它们都不是 ISO C++11 标准库。

GCC/Clang 常见示例为：

```text
c++ -std=c++11 -g -O1 \
  -fsanitize=address,undefined \
  -fno-omit-frame-pointer source.cpp -o app

valgrind --leak-check=full ./app
```

具体选项、平台支持和能否组合以工具链文档为准。工具会改变内存布局、时序和性能，应使用独立诊断构建，并结合可复现测试解释报告。

## 557【节点：TH-01】【工程概念/C++11 边界】进程、线程、并发和并行分别描述什么？

**答案：** 进程通常是操作系统资源与地址空间隔离单位，ISO C++11 不提供创建进程的标准接口；线程是进程内的执行序列，C++11 标准库提供 `std::thread` 抽象。并发表示多个任务在时间上重叠推进，并行表示它们在同一时刻真实执行。

单核系统也能通过调度实现并发，多核不保证程序一定并行。并发正确性要处理共享状态、生存期、同步和停止；性能还受任务粒度、缓存、调度器和硬件影响。操作系统的线程 ID、优先级和亲和性属于平台接口，不是 `std::thread` 的可移植保证。

## 558【节点：TH-02】【C++11·标准库】创建 `std::thread` 后，线程对象析构前必须满足什么条件？

**答案：** 包含 `<thread>` 后，可用可调用对象和参数创建线程：

```cpp
void run(int id);

std::thread worker(run, 7);
worker.join();
```

构造成功后新执行线程可以立即开始，不能假定下一行先于线程入口。关联线程的 `std::thread` 对象若在析构时仍 `joinable()`，会调用 `std::terminate`；因此每条正常和异常路径都必须 `join()`、`detach()` 或把所有权移动给可靠的线程管理对象。构造线程失败会抛 `std::system_error`。

## 559【节点：TH-03】【C++11·标准库】线程参数为什么默认不是引用，`std::ref` 又带来什么生存期责任？

**答案：** `std::thread` 构造函数会衰减并保存可调用对象与参数副本，在线程内部再以移动值等规则调用。这避免默认保存对构造表达式中临时变量的引用。显式引用传递要写：

```cpp
int result = 0;
std::thread worker(compute, std::ref(result));
worker.join();
```

`std::ref`/`std::cref` 位于 `<functional>`，只包装引用，不延长对象生存期。调用方必须保证被引用对象在线程最后一次访问前仍存在，并用 `join`、锁或其他同步解决并发访问；传局部变量后立即 `detach()` 通常会制造悬空引用风险。

## 560【节点：TH-04】【C++11·标准库】`joinable()`、`join()` 和 `detach()` 各改变什么状态？

**答案：** `joinable()` 查询 `thread` 对象当前是否关联一个尚需处理的执行线程。`join()` 阻塞调用线程直到目标线程完成，并建立完成同步；`detach()` 让执行线程独立继续，当前 `thread` 对象不再关联它。

```cpp
if (worker.joinable())
    worker.join();
```

成功调用 `join` 或 `detach` 后，`joinable()` 为假，不能再次调用。对不满足前置条件的对象调用会抛 `std::system_error`。`detach` 不是“自动管理后台任务”：程序仍必须另外保证其访问对象、库和进程资源的生存期。

## 561【节点：TH-05】【C++11·标准库】为什么 `std::thread` 可移动但不可复制，移动赋值前要检查什么？

**答案：** 一个关联线程应只有一个负责 `join` 或 `detach` 的 `std::thread` 所有者，因此复制构造和复制赋值被删除，所有权通过移动转移：

```cpp
std::thread first(work);
std::thread second = std::move(first);
second.join();
```

移动后 `first` 不再关联该线程，`second` 接管责任。尤其要注意移动赋值：如果目标 `thread` 在赋值前仍 `joinable()`，程序调用 `std::terminate`，不会替你先 join。线程容器或管理类必须在覆盖旧值前完成旧线程的生命周期处理。

## 562【节点：TH-06】【C++11·语言/标准库】为什么工作线程必须在入口最外层处理异常？

**答案：** 异常只沿当前线程的调用栈传播，不会自动跳到创建该线程的调用点。若异常逃出线程入口函数，运行时调用 `std::terminate`。入口应捕获并在本线程处理，或保存到共享状态：

```cpp
std::promise<void> completion;
std::future<void> result = completion.get_future();

std::thread worker([&] {
    try {
        work();
        completion.set_value();
    } catch (...) {
        completion.set_exception(std::current_exception());
    }
});
worker.join();
result.get(); // 在调用线程重新抛出
```

共享 `exception_ptr` 也可实现，但访问其变量仍需同步。

## 563【节点：TH-07】【ISO C++11·内存模型】什么条件构成数据竞争，为什么结果不是“最后一次写入获胜”？

**答案：** 两个不同线程的动作访问同一内存位置且相互冲突（至少一个修改或涉及生存期变化），其中至少一个是非原子访问，并且二者之间没有标准规定的 happens-before 关系，就形成数据竞争。含数据竞争的程序行为未定义。

因此编译器不必实现“最后写者获胜”，源码中的读写甚至可能被优化、重排或消除。共享普通状态应统一放进由同一互斥量保护的临界区，或在适合独立原子化时使用 `std::atomic<T>` 并设计明确的内存序协议。

## 564【节点：TH-08】【C++11·标准库】四种基本互斥量类型的能力有何区别？

**答案：** `<mutex>` 提供：

- `std::mutex`：普通非递归互斥；
- `std::recursive_mutex`：同一线程可重复加锁，但必须对应解锁；
- `std::timed_mutex`：普通互斥加 `try_lock_for`/`try_lock_until`；
- `std::recursive_timed_mutex`：递归与定时能力组合。

基本接口是 `lock()`、`try_lock()`、`unlock()`。互斥量不可复制；普通 `mutex` 被同一线程重复 `lock()` 不应被当作合法递归用法。业务代码通常不直接手工配对 `lock/unlock`，而由 `lock_guard` 或 `unique_lock` 保证异常路径解锁。

## 565【节点：TH-09】【C++11·标准库】`lock_guard` 与 `unique_lock` 应分别用于什么场景？

**答案：** `lock_guard` 是最小的固定作用域锁，构造即加锁、析构即解锁：

```cpp
std::lock_guard<std::mutex> lock(mutex);
update(shared_state);
```

`unique_lock` 体积和状态更多，但可延迟加锁、显式解锁/重新加锁、移动所有权，并满足 `condition_variable` 的等待要求：

```cpp
std::unique_lock<std::mutex> lock(mutex, std::defer_lock);
lock.lock();
```

两者都依赖底层互斥量比锁对象活得久。`adopt_lock` 只可用于当前线程已经正确持有的锁，否则行为错误。

## 566【节点：TH-10】【C++11·标准库】同时获取两个互斥量时，怎样使用 `std::lock` 减少死锁风险？

**答案：** 可先建立延迟加锁的所有者，再让 `std::lock` 用避免死锁的算法获取全部锁：

```cpp
std::unique_lock<std::mutex> first(mutex1, std::defer_lock);
std::unique_lock<std::mutex> second(mutex2, std::defer_lock);
std::lock(first, second);

update_both();
```

成功后两个 `unique_lock` 各自拥有锁并在析构时释放；若获取过程抛异常，接口会处理已取得的锁。`std::lock` 只解决这一组获取动作的互锁问题，不会修复程序其他地方违反全局加锁协议，也不能让同一个非递归互斥量安全地作为两个参数传入。

## 567【节点：TH-11】【工程概念】死锁、活锁和饥饿有什么区别，C++11 标准锁是否保证公平？

**答案：** 死锁是参与者相互等待而都无法继续；活锁是线程持续改变状态或重试，却没有实际进展；饥饿是某个线程长期得不到资源，而其他线程仍在推进。统一锁顺序、用 `std::lock`、缩短临界区和避免持锁调用未知回调有助于防止死锁。

不加设计地循环 `try_lock()` 可能形成活锁并消耗 CPU，可结合退避、条件变量或队列协议。ISO C++11 的普通互斥量不承诺严格公平或等待时间上界，调度公平性也属于实现和操作系统层面，因此“最终一定轮到某线程”不能仅由 `std::mutex` 推出。

## 568【节点：TH-12】【C++11·标准库】条件变量等待为什么必须配合 `unique_lock` 和共享谓词？

**答案：** 条件变量本身不保存业务条件；条件存在受互斥量保护的共享状态中。标准模式是：

```cpp
std::unique_lock<std::mutex> lock(mutex);
condition.wait(lock, [&] { return ready || stopped; });
consume();
```

`wait` 在阻塞前原子地释放互斥量，唤醒后重新取得锁，再检查谓词。通知方在同一同步协议下修改 `ready`，随后调用 `notify_one()` 或 `notify_all()`。普通 `std::condition_variable` 要求 `std::unique_lock<std::mutex>`；需要其他锁类型时有 `condition_variable_any`，但仍必须维护同一谓词协议。

## 569【节点：TH-13】【工程概念】什么是虚假唤醒和丢失唤醒，谓词形式怎样同时处理两者？

**答案：** 虚假唤醒是 `wait` 可能在没有相应业务通知时返回；丢失唤醒通常指通知发生时没有合适等待者，而后来等待者错误地把通知当作可保存事件。条件变量不保存通知次数，所以正确性必须依赖共享状态。

```cpp
condition.wait(lock, [&] { return !queue.empty() || closed; });
```

谓词形式等价于在循环中反复检查：状态早已满足时不会睡眠，虚假唤醒时会继续等待。谓词所读写的状态必须按同一互斥协议保护；只把 `wait` 改成 `if` 或只依赖 `notify_one()` 的时间顺序都不可靠。

## 570【节点：TH-14】【C++11·标准库】`std::call_once` 怎样处理多线程初始化和初始化函数抛异常？

**答案：** `<mutex>` 提供 `std::once_flag` 与 `std::call_once`：

```cpp
std::once_flag flag;

void ensure_initialized()
{
    std::call_once(flag, [] {
        initialize_resource();
    });
}
```

多个线程调用时，只有一次正常返回的调用成为完成初始化，其效果会对相应返回者正确同步。若初始化函数抛异常，本次尝试不会把 flag 标记为完成，异常传给该调用者，之后其他调用可再次尝试。C++11 还保证函数局部静态对象的初始化具有线程安全协议；二者适合的封装方式不同。
