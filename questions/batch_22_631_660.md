# C++11 第二十二批题目（631–660）：链接、ABI 与 CMake

> CMake、GCC/Clang、目标文件和 ABI 都属于工具链或平台层，不是 ISO C++11 语言特性。

## 631【节点：BUILD-08】【ISO C++11·规则】`inline` 的核心语言作用是什么，为什么它不等于“强制展开机器代码”？

**答案：** `inline` 的重要标准作用是允许满足 ODR 条件的同一实体定义出现在多个翻译单元，从而可在头文件定义函数：

```cpp
inline int twice(int value)
{
    return value * 2;
}
```

类定义内部定义的成员函数也隐式 inline。多个定义必须词法一致，并在各翻译单元中以一致方式查找到相关名字。是否把调用展开成机器指令由优化器决定；标了 inline 仍可保留调用，未标 inline 也可被优化展开。用宏让不同源文件看到不同 inline 定义会违反 ODR。

## 632【节点：BUILD-09】【ISO C++11·预处理器】include guard 能防止哪一种重复，为什么不能修复跨翻译单元重复定义？

**答案：** 标准保护形式为：

```cpp
#ifndef PROJECT_PATH_WIDGET_HPP
#define PROJECT_PATH_WIDGET_HPP

// 头文件内容

#endif
```

第二次在同一预处理流程中包含该头时，宏已定义，正文被跳过。因此它只防止同一个翻译单元经直接或间接路径重复处理头内容；多个 `.cpp` 各自仍会处理一次，普通外部定义放头中仍可能跨单元重复。保护宏必须全项目唯一。`#pragma once` 被主流编译器支持，但不是 ISO C++11 规定的预处理指令。

## 633【节点：BUILD-10】【工具链】怎样从错误阶段区分预处理、编译、链接和装载失败？

**答案：** 头文件找不到或条件指令错误通常在预处理阶段；缺分号、未声明名字、类型/模板/重载错误属于编译；目标格式或架构问题可能在汇编；未定义引用、重复符号、漏库和入口点缺失属于链接。

可先分阶段：

```text
g++ -std=c++11 -c source.cpp -o source.o
g++ source.o dependency.o -o app
```

如果可执行文件已产生，却因 `.so` 缺失或版本符号不匹配而无法启动，那是动态装载失败。部分 ODR 违反无需诊断，所以“编译链接成功”仍不是符合标准的证明。

## 634【节点：BUILD-11】【ABI/工具链】C++ 名字修饰为什么能区分重载，又为什么不能跨工具链假定格式稳定？

**答案：** C++ 允许命名空间、类成员和重载，目标文件的符号表需要区分 `ns::f(int)` 与 `ns::f(double)`。工具链通常把作用域和类型编码进符号名，这就是名字修饰。

GNU/LLVM 环境可用：

```text
nm -C object.o
c++filt _ZN2ns1fEi
```

具体编码由平台 ABI 和编译器决定，不是 ISO C++11 语法。编译器、ABI 版本或选项不兼容时，同一源码签名可能产生不同二进制契约；反修饰只帮助阅读，不能证明组件布局和运行库兼容。

## 635【节点：BUILD-12】【ISO C++11·语言链接】共享 C/C++ 头怎样正确使用 `extern "C"`？

**答案：** C 编译器不认识 `extern "C"`，所以共享头应按 `__cplusplus` 条件包装：

```c
#include <stddef.h>

#ifdef __cplusplus
extern "C" {
#endif

int api_run(void* handle, const unsigned char* data, size_t size);

#ifdef __cplusplus
}
#endif
```

它为具有外部链接的名字和函数类型指定 C 语言链接，通常避免 C++ 重载式名字修饰。它不统一类布局、异常、模板、标准容器、分配器或完整 ABI。稳定接口应使用双方理解的标量、字节缓冲和不透明句柄，并阻止 C++ 异常逃出 C 边界。

## 636【节点：BUILD-13】【工程概念】ABI 包括哪些内容，为什么源码 API 相同仍可能二进制不兼容？

**答案：** ABI 是已编译组件之间的契约，覆盖调用约定、参数和返回值传递、名字修饰、对象布局与对齐、虚表、异常展开、运行库、符号版本和导出规则。ISO C++11 主要规定语言语义，不统一不同平台或工具链的这些细节。

例如库按默认对齐编译，而调用方用 packing 宏看到不同结构体偏移，符号可能链接成功却读取错误字段。长期稳定边界常使用窄 C ABI、不透明句柄、显式版本，以及“在哪一侧分配就在哪一侧释放”的接口。

## 637【节点：BUILD-14】【工具链/文件格式边界】目标文件、可执行文件、重定位和符号表分别起什么作用？

**答案：** 目标文件包含机器代码、数据、未解析外部引用和重定位记录；符号表描述已定义或待解析名字；重定位告诉链接器最终地址确定后修补哪些位置。链接器组合目标文件和库，产生可执行文件或共享对象。

```text
g++ -std=c++11 -c a.cpp -o a.o
g++ a.o b.o -o app
```

Linux 常用 ELF，Windows 常用 COFF/PE，macOS 常用 Mach-O；这些格式不由 ISO C++11 固定。`readelf -Ws`、`nm -C` 等命令是平台工具，剥离调试符号也不等于删除所有运行期所需动态符号。

## 638【节点：BUILD-15】【工程/平台概念】静态库和动态库在链接、部署与更新上有什么差别？

**答案：** 静态库通常是目标文件归档，最终链接时把需要的成员纳入可执行文件；库更新后，程序必须重新链接才能包含新代码。动态库保持独立，装载器在启动或运行期解析，可由多个进程映射共享，但部署依赖搜索路径、SONAME/版本和 ABI。

Linux 常见 `.a/.so`，Windows 常见 `.lib/.dll`，均是平台工具链形式。替换动态库后，已运行进程通常仍使用已装载映像；重启会尝试加载新文件，缺导出或版本不匹配可直接装载失败，隐蔽 ABI 不兼容则可能运行后崩溃。

## 639【节点：BUILD-16】【GCC/Clang 工具链】开发、发布和 Sanitizer 构建为什么应分开配置？

**答案：** 开发构建重视诊断和可调试性，例如：

```text
g++ -std=c++11 -g -O0 -Wall -Wextra -Wpedantic source.cpp -o app
```

发布通常从经测试的 `-O2` 等优化开始；ASan/UBSan/TSan 需要相应编译和链接选项，并会改变布局、时序或性能，应使用独立构建目录。警告集合、优化级别和 Sanitizer 都是具体编译器能力，不是 C++11。CI 可分别运行严格警告、普通测试与诊断构建，并保存完整命令以复现。

## 640【节点：BUILD-17】【工具链边界】怎样要求 GCC/Clang 使用严格 C++11，`gnu++11` 又多了什么？

**答案：** GCC/Clang 可写：

```text
g++ -std=c++11 -pedantic-errors source.cpp -o app
```

`-std=c++11` 选择标准方言，`-pedantic-errors` 有助于把部分扩展诊断为错误；`-std=gnu++11` 则允许 GNU 扩展。编译器接受语法不代表其标准库实现也完整，供应商扩展更不能冒充 ISO C++11。MSVC 没有与 GCC 历史 C++11 模式完全等价的开关，应按版本和所需特性验证。

## 641【节点：BUILD-18】【GNU 链接器边界】为什么静态库链接顺序可能决定是否出现 `undefined reference`？

**答案：** GNU 风格链接器通常按命令行扫描静态归档，只在当前存在未满足引用时抽取所需成员，所以使用者常放前、提供定义的库放后：

```text
g++ main.o -L/path -lfoo -lbar -o app
```

若 `main.o` 引用 `foo`，先扫 `libfoo.a` 再看到引用可能不会抽取目标成员。循环静态依赖可重构，或使用 GNU ld 的 `--start-group/--end-group`，但后者不可移植且可能增加链接成本。动态库和其他链接器的规则可能不同，优先让构建系统传播完整 target 依赖闭包。

## 642【节点：BUILD-19】【工具链】编译器前端、C++ 标准库和低层运行库为什么是不同组件？

**答案：** 前端解析 C++ 并生成代码；标准库实现容器、线程、流等接口；低层运行库还支持异常展开、启动代码、整数辅助和线程局部存储。GCC 常配合 libstdc++/libgcc，Clang 可配 libc++ 或 libstdc++ 以及不同运行库。

用 `g++`/`clang++` 驱动链接通常会自动加入匹配的 C++ 库；直接用 `gcc` 或 `ld` 需要自行提供准确项。相同前端不保证标准库 ABI 相同，跨库传递 `std::string`、异常或跨侧释放内存尤其依赖完整运行库一致性。

## 643【节点：BUILD-20】【工程/ABI】哪些编译选项和宏必须在共享二进制边界两侧保持一致？

**答案：** 架构与指针宽度、结构体 packing、异常/RTTI、运行库选择、调试迭代器、字符宽度，以及改变公共类定义的条件宏，都可能改变 ABI。调用方与库若看到不同布局，可能链接成功后破坏内存。

应让构建 target 传播公共定义和选项，生成统一配置头并导出 ABI 版本，在 CI 中用受支持工具链矩阵共同构建调用方与库。ISO C++11 没有“自动 ABI 一致”语法；libstdc++ 双 ABI 宏、MSVC 运行库选项等都要查具体版本文档，不能只以“能链接”为判断。

## 644【节点：CMAKE-01】【CMake 工具链】CMake 是编译器吗，它在构建链路中处于什么位置？

**答案：** CMake 是构建系统生成器和项目配置语言，不解析 C++ 语义，也不自行完成机器代码链接。它读取 `CMakeLists.txt`、探测工具链和依赖，把 target 图转换成 Ninja、Make、Visual Studio 等原生构建规则，再由这些工具调用编译器和链接器。

```text
cmake -S . -B build -G Ninja
cmake --build build
```

CMake 版本、命令和生成器不是 ISO C++11。动态库、目标文件和链接本来就属于工具链，CMake只是跨平台地组织它们。

## 645【节点：CMAKE-02】【CMake 工具链】配置、生成和构建三个阶段分别做什么？

**答案：** 配置阶段执行 CMake 语言、读取缓存并探测编译器和依赖；生成阶段写出所选原生构建系统的规则；构建阶段才真正调用编译器、链接器和自定义命令。

```text
cmake -S . -B build
cmake --build build --parallel
```

第一条通常连续完成配置与生成。缓存保存编译器路径和探测结果；更换编译器、架构或关键 toolchain 设置后沿用旧目录容易混乱，通常应使用新构建目录。构建失败还需查看实际编译/链接命令，而不能只说“CMake 错了”。

## 646【节点：CMAKE-03】【CMake 工具链】一个最小 C++ 工程的 `CMakeLists.txt` 为什么要包含三条核心声明？

**答案：** 最小示例是：

```cmake
cmake_minimum_required(VERSION 3.16)
project(demo LANGUAGES CXX)

add_executable(app main.cpp)
```

`cmake_minimum_required` 选择项目的 CMake 行为基线，`project` 声明项目与语言，`add_executable` 建立产物 target。这里的 `3.16` 是示例 CMake 最低版本，不表示 C++ 标准。缓存、目标文件和产物应进入独立构建目录，不能依赖某个生成器固定的输出路径。

## 647【节点：CMAKE-04】【CMake 工具链】为什么 target 是 CMake 工程的核心抽象？

**答案：** target 表示可执行文件、库或只携带使用要求的逻辑组件。源码、包含路径、编译特性、宏和链接依赖都应绑定到真正需要它们的 target：

```cmake
add_library(core core.cpp)
add_executable(app main.cpp)
target_link_libraries(app PRIVATE core)
```

CMake 根据 target 依赖图生成命令并传播使用要求。全局修改 `CMAKE_CXX_FLAGS`、`include_directories()` 等容易污染无关目标、第三方代码和测试，削弱可组合性与跨平台控制。

## 648【节点：CMAKE-05】【CMake 工具链】怎样声明目标需要 C++11，并控制是否允许编译器扩展？

**答案：** 可用编译特性：

```cmake
target_compile_features(app PRIVATE cxx_std_11)
```

或明确 target 属性：

```cmake
set_target_properties(app PROPERTIES
    CXX_STANDARD 11
    CXX_STANDARD_REQUIRED YES
    CXX_EXTENSIONS NO)
```

`cxx_std_11` 表示至少具备 C++11，环境可能选择更高默认标准；若题库要求严格边界，应结合属性和 CI 验证。可用 meta-feature 与行为取决于项目声明的 CMake 最低版本，CMake 最终只是为具体编译器选择相应选项。

## 649【节点：CMAKE-06】【CMake 工具链】源码列表与包含目录为什么必须分开配置？

**答案：** 源码列表决定编译哪些翻译单元，包含目录只告诉编译器到哪里查找头文件：

```cmake
target_sources(core PRIVATE src/core.cpp)
target_include_directories(core
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
    PRIVATE src)
```

公共头所需路径通常传播给消费者，私有实现路径不应泄漏。头搜索路径不是链接库路径。显式源码列表便于审查；若使用 glob，还要理解新增文件何时触发重新配置。

## 650【节点：CMAKE-07】【CMake 工具链】编译定义、编译选项和链接选项为什么不能混写？

**答案：** 宏用 `target_compile_definitions`，且条目不带 `-D`；警告、优化等编译器参数用 `target_compile_options`：

```cmake
target_compile_definitions(core PRIVATE FEATURE_X=1)

if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
    target_compile_options(core PRIVATE -Wall -Wextra)
endif()
```

GCC 选项不能无条件传给 MSVC；链接参数也不应伪装成编译参数。会改变公共头布局或 ABI 的宏必须以 PUBLIC/INTERFACE 方式一致传播，纯实现开关保持 PRIVATE。具体命令可用性取决于 CMake 版本。

## 651【节点：CMAKE-08】【CMake 工具链】`STATIC`、`SHARED`、`MODULE`、`OBJECT` 和 `INTERFACE` 库有什么区别？

**答案：** 常见创建形式为：

```cmake
add_library(core STATIC core.cpp)
add_library(runtime SHARED runtime.cpp)
add_library(plugin MODULE plugin.cpp)
add_library(parts OBJECT a.cpp b.cpp)
add_library(headers INTERFACE)
```

STATIC 产生静态归档，SHARED 产生动态库，MODULE 通常供显式装载而不直接链接，OBJECT 提供可复用目标文件，INTERFACE 不编译源码而只传播使用要求。省略类型可能受 `BUILD_SHARED_LIBS` 影响；Windows 共享库还涉及导出符号和导入库。

## 652【节点：CMAKE-09】【CMake 工具链】为什么应优先链接命名 target，而不是手工拼 `-L`、`-l` 和文件路径？

**答案：** 连接 target 可同时获得产物位置、配置、传递依赖、包含路径和编译定义：

```cmake
target_link_libraries(app PRIVATE core)
```

若 `core` 是本项目 target 或 Imported Target，CMake 能按生成器、架构和 Debug/Release 选择正确产物并形成依赖闭包。手工 `link_directories` 和裸名称容易选错版本或架构。链接成功也不保证运行时能找到共享库，动态装载搜索与 RPATH 仍是平台/部署问题。

## 653【节点：CMAKE-10】【CMake 工具链】`PRIVATE`、`PUBLIC` 和 `INTERFACE` 应怎样从公开接口判断？

**答案：** `PRIVATE` 只供当前 target，`PUBLIC` 同时供当前 target 与消费者，`INTERFACE` 只供消费者。规则适用于 include、定义、特性和链接依赖。

若某头路径只被 `.cpp` 使用，选 PRIVATE；若公共头暴露第三方类型，当前库和消费者都需其头及 ABI 要求，通常选 PUBLIC；纯头文件 target 的要求用 INTERFACE。不能机械地给所有库写 PUBLIC：传播过多会污染下游，传播不足则使消费者无法编译或看到不同 ABI。

## 654【节点：CMAKE-11】【CMake 工具链】`find_package` 与 Imported Target 怎样封装外部依赖？

**答案：** 包查找可声明版本和组件：

```cmake
find_package(Foo 2.0 REQUIRED COMPONENTS core)
target_link_libraries(app PRIVATE Foo::Core)
```

Config 模式使用包提供的配置，Module 模式使用 `FindFoo.cmake`；成功后包文档规定 Imported Target 名称。target 封装库位置、头路径、宏和传递依赖，比手工拼接稳定。找到包不代表架构和版本必然正确，toolchain file、`CMAKE_PREFIX_PATH` 和包管理器都会影响搜索结果。

## 655【节点：CMAKE-12】【CMake 工具链】单配置与多配置生成器怎样选择 Debug/Release？

**答案：** Ninja、Unix Makefiles 等单配置生成器通常在配置时选择：

```text
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
```

Visual Studio、Xcode 和多配置 Ninja 通常在构建时选择：

```text
cmake -S . -B build
cmake --build build --config Release
```

多配置生成器一般不靠 `CMAKE_BUILD_TYPE`；产物路径还可能包含配置子目录。脚本不能假定所有生成器的配置和输出布局相同。

## 656【节点：CMAKE-13】【工程惯例】为什么源码外构建更安全，切换编译器时为什么应新建目录？

**答案：** `cmake -S . -B build/debug` 把缓存、生成规则、目标文件和产物放到源码树外，保持源码干净，并允许不同编译器、架构和配置各用独立目录。

CMakeCache 记录绝对工具路径和探测结果；直接把旧目录切换到另一工具链可能留下互相矛盾的缓存。构建目录原则上可删除重建，源码、CMakeLists、toolchain 文件和必要脚本应纳入版本控制。执行清理前仍要确认目标确实是明确构建目录，不能误删源码树。

## 657【节点：CMAKE-14】【CMake/CTest 工具链】怎样注册并运行一个测试，CTest 又不负责什么？

**答案：** 示例：

```cmake
include(CTest)
add_executable(unit_tests tests.cpp)
add_test(NAME unit COMMAND unit_tests)
```

先构建，再运行：

```text
cmake --build build
ctest --test-dir build --output-on-failure
```

多配置环境还需 `-C Debug` 等配置。`add_test` 只注册命令，不自动编译 target；CTest 负责调度和报告，不是断言、Mock 或测试数据框架。工作目录、环境变量、超时和并行资源应按测试显式配置。

## 658【节点：CMAKE-15】【CMake 工具链】“本机能构建”与“库可安装、可被 `find_package`”之间还缺什么？

**答案：** 需要安装产物和公共头、导出 target，并提供包配置与版本文件，例如：

```cmake
install(TARGETS core EXPORT ProjectTargets)
install(DIRECTORY include/ DESTINATION include)
install(EXPORT ProjectTargets
        NAMESPACE Project::
        DESTINATION lib/cmake/Project)
```

公开包含目录要区分 `BUILD_INTERFACE` 与 `INSTALL_INTERFACE`，避免把开发机绝对路径写入安装接口。静态/动态产物目录、RPATH、依赖打包和 Windows DLL 都有平台差异；可重定位包还需 `<Project>Config.cmake` 正确查找其依赖。

## 659【节点：CMAKE-16】【CMake 工具链】使用 `std::thread` 时为什么应链接 `Threads::Threads`，而不是跨平台硬编码 `-lpthread`？

**答案：** 线程支持在不同平台可能需要编译标志、链接库或无需额外选项。FindThreads 把差异封装为 Imported Target：

```cmake
find_package(Threads REQUIRED)
target_link_libraries(app PRIVATE Threads::Threads)
```

在 GNU/Linux 上 `-pthread` 可能同时影响预处理、编译和链接，不等价于只写 `-lpthread`；Windows 也没有相同库名。若库的公开接口把线程使用要求传给消费者，再按真实接口关系选择 PUBLIC，否则通常 PRIVATE。

## 660【节点：LINUX-01】【Linux/GNU 工具链】`g++`、C++ 前端、汇编器和链接器分别承担什么工作？

**答案：** `g++`/`clang++` 通常是驱动程序，根据选项调用预处理器和 C++ 前端，前端完成语言分析和代码生成，GNU `as` 等汇编器生成 `.o`，GNU ld、gold 或 lld 等链接器解析符号并生成 ELF 产物。驱动还会加入匹配的 C++ 标准库与运行库。

```text
g++ -v -std=c++11 main.cpp -o app
clang++ -### -std=c++11 main.cpp -o app
```

`-E/-S/-c` 可停在不同阶段。具体子工具、ELF 和命令选项属于 Linux/工具链，不是 ISO C++11。
