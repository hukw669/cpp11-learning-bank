# C++11 第二十批题目（571–600）：异步设施、原子与内存模型

> 本批严格区分 ISO C++11 语言规则、C++11 标准库接口，以及硬件、操作系统和工具链行为。

## 571【节点：TH-15】【ISO C++11·语法】`thread_local` 对象何时创建和销毁，它与普通共享全局变量有何不同？

**答案：** 声明为 `thread_local` 的变量具有线程存储期，每个线程拥有自己的对象实例：

```cpp
thread_local unsigned int request_count = 0;

void record_request()
{
    ++request_count; // 修改当前线程自己的实例
}
```

实例通常在该线程首次需要初始化时按规则初始化，并在线程退出时销毁；具有动态初始化的线程局部对象仍要注意初始化依赖和析构顺序。`thread_local` 避免的是不同线程访问同一实例，并不让它适合跨线程共享数据，也不等同于任务局部存储：线程池中的多个任务可能复用同一工作线程和同一个实例。

## 572【节点：TH-16】【C++11·标准库】`promise`、`future` 和共享状态怎样传递值、异常与“生产者消失”？

**答案：** `promise` 是生产端，`future` 是一次性消费端，二者通过共享状态通信：

```cpp
std::promise<int> promise;
std::future<int> future = promise.get_future();

std::thread producer([&] {
    try {
        promise.set_value(compute());
    } catch (...) {
        promise.set_exception(std::current_exception());
    }
});

int value = future.get();
producer.join();
```

`get()` 会等待结果并在状态保存异常时重新抛出，普通 `future` 的结果通常只能取得一次。若尚未设置结果的 `promise` 被销毁，共享状态会以 `broken_promise` 错误使等待者就绪。重复 `get_future()`、重复设置结果等契约违反会以 `std::future_error` 报告。

## 573【节点：TH-17】【C++11·标准库】`std::async` 的 `async`、`deferred` 和默认策略分别意味着什么？

**答案：** 明确异步执行可写：

```cpp
std::future<Result> result =
    std::async(std::launch::async, function, arguments);
```

`std::launch::async` 请求异步执行；`std::launch::deferred` 延迟到调用该 future 的非定时等待或 `get()` 时，在等待线程中执行。未显式给策略的标准重载相当于允许实现从 `async` 和 `deferred` 中选择，不能假定必然创建后台线程。

由 `async` 返回且采用异步策略的 future 在某些最后引用销毁场景会等待任务完成，所以丢弃临时 future 可能意外串行化。并发数量、线程池实现和调度性能也不是 ISO C++11 的固定保证。

## 574【节点：TH-18】【C++11·标准库】`packaged_task` 与 `shared_future` 分别解决“任务包装”和“多消费者”中的什么问题？

**答案：** `packaged_task` 把可调用对象与 future 共享状态绑定，调用任务时把返回值或异常写入状态：

```cpp
std::packaged_task<int(int)> task(square);
std::future<int> result = task.get_future();
std::thread worker(std::move(task), 7);

int value = result.get();
worker.join();
```

普通 `future` 可移动、通常只允许一次 `get()`；调用 `share()` 可转换成可复制的 `shared_future`，多个消费者可等待并反复取得同一结果。复制 `shared_future` 只共享结果状态，不自动同步消费者对结果对象内部可变状态的进一步访问。

## 575【节点：TH-19】【C++11·标准库】相对超时为什么通常选 `steady_clock`，定时等待返回又为何不等于条件成立？

**答案：** `steady_clock` 保证时间点不倒退，适合测量耗时和截止期限；`system_clock` 代表日历时间，可能因校时而跳变。线程可使用：

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(10));
std::this_thread::sleep_until(deadline);
```

睡眠只保证不会有意早于规定条件恢复，不保证在截止时刻精确获得 CPU。`future::wait_for` 返回 `ready`、`timeout` 或可能的 `deferred`；条件变量的定时等待也必须醒来后重新检查谓词。超时是控制流结果，不会自动取消仍在运行的任务。

## 576【节点：TH-20】【C++11·标准库规则】多个线程什么时候可以同时访问标准容器，什么时候必须外部同步？

**答案：** 对彼此不同的容器对象，并发调用通常互不构成同一对象的数据竞争。对同一个容器，可并发进行标准明确视为只读的操作；标准库还要求除 `vector<bool>` 外，不同线程修改同一容器中不同元素时避免库内部产生数据竞争。

但结构性修改如 `push_back`、`erase`、rehash、扩容会改变容器元数据并可能使迭代器或引用失效，不能与未同步访问并发。复合业务操作也需要锁：

```cpp
std::lock_guard<std::mutex> lock(mutex);
if (!queue.empty()) {
    value = queue.front();
    queue.pop();
}
```

容器保证不等于元素对象自身的线程安全保证。

## 577【节点：TH-21】【C++11/工程模式】C++11 没有 `stop_token` 时，怎样让阻塞工作线程协作式停止？

**答案：** 可用原子停止标志表示请求，并用条件变量唤醒正在等待任务的线程：

```cpp
std::atomic<bool> stop(false);

// 请求停止
stop.store(true);
condition.notify_all();

// 工作线程等待
std::unique_lock<std::mutex> lock(mutex);
condition.wait(lock, [&] {
    return stop.load() || !tasks.empty();
});
```

工作线程应在安全检查点退出并由管理者 `join()`。只有原子标志而没有唤醒机制，会让阻塞在线程条件变量上的工作者永远看不到请求；只有通知而没有受同步保护的状态，又可能丢失。强制终止线程不是 ISO C++11 能安全完成的通用操作。

## 578【节点：TH-22】【C++11/工程模式】一个基本生产者—消费者队列或线程池需要哪些状态和关闭规则？

**答案：** 典型组件包括任务队列、保护队列与关闭状态的互斥量、条件变量、若干 `std::thread` 和停止/排空策略。消费者在谓词中同时等待“有任务”或“已关闭”：

```cpp
condition.wait(lock, [&] {
    return closed || !tasks.empty();
});

if (closed && tasks.empty())
    return;
```

生产者在锁下入队，解锁后通知；关闭方在锁下改变 `closed`，再 `notify_all` 并 join 所有工作线程。工程契约还必须规定关闭后是否拒绝新任务、已入队任务是排空还是取消、任务异常怎样传回，以及有界队列如何对生产者施加背压。ISO C++11 没有标准线程池类。

## 579【节点：TH-23】【C++11·标准库/平台边界】`native_handle()` 能做什么，为什么调用平台线程 API 会降低可移植性？

**答案：** `std::thread::native_handle()` 返回实现定义的原生句柄类型：

```cpp
std::thread worker(work);
std::thread::native_handle_type handle =
    worker.native_handle();
```

随后可能用 POSIX `pthread_*` 或 Windows 线程 API 设置名称、亲和性、优先级等，但函数、句柄类型、错误规则和与 C++ 运行库的互操作保证都取决于平台与标准库实现。句柄只应在关联线程和对象状态有效时使用，并继续由 `std::thread` 正确 join/detach；ISO C++11 不保证任何特定原生类型或调度效果。

## 580【节点：AT-01】【ISO C++11·内存模型】既然每个线程内源码有先后顺序，为什么多线程程序还需要内存模型？

**答案：** 编译器可在保持单线程可观察行为的前提下重排、合并或消除操作，处理器也可能乱序执行并通过缓存传播值。源码中线程 A 写 `data` 后写普通 `ready`，不能单靠文字顺序保证线程 B 看到 `ready` 时也看到新 `data`；无同步的冲突访问还可能直接形成数据竞争。

C++11 内存模型规定内存位置、原子操作、线程内顺序、同步关系和 happens-before，给编译器、硬件与程序员共同契约。它描述抽象机允许观察到什么，不等同于一句“刷新 CPU 缓存”，具体机器指令由编译器和目标架构决定。

## 581【节点：AT-02】【ISO C++11·内存模型】“同一个内存位置”怎样判断，相邻结构体成员与相邻位域有何不同？

**答案：** 内存位置是数据竞争判断的语言单位。一个非位域标量对象通常构成一个位置；相邻的非零宽度位域可能共同属于一个内存位置，而两个普通非位域成员通常是不同位置。

```cpp
struct Separate { int first; int second; };
struct Packed   { unsigned first : 1; unsigned second : 1; };
```

不同线程分别修改 `Separate` 的两个成员通常不因这两个访问本身形成数据竞争；分别修改 `Packed` 的相邻位域却可能冲突。两个动作访问重叠存储且至少一个修改对象或开始/结束对象生存期，就可能是冲突访问；物理地址“看起来接近”不能替代标准规则。

## 582【节点：AT-03】【ISO C++11·求值顺序】`sequenced-before` 解决什么问题，为什么给表达式加分组括号不能修复未排序修改？

**答案：** `sequenced-before` 描述同一线程内两个求值的抽象先后。一个完整表达式先于下一个完整表达式；内建 `&&`、`||`、逗号运算符和条件运算符的相关部分有各自顺序规则。C++11 中普通算术操作数、多个函数实参往往没有彼此求值顺序保证。

```cpp
int i = 1;
int result = (i++) + (++i); // C++11：对 i 的修改彼此未排序，未定义行为
```

括号只改变语法分组，不建立求值先后。应拆成多个完整表达式。`sequenced-before` 是单线程关系，不能单独保证另一个线程何时看见结果。

## 583【节点：AT-04】【ISO C++11·内存模型】`synchronizes-with` 与 `happens-before` 是什么关系？

**答案：** `synchronizes-with` 是特定标准同步操作建立的跨线程边，例如一个互斥量的 `unlock()` 与另一线程随后成功取得同一互斥量，或 release 原子写与读取到该发布值的 acquire 原子读。`happens-before` 把线程内的 sequenced-before、这些同步边以及传递关系组合起来。

若写入 `data` happens-before 另一线程读取 `data`，该读就能按模型获得相应可见性并避免这对访问的数据竞争。源码时间、日志先后或“某线程大概先跑完”都不是同步关系；必须由标准操作如锁、线程启动/汇合、future 状态或正确原子协议建立。

## 584【节点：AT-05】【ISO C++11·规则】为什么普通对象上的数据竞争是未定义行为，而不是只导致值不确定？

**答案：** 数据竞争意味着不同线程对同一内存位置存在未被 happens-before 排序的冲突访问，且至少一个访问非原子。标准把整个程序行为定为未定义，使编译器能够假定合法程序没有此类竞争并进行普通代码优化。

后果不限于读到旧值或撕裂值：循环可能被消除，访问可能被合并，控制流可能出现源码推理无法解释的结果。`volatile`、调试输出、时间延迟都不修复数据竞争。应使用同一互斥协议，或把适合的独立状态改成 `std::atomic<T>` 并证明完整同步关系。

## 585【节点：AT-06】【C++11·标准库】`std::atomic<T>` 与 `std::atomic_flag` 的基本接口和限制是什么？

**答案：** `<atomic>` 提供原子对象：

```cpp
std::atomic<int> count(0);
count.store(3);
int value = count.load();
int old = count.exchange(7);

std::atomic_flag flag = ATOMIC_FLAG_INIT;
bool was_set = flag.test_and_set();
flag.clear();
```

原子对象不可按普通对象方式复制；适用的 `T` 必须满足标准对原子模板的类型要求。`atomic_flag` 是 C++11 保证无锁的最小原子类型，但 C++11 没有 `atomic_flag::test()`、`wait()` 或 `notify()`。除非显式指定，操作默认使用 `memory_order_seq_cst`；“原子”只保护该原子操作，不会自动把多个变量组成事务。

## 586【节点：AT-07】【C++11·标准库】原子整数的 `fetch_add`、前置 `++` 和后置 `++` 分别返回什么？

**答案：** 整型原子提供 `fetch_add`、`fetch_sub`、`fetch_and`、`fetch_or`、`fetch_xor` 等原子读—改—写操作：

```cpp
std::atomic<unsigned int> counter(10);
unsigned int old1 = counter.fetch_add(2); // 返回 10，counter 变 12
unsigned int new1 = ++counter;            // 返回更新后的 13
unsigned int old2 = counter++;            // 返回更新前的 13
```

整个读—改—写对该原子对象不可分割，仍应根据协议选择内存序。适用的原子指针也有按元素步长的算术操作。接口返回旧值还是新值会影响无锁算法逻辑，不能凭普通整数直觉混用。

## 587【节点：AT-08】【C++11·标准库】`compare_exchange_weak` 为什么要放在循环里，失败时 `expected` 会怎样变化？

**答案：** 比较交换把原子当前值与 `expected` 比较；相等则写入 `desired` 并成功，不等则失败并把观察到的当前值写回 `expected`。weak 版本还允许伪失败，因此常见循环为：

```cpp
int expected = value.load(std::memory_order_relaxed);
do {
    desired = transform(expected);
} while (!value.compare_exchange_weak(
             expected, desired,
             std::memory_order_release,
             std::memory_order_relaxed));
```

每次失败后必须基于已更新的 `expected` 重新计算目标值。strong 版本不允许伪失败，适合不便循环的单次判断。失败内存序不能包含 release 语义，也不得强于成功序；具体合法组合必须遵守接口约束。

## 588【节点：AT-09】【ISO C++11·内存模型】原子对象的 modification order 能保证什么，不能保证什么？

**答案：** 对每一个独立原子对象，其所有修改形成一个所有线程一致同意的总修改顺序；写入、交换、成功的 CAS 和其他读—改—写都进入该顺序。原子读取能观察哪些修改还受到其内存序及 happens-before 关系约束。

这个顺序只针对同一个原子对象。两个不同原子各自有修改顺序，并不自动形成共同快照或全局先后；对普通对象也不会仅因旁边有一个原子就自动排序。需要跨对象关系时，应使用互斥量、release/acquire 发布协议或更严格且经过证明的原子算法。

## 589【节点：AT-10】【C++11·标准库/内存模型】默认的 `memory_order_seq_cst` 比普通原子性多提供什么？

**答案：** 未指定内存序的原子操作默认使用顺序一致序：

```cpp
ready.store(true); // 等价于显式 memory_order_seq_cst
bool seen = ready.load();
```

除各自的 acquire/release 效果外，所有顺序一致原子操作还参与一个与规定关系一致的单一总顺序，使跨线程推理通常更直观。它可能比弱序产生更强约束，但性能取决于架构和编译器，不能只凭名字断定一定慢。

顺序一致仍不会把多个原子操作合成不可分割事务，也不能修复与普通对象之间未建立关系的数据竞争。

## 590【节点：AT-11】【C++11·内存模型】怎样用 release 写和 acquire 读安全发布一个普通对象的内容？

**答案：** 发布线程先写普通数据，再对同一原子标志执行 release；接收线程以 acquire 读取到该发布值后，才能使用数据：

```cpp
// 线程 A
payload = make_payload();
ready.store(true, std::memory_order_release);

// 线程 B
if (ready.load(std::memory_order_acquire))
    consume(payload);
```

当 acquire 读取到相应 release 写入的值或规则允许的释放序列值时，两者 synchronizes-with，线程 A 中标志前的写 happens-before 线程 B 中标志后的读。仅仅分别写 release 和 acquire 关键字不够：必须通过同一个原子并满足读到相应发布的联系。

## 591【节点：AT-12】【C++11·标准库】`memory_order_acq_rel` 应用于哪些操作，为什么不能把它随意传给纯 `load` 或纯 `store`？

**答案：** `acq_rel` 同时要求获取与发布语义，适合交换、fetch 操作和成功 CAS 等读—改—写：

```cpp
int previous =
    state.exchange(next, std::memory_order_acq_rel);
```

它可获取此前发布给该原子的效果，并发布本线程此前操作给后续获取者。纯 load 没有要发布的写入部分，纯 store 没有要获取的读取部分，因此各自只接受标准规定的合法内存序；不能为了“更安全”传任意枚举。CAS 还分别指定成功序和失败序，失败路径只是读取，不能使用 release 或 acq_rel。

## 592【节点：AT-13】【C++11·标准库】`memory_order_relaxed` 仍保证什么，为什么适合统计计数却不适合发布对象？

**答案：** relaxed 原子操作仍保证对该原子对象的访问原子性，并参与该对象的修改顺序，但不建立与其他内存访问的跨线程同步：

```cpp
std::atomic<unsigned long> events(0);
events.fetch_add(1, std::memory_order_relaxed);
```

若业务只要求最终得到原子计数，而计数值不承担“看到它就可以读取另一对象”的信号，relaxed 常常足够。若先写 `payload` 再 relaxed 写 `ready`，另一线程 relaxed 读到 ready 并不能由此推出 payload 可见；发布协议需要 release/acquire、锁或其他同步。

## 593【节点：AT-14】【C++11·标准库/工程边界】`memory_order_consume` 的设计意图是什么，工程代码为什么通常改用 acquire？

**答案：** consume 试图只沿从原子读取值产生的“依赖链”传播可见性，理论上可比完整 acquire 约束更弱：

```cpp
Node* node = head.load(std::memory_order_consume);
use(node->payload);
```

但依赖传播规则复杂，普通代码变换很容易破坏推理，长期以来许多编译器把 consume 实际实现得近似 acquire。严格可维护的工程代码通常直接使用 `memory_order_acquire`，接受可能更强的约束，而不是依赖难以审查的 consume 技巧。这里描述的是 C++11 接口与实现现实，不能从某一架构偶然生成的指令反推可移植保证。

## 594【节点：AT-15】【C++11·标准库】原子栅栏怎样建立同步，为什么“线程两边各放一个 fence”本身不够？

**答案：** `<atomic>` 提供 `std::atomic_thread_fence(order)`。栅栏必须通过符合规则的原子读写建立联系，例如：

```cpp
// 线程 A
data = 42;
std::atomic_thread_fence(std::memory_order_release);
ready.store(true, std::memory_order_relaxed);

// 线程 B
if (ready.load(std::memory_order_relaxed)) {
    std::atomic_thread_fence(std::memory_order_acquire);
    use(data);
}
```

只有当读取观察到相应原子写入并满足 fence 同步规则时，普通数据才被正确排序。两个孤立 fence 没有通信媒介，不能自行 synchronizes-with。`atomic_signal_fence` 面向同一线程与信号处理的编译器排序约束，不是跨线程硬件同步替代品。

## 595【节点：AT-16】【ISO C++11·内存模型】“安全发布”一个指针或对象需要同时满足哪些条件？

**答案：** 发布前必须完成对象初始化，使用标准同步把初始化效果传给接收者，并保证对象生存期覆盖接收者全部访问。例如：

```cpp
payload = new Payload(arguments);
ready.store(true, std::memory_order_release);

// 另一线程
if (ready.load(std::memory_order_acquire))
    use(*payload);
```

这里还必须设计最终由谁删除 `payload`，确保没有接收者仍在使用时释放。也可把对象放在同一互斥量保护下，或在线程启动前完成初始化并通过线程启动规则传递。仅把指针赋给普通全局、只使用 `volatile`，或只有原子指针但错误使用 relaxed，都不自动安全发布其所指内容。

## 596【节点：AT-17】【C++11·标准库规则】多个 `shared_ptr` 的引用计数线程安全，为什么其指向对象仍可能发生数据竞争？

**答案：** 不同 `shared_ptr` 对象即使共享同一控制块，也可以在多个线程中分别复制、销毁和赋值，因为控制块的所有权计数按标准要求协调。这个保证只管理生命周期，不保护 `T` 的成员：

```cpp
std::shared_ptr<State> local = shared;
std::lock_guard<std::mutex> lock(local->mutex);
++local->counter;
```

若两个线程无同步地修改 `local->counter`，仍可能数据竞争。另一个边界是“同一个 `shared_ptr` 变量”：一线程写它而另一线程同时读写它，需要锁或 C++11 的 `shared_ptr` 原子自由函数，不能把控制块安全误解为变量本身安全。

## 597【节点：AT-18】【C++11·标准库】C++11 怎样原子读写同一个 `shared_ptr` 槽位，为什么不能写 `std::atomic<std::shared_ptr<T>>`？

**答案：** C++11 为 `shared_ptr` 提供 `<memory>` 中的原子自由函数：

```cpp
std::shared_ptr<T> slot;

std::shared_ptr<T> value = std::atomic_load(&slot);
std::atomic_store(&slot, replacement);
std::shared_ptr<T> old = std::atomic_exchange(&slot, replacement);
```

还有 `atomic_compare_exchange_weak/strong` 和带 `_explicit` 的内存序版本。所有并发访问同一槽位都必须采用同一套原子接口，不能混入普通赋值。`std::atomic<std::shared_ptr<T>>` 的标准特化是 C++20 内容，不属于 C++11；这些自由函数只原子管理指针槽位和所有权，不保护所指对象成员。

## 598【节点：AT-19】【并发算法概念】lock-free、wait-free 与 `atomic.is_lock_free()` 分别说明什么？

**答案：** `atomic_object.is_lock_free()` 只查询该原子类型/对象的操作在当前实现中是否以无锁方式提供，不评价整个算法。`std::atomic_flag` 是 C++11 特别保证无锁的原子类型，其他原子可能内部使用锁。

算法层面，lock-free 通常表示系统整体持续取得进展，即使个别线程可能长期失败；wait-free 要求每个参与操作都能在有界步骤内完成；obstruction-free 则只要求线程单独运行足够久时能完成。一个底层原子无锁，不代表包含重试、分配、调度或锁的上层算法自动 lock-free，更不代表延迟一定更低。

## 599【节点：AT-20】【硬件/性能边界】什么是伪共享，`alignas(64)` 为什么只能是平台相关优化假设？

**答案：** 两个线程即使修改不同的 C++ 内存位置，如果这些位置落在同一硬件缓存行，缓存一致性仍可能让该行在核心间反复迁移，造成伪共享。程序语言上没有数据竞争，性能却可能显著下降。

可尝试把高频独立写入的数据分离、分片或按目标缓存行填充，例如 `struct alignas(64) Counter { std::atomic<long> value; };`。但 C++11 没有可移植缓存行大小查询；`64`、分配器布局、相邻数组元素位置和硬件一致性粒度都属于平台假设。`std::hardware_destructive_interference_size` 是 C++17，不能写进严格 C++11 接口。

## 600【节点：AT-21】【工具链边界】ThreadSanitizer 能发现什么，为什么一次无报告运行不能证明并发程序正确？

**答案：** TSan 通过编译插桩和运行时记录检测实际执行路径中的数据竞争及部分同步误用。GCC/Clang 常见独立诊断构建为：

```text
c++ -std=c++11 -g -O1 \
  -fsanitize=thread -fno-omit-frame-pointer \
  source.cpp -pthread -o app
```

这些选项不是 ISO C++11，支持范围以具体编译器、运行库和平台为准；TSan 通常也不与 ASan 放在同一构建中。它只能观察测试覆盖到的执行、可能改变调度时序，并可能不理解某些自定义汇编或平台同步原语。因此应扩大压力测试和调度覆盖，结合内存模型证明、代码评审与报告定位，而不能把“未报告”当成正确性证明。
