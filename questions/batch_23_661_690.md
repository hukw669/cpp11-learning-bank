# C++11 第二十三批题目（661–690）：Linux 工程与综合巩固

> 661–678 逐一覆盖 Linux 主节点；679–690 明确标为综合题并复用真实节点 ID。POSIX、Linux、ELF、GNU 工具链和 CMake 均不属于 ISO C++11。

## 661【节点：LINUX-02】【Linux/GCC 工具链】一条常见 `g++` 命令中的 `-I`、`-L`、`-l`、`-pthread` 和 `-o` 各控制什么？

**答案：** 示例：

```text
g++ -std=c++11 -Wall -Wextra -Wpedantic -g -O0 \
  -Iinclude src/main.cpp -L/opt/foo/lib -lfoo \
  -pthread -o app
```

`-I` 增加编译期头搜索目录，`-L` 增加链接期库搜索目录，`-lfoo` 请求链接 `libfoo`，`-pthread` 启用该工具链的线程编译和链接要求，`-o` 指定产物名；`-c` 则只生成目标文件。`-L` 不影响程序启动时的 `.so` 搜索，头文件找到也不证明库架构或版本正确。GNU 静态链接通常还要求库放在使用它的目标文件之后。

## 662【节点：LINUX-03】【Linux/ELF 工具链】ELF 的“节”和“段”为什么不能混为一谈？

**答案：** 节主要服务编译与链接视图，例如 `.text`、`.rodata`、`.data`、`.bss`、符号表和重定位节；段由程序头描述，服务装载器把若干节按读/写/执行权限映射进进程地址空间。

```text
readelf -h app   # ELF 头
readelf -S app   # 节
readelf -l app   # 程序头与装载段
readelf -Ws app  # 符号
readelf -r app   # 重定位
```

ELF、ASLR、PIE 和这些工具属于 Linux/Unix 工具链，不是 C++ 对象模型；文件节地址不能直接当成语言保证的运行时对象地址。

## 663【节点：LINUX-04】【Linux/GNU 工具链】`.a` 静态库是什么，为什么它不会自动把自己的依赖全部装进去？

**答案：** `.a` 通常是 `ar` 管理的目标文件归档：

```text
g++ -std=c++11 -c foo.cpp -o foo.o
ar rcs libfoo.a foo.o
ar t libfoo.a
g++ main.o -L. -lfoo -o app
```

链接器从归档中抽取满足当前未解析符号的成员；归档并不是已完成链接的独立程序，也通常不会把 `foo.o` 所依赖的另一个库代码自动复制进来。最终可执行文件仍需闭合全部依赖，并受 GNU 从左到右扫描规则影响。更新 `.a` 不会改变已经链接好的程序，必须重新链接。

## 664【节点：LINUX-05】【Linux/ELF 工具链】怎样生成一个基本共享库，为什么“成功生成 `.so`”不等于 ABI 稳定？

**答案：** GNU/ELF 常见流程为：

```text
g++ -std=c++11 -fPIC -c foo.cpp -o foo.o
g++ -shared foo.o \
  -Wl,-soname,libfoo.so.1 \
  -o libfoo.so.1.0
```

应用链接后记录动态依赖，装载器在运行时找到并重定位 `.so`。`-fPIC`、`-shared` 和 ELF 都是平台工具链能力。C++ 类布局、名字修饰、异常和运行库仍可能随工具链或选项变化；长期接口应控制导出，采用版本策略，并优先使用窄 C ABI 与不透明句柄。仍有线程执行库代码时卸载会使代码或对象悬空。

## 665【节点：LINUX-06】【Linux/ELF 工具链】PIC、SONAME、真实文件名和链接名分别解决什么问题？

**答案：** PIC 让代码可装载到不同虚拟地址，并尽量避免修改共享代码页。SONAME 是依赖者记录的 ABI 主版本名。常见布局是：

```text
libfoo.so       -> libfoo.so.1
libfoo.so.1     -> libfoo.so.1.2.3
libfoo.so.1.2.3    # 真实文件，SONAME 为 libfoo.so.1
```

可用 `readelf -d libfoo.so.1.2.3` 检查 SONAME。布局和符号链接是发行版/部署惯例，不会自动判断兼容性；破坏 ABI 的变化应提升主 SONAME，兼容修复才可保留。开发链接名与运行时依赖名承担不同角色。

## 666【节点：LINUX-07】【Linux/ELF 装载器】链接时找到 `.so`，为什么程序启动时仍可能报“cannot open shared object file”？

**答案：** `-L` 只帮助链接器选择库；运行时由 ELF 动态装载器按 DT_RUNPATH/旧 DT_RPATH、环境、缓存和默认目录等规则搜索。可检查：

```text
readelf -d app
ldd app
LD_DEBUG=libs ./app
```

可重定位应用常按部署策略设置 `-Wl,-rpath,'$ORIGIN/../lib'`。精确优先级受 glibc、secure-execution 和标签类型影响，不能把全局 `LD_LIBRARY_PATH` 当稳定发布方案。对不可信二进制优先静态检查 `readelf`，不要随意触发其装载行为。

## 667【节点：LINUX-08】【Linux/二进制工具】链接报 `undefined reference` 时，怎样用 `nm` 和 `readelf` 判断是缺定义还是签名不一致？

**答案：** 先取得链接器报告的完整 C++ 签名，再检查调用目标和候选库：

```text
nm -C caller.o
nm -C libfoo.a
readelf -Ws libfoo.so
objdump -t -C object.o
```

调用目标中的 `U` 表示未定义引用，库中应出现完全相容的已定义符号；只看函数短名会漏掉命名空间、参数 `const`、引用和 ABI 修饰差异。共享库还要看动态符号表、可见性和版本。隐藏或已剥离符号、LTO 和工具版本会影响输出，这些工具结论属于二进制层。

## 668【节点：LINUX-09】【Linux/GCC 工具链】`-pthread` 为什么不应简单替换为 `-lpthread`？

**答案：** `-pthread` 是 GCC/Clang 驱动选项，可能同时设置线程相关预处理/编译模式并向链接器传递适当线程支持：

```text
g++ -std=c++11 main.cpp -pthread -o app
```

`-lpthread` 只表达一个具体库搜索项，不能代表编译阶段的全部要求；即使某些现代 glibc 版本合并了库实现，也应沿用工具链推荐方式。跨平台 CMake 工程应写 `find_package(Threads REQUIRED)` 和 `Threads::Threads`，不要把 Linux 选项泄漏给 Windows 等目标。

## 669【节点：LINUX-10】【Linux/GDB 工具链】分析 core dump 为什么必须保留匹配的可执行文件、共享库和调试符号？

**答案：** core 保存崩溃时进程内存和寄存器快照，地址只有结合当时完全匹配的映像与符号才能可靠还原函数和变量：

```text
g++ -std=c++11 -g -O0 main.cpp -o app
gdb ./app core
```

GDB 中常用 `bt`、`thread apply all bt`、`info threads`、`frame` 和 `print`。优化可能使变量消失、代码内联或执行顺序难以对应源码。core 是否生成及位置受 `ulimit`、core_pattern、systemd 与权限影响；core 可能含密钥和用户数据，应按敏感产物保护。

## 670【节点：LINUX-11】【Linux/POSIX】文件描述符是什么，`dup` 或 `fork` 后为什么可能共享文件偏移？

**答案：** fd 是进程描述符表中的非负整数索引，可引用文件、管道、终端、套接字等内核对象。`dup` 或 `fork` 可产生多个描述符引用同一个打开文件描述，因此共享文件偏移和部分状态；描述符自身还具有 `FD_CLOEXEC` 等标志。

fd 关闭后整数值可能很快复用，缓存旧数值会误操作新资源。它既不是 C++ 指针，也不是 `FILE*`。C++ 系统代码应使用不可复制、可移动的 RAII `unique_fd`，并用 `O_CLOEXEC` 或 `fcntl` 控制跨 `exec` 泄漏。

## 671【节点：LINUX-12】【Linux/POSIX】为什么 `read`/`write` 成功返回也可能需要循环，`EINTR` 与 `EAGAIN` 又应怎样区分？

**答案：** `read/write` 返回实际传输字节数，正数可能少于请求；`read` 返回 0 通常表示 EOF，`-1` 才检查 `errno`。阻塞调用被信号打断可能得到 `EINTR`，可按接口语义重试；非阻塞 fd 暂时不能推进时得到 `EAGAIN/EWOULDBLOCK`，应回到事件循环等待就绪。

循环必须更新缓冲偏移，写满或达到协议允许的结束条件。`open` 带 `O_CREAT` 时还要传 mode。Linux 上 `close` 报错后 fd 可能已释放并被复用，不能像普通读写那样盲目重试；应遵循目标平台文档并用唯一 RAII 所有者。

## 672【节点：LINUX-13】【Linux/POSIX】非阻塞 fd 与 `epoll` 怎样配合，为什么“可读事件”不等于“一条完整消息已到达”？

**答案：** 可用 `fcntl` 设置 `O_NONBLOCK`，把 fd 注册进 Linux `epoll`。收到可读事件后持续 `read`，直到返回 `EAGAIN`；边沿触发模式尤其必须排空，否则可能不再得到推进通知。

就绪只表示当前一次操作可能推进，不保证读满缓冲、拿到完整应用消息或连接仍持续有效。协议层还要累积半包、解析长度、限制内存、处理对端关闭和写侧背压。`select/poll` 属 POSIX，`epoll` 是 Linux 专有；它们不是 ISO C++11 并发接口。

## 673【节点：LINUX-14】【实现/平台边界】Linux 上 `std::thread` 通常基于 pthread，为什么仍不应把二者视为同一 API？

**答案：** ISO C++11 定义 `std::thread` 的创建、join 与内存模型语义；libstdc++/libc++ 在 Linux 上通常借助 pthread 实现，但这种映射不是语言保证。需要亲和性或平台线程名时，可从 `native_handle()` 取得实现句柄并在隔离层调用扩展。

业务代码应优先使用 `std::thread/std::mutex`。直接对标准线程执行 `pthread_cancel` 可能绕开正常 C++ 控制流、破坏 RAII 和库假设；native handle 类型、有效期及互操作规则必须查所用标准库和操作系统文档。

## 674【节点：LINUX-15】【Linux/POSIX】`fork`、`exec` 和 `waitpid` 怎样组成创建新程序的基本流程？

**答案：** `fork()` 返回 `-1` 表示失败、子进程中为 0、父进程中为子 PID。子进程可调整 fd 后调用 `exec*`，成功的 exec 用新程序映像替换当前进程且不返回；父进程关闭不用的管道端并用 `waitpid` 回收退出状态。

退出状态要用 `WIFEXITED/WEXITSTATUS` 等宏解释。多线程进程 fork 后，子进程在 exec 前只能安全调用 POSIX 允许的 async-signal-safe 操作，继承的 mutex 可能由已消失线程持有。应设置 close-on-exec，exec 失败时走极小、明确的 `_exit` 路径。

## 675【节点：LINUX-16】【Linux/POSIX】信号处理器中为什么不能直接使用 iostream、`new`、普通 mutex 或大多数标准库？

**答案：** 信号可在几乎任意指令点中断线程；被中断代码可能正持有库内部锁或处于非重入状态。POSIX 只保证有限的 async-signal-safe 函数集合，C++ iostream、动态分配、普通锁和条件变量不在可随意调用范围内。

常见模式是处理器只修改允许的简单状态或向 self-pipe 写一个字节，由正常事件循环完成日志和资源操作；安装使用 `sigaction`，多线程程序还要设计信号 mask。Linux `signalfd` 是专有扩展。不能仅因某个 `std::atomic` 无锁就把任意标准库操作宣称为 POSIX 信号安全。

## 676【节点：LINUX-17】【Linux/POSIX】`mmap`、`msync` 和 `fsync` 各处在哪一层，为什么映射写完仍不代表崩溃后数据一致？

**答案：** `mmap` 把文件或匿名对象映射到虚拟地址；`MAP_SHARED` 修改可回写，`MAP_PRIVATE` 通常写时复制。`msync(MS_SYNC)` 协调映射脏页回写，`fsync(fd)` 请求同步文件数据及必要元数据，最后以 `munmap` 解除映射。

每次调用都要检查错误，映射只可访问长度内地址，offset 还受页对齐要求。内存写、页回写、文件系统提交、设备缓存和应用格式的事务提交是不同层；必须设计写入顺序、校验与恢复。映射字节也不会自动创建 C++ 对象或提供跨进程原子同步。

## 677【节点：LINUX-18】【Linux/工具链】Valgrind、Sanitizer 和 `perf` 为什么不能互相替代？

**答案：** Memcheck 关注非法内存、未初始化传播和泄漏；ASan/UBSan 用编译插桩检测内存错误与部分 UB；TSan 检测数据竞争；`perf` 采样 CPU、缓存和调度性能。它们观察的维度不同。

```text
valgrind --leak-check=full ./app
perf record -g ./app
perf report
```

Sanitizer 需在编译和链接都加对应 `-fsanitize=`，TSan 与 ASan 通常分开构建。工具会改变时序和性能，`perf` 还受权限、采样率和符号质量影响。应先修正确性问题，再测性能；无报告不等于无缺陷。

## 678【节点：LINUX-19】【工程设计】怎样把 ISO C++11 可移植业务层与 Linux/POSIX 实现层隔离？

**答案：** 公共层暴露平台无关的窄接口和 RAII 语义，平台层封装 fd、事件循环、进程、信号、路径和动态库。Linux 头、`errno` 与系统宏只出现在实现 target：

```cmake
if(CMAKE_SYSTEM_NAME STREQUAL "Linux")
    target_sources(platform PRIVATE platform/linux/event_loop.cpp)
endif()
```

目录可分 `core/` 与 `platform/linux/`，业务测试通过替身实现运行。抽象仍要明确阻塞、关闭、错误和能力差异，不能假装所有系统语义完全相同；CMake 条件和 POSIX API 都不是 C++11 语言内容。

## 679【节点：IO-20】【综合】【序列化/持久化】怎样把“可移植记录格式”“C++ 流刷新”和“Linux 断电持久化”分成三个独立契约？

**答案：** 第一层由序列化协议规定魔数、版本、定宽字段、端序、UTF-8、长度上限和校验，与内存结构布局无关。第二层由 C++ 流或 POSIX 写循环确保全部字节成功交给操作系统；`ostream::flush()` 只处理流缓冲。

第三层是 Linux/POSIX 部署协议：常见做法写同目录临时文件、检查所有写入、`fsync` 临时文件、以 `rename` 提交，再按文件系统要求同步目录 fd。原子 rename、目录持久化和设备断电语义必须按目标文件系统验证。任何一层成功都不能替代另外两层，恢复程序还应拒绝截断、超长或校验失败的记录。

## 680【节点：BUILD-10】【综合】【链接排障】一个 CMake 工程出现 `undefined reference to ns::run(int)`，应按什么证据链定位？

**答案：** 先确认调用翻译单元包含了正确公共头，再用详细构建输出取得真实编译和链接命令。检查调用目标存在未定义的完全签名：

```text
nm -C caller.o
nm -C libprovider.a
readelf -Ws libprovider.so
```

若库没有同签名定义，检查命名空间、参数 cv/ref、条件宏和是否漏编译源文件；若静态库有定义，检查 GNU 链接顺序和依赖闭包；若共享库有符号，检查可见性、架构和版本。最后在 CMake 中用 `target_link_libraries` 建立真实 target 依赖，而不是只添加头目录。

## 681【节点：BUILD-12】【综合】【C ABI 插件】怎样设计一个既不跨边界传播异常、又不跨运行库错误释放内存的插件入口？

**答案：** 公共头在 C++ 下使用 `extern "C"`，只暴露固定语义标量、不透明句柄、调用者缓冲区和稳定状态码。创建与销毁必须成对由同一插件实现：

```cpp
typedef struct plugin_handle plugin_handle;

extern "C" int plugin_create(plugin_handle** out) noexcept;
extern "C" void plugin_destroy(plugin_handle* handle) noexcept;
```

实现入口内部捕获所有 C++ 异常并转换错误，不能让调用方 `delete` 插件分配的对象，也不要跨边界传 `std::string`、容器、异常或类布局。接口还应有 ABI 版本查询、结构体尺寸字段和线程/生命周期规则。`extern "C"` 只提供语言链接，不会自动完成这些设计。

## 682【节点：BUILD-15】【综合】【动态库升级】替换 `libfoo.so` 后，为什么已运行进程、重启后的进程可能表现完全不同？

**答案：** 已运行进程通常继续使用已经映射并完成重定位的旧共享对象；替换磁盘路径不会把现有调用自动热切换。新进程启动时根据记录的 SONAME 和搜索规则加载当前候选：文件缺失、架构错误、版本符号或导出缺失会装载失败。

更危险的是 SONAME 未变但 ABI 已破坏，新程序可能成功装载后按错误布局运行。升级应采用真实文件加版本化 SONAME/符号链接、原子部署步骤、ABI 兼容检查和回滚策略。需要热更新时还要证明旧库无活动线程、对象和函数指针后才能卸载。

## 683【节点：CMAKE-05】【综合】【标准边界】怎样确保应用、库和测试都真正按项目要求使用 C++11，而不是只给一个目标加 `-std`？

**答案：** 把要求绑定到每个拥有源码或公开接口的 target；公共头需要 C++11 时，库应把 `cxx_std_11` 作为 PUBLIC/INTERFACE 使用要求传播，纯内部实现才可 PRIVATE。严格边界还可设置：

```cmake
set_target_properties(target PROPERTIES
    CXX_STANDARD 11
    CXX_STANDARD_REQUIRED YES
    CXX_EXTENSIONS NO)
```

测试和工具 target 也必须声明或从依赖获得要求。CI 应用实际编译器命令验证标准方言，并扫描题库排除 C++14/17 API。第三方预编译库还要单独验证 ABI，语言标准开关不能解决二进制兼容。

## 684【节点：CMAKE-10】【综合】【依赖传播】一个库的公共头暴露第三方类型、实现文件使用另一私有库时，作用域应怎样选择？

**答案：** 公共头中的第三方类型要求消费者也能找到相应头并采用一致宏/ABI，因此其 include、定义和 target 依赖通常是 PUBLIC。只在 `.cpp` 中使用的实现库通常是 PRIVATE；纯头文件适配层自身不编译，要求写 INTERFACE。

判断依据不是“这是库，所以都 PUBLIC”，而是消费者编译公开接口是否真正需要该要求。过度 PUBLIC 会污染下游选项和依赖，错误 PRIVATE 又会导致消费者缺头、缺宏或 ABI 不一致。最终链接闭包还需由 CMake target 图针对静态/共享产物正确形成。

## 685【节点：CMAKE-14】【综合】【测试流水线】怎样组织普通测试、ASan/UBSan 和 TSan，使报告既可复现又不互相干扰？

**答案：** 使用独立源码外构建目录和 target 配置：普通 Debug 运行全部 CTest；ASan/UBSan 构建在编译、链接阶段一致插桩；TSan 单独构建运行并发压力用例。每套都保存编译器、CMake、内核版本与完整命令。

```text
ctest --test-dir build-debug --output-on-failure
ctest --test-dir build-asan  --output-on-failure
ctest --test-dir build-tsan  --output-on-failure
```

先修 Sanitizer 正确性问题再做 `perf` 基准。测试要固定输入但增加并发调度覆盖；工具改变时序且只观察执行路径，无报告不能替代内存模型证明。

## 686【节点：LINUX-12】【综合】【可靠 I/O】怎样设计一个可复用的 POSIX “写满缓冲区”函数而不误处理 `EINTR`、`EAGAIN` 和 0 返回？

**答案：** 函数维护已写偏移，正返回值推进偏移；`-1/EINTR` 按调用协议重试；`-1/EAGAIN` 或 `EWOULDBLOCK` 在非阻塞模式下返回“等待可写”状态，而不是忙等；其他错误连同保存的 `errno` 返回。若 `write` 对非零请求返回 0，应避免死循环并按接口契约视为无法推进。

接口必须区分“完成、暂时阻塞、永久错误”，由事件循环在可写通知后续写。fd 由独立 RAII 所有者关闭，写函数只借用；缓冲区在异步续写完成前必须存活。网络连接还要处理对端关闭和 SIGPIPE 策略。

## 687【节点：LINUX-13】【综合】【高并发网络】一个边沿触发 epoll 服务器为什么必须同时设计输入累积、输出队列和背压？

**答案：** 边沿触发只通知状态变化；收到可读后必须循环读取到 `EAGAIN`，把字节累积到连接缓冲并按协议解析半包/多包。响应写入也可能短写，剩余数据进入输出队列，并在队列非空时关注可写事件。

如果生产速度超过网络发送速度而队列无限增长，进程会耗尽内存；应设置每连接和全局上限、暂停读取或拒绝请求，并定义超时与关闭策略。fd 关闭后编号可能复用，事件数据应携带可验证的连接身份。epoll 是 Linux API，业务协议和任务执行可留在平台无关层。

## 688【节点：LINUX-15】【综合】【多线程进程】多线程服务怎样安全地执行 fork/exec 子程序并传递管道？

**答案：** 在父进程先创建带 close-on-exec 的管道，协调并发创建 fd 的竞态，再 fork。子进程只执行极小的 async-signal-safe 路径：关闭不用端、`dup2` 重定向、调用 `execve`；exec 失败用安全方式报告并 `_exit`。不要在子进程调用 iostream、分配器或普通锁。

父进程关闭自己的无用端，以非阻塞或专门线程读写管道，并 `waitpid` 回收子进程。必须处理 fork 失败、exec 失败、退出状态和超时。更高层可评估 `posix_spawn`，但其具体能力仍属 POSIX，不是 C++11。

## 689【节点：LINUX-17】【综合】【崩溃一致性】使用 `mmap` 更新文件时，为什么“写数据后 `msync`”仍不足以形成可靠事务？

**答案：** 崩溃可能发生在任意字节或元数据提交之间；`msync` 处理映射页回写，但不自动定义应用记录边界、写入顺序、校验、版本和恢复选择，也不替代所有文件系统/设备持久化要求。

可靠格式可采用双槽或写前日志：先写新内容与校验，按平台要求同步，再原子更新带序号的提交记录；恢复时选择校验通过的最新完整版本。涉及文件大小、rename 或目录项时还要考虑 `fsync` 相应文件和目录。具体保证必须对目标内核、文件系统和存储设备测试并记录，不能宣称为 ISO C++11 行为。

## 690【节点：LINUX-19】【综合】【工程架构】怎样组织一个同时支持标准 C++11 单元测试和 Linux 生产实现的系统库？

**答案：** `core/` 只依赖 ISO C++11 类型和窄抽象接口，定义解析、调度策略与错误模型；`platform/linux/` 用 RAII 封装 fd、epoll、信号、进程和动态库，并把 `errno` 转换为项目错误。公共头不包含 Linux 头或泄漏 fd 整数。

CMake 建立 `core`、平台实现和接口 target，按 `CMAKE_SYSTEM_NAME` 选择源文件，并让测试链接内存/模拟实现；生产测试再覆盖真实 Linux 行为。ABI 边界使用版本化 C 接口或严格同工具链契约。抽象文档明确阻塞、所有权、关闭、线程安全和不支持能力，而不是假装各平台完全相同。
