# C++11 第十七批题目（481–510）

## 481【节点：X15】【易混复习】变量类型是 `Widget&&`，为什么表达式中直接写变量名仍按左值处理？

**答案：** 引用类型决定变量怎样绑定，表达式值类别描述某次使用怎样参与运算。一个具名变量有稳定身份，所以通过名字形成的表达式是左值，即使它的声明类型为右值引用。于是 `consume(value)` 按左值传递；确定要放弃其状态时写 `std::move(value)`，转发模板要恢复调用者原值类别时写 `std::forward<T>(value)`。具名表达式的值类别和转换规则属于 ISO C++11；“看到 `&&` 就一定是右值”只是错误记忆法。

## 482【节点：X15】【综合巩固】下面函数体为什么不能只看形参声明中的 `&&` 判断会选哪个重载？

**答案：** 假定 `consume` 已提供左值和右值重载，以下是函数体片段：

```cpp
void send(Widget&& item)
{
    consume(item);
    consume(std::move(item));
}
```

第一行使用具名表达式 `item`，所以选择左值入口；第二行由 `std::move` 显式产生将亡值，才有机会选择右值入口。第二次调用后不能再依赖 `item` 的旧内容，但它仍活着并会正常析构。该结论来自 ISO C++11 值类别和重载规则；究竟转移哪些资源由 `Widget` 的实现合同决定。

## 483【节点：X16】【易混复习】怎样判断一个 `T&&` 是普通右值引用还是转发引用？

**答案：** 只有函数调用正在推导模板形参 `T`，形参形式恰为无 `const/volatile` 的 `T&&` 时，它才是转发引用，可通过引用折叠接收左值和右值。固定类型 `Widget&&` 是普通右值引用；`const T&&` 不是转发引用；类模板 `Box<T>` 的普通成员 `void f(T&&)` 中，`T` 已由类实例确定，也不是本次函数调用推导。规则属于 ISO C++11；“转发引用”是对这套推导行为的通用术语。

## 484【节点：X17】【易混复习】`unique_ptr` 的 `get()`、`release()` 和 `reset()` 对所有权分别做什么？

**答案：** `get()` 只返回当前裸指针供临时观察，所有者不变；`release()` 返回裸指针并让智能指针放弃所有权，但不会删除对象，接收方必须立刻安排新的所有者或正确释放；`reset(p)` 先清理旧目标，再接管 `p`，无参 `reset()` 则清空。删除 `get()` 的返回值会让智能指针留下悬空地址并可能重复释放，忽略 `release()` 结果会泄漏。这些成员语义是 ISO C++11；裸指针交给哪种旧接口仍需工程文档约定。

## 485【节点：X18】【易混复习】`unique_ptr` 与 `shared_ptr` 的选择标准是“一个地方用”和“多个地方用”吗？

**答案：** 不是按访问位置数量判断，而是按销毁责任判断。`unique_ptr` 表示唯一所有者，可移动、不可复制；很多函数仍可通过引用或裸观察指针借用同一对象。`shared_ptr` 表示多个主体共同承担保持对象存活的责任，通过控制块计数，最后一个强所有者离开时销毁目标。循环强引用需由 `weak_ptr` 表示非拥有方向。三种智能指针行为是 ISO C++11；优先独占、只在真实共同所有权时共享是设计原则。

## 486【节点：X19】【版本边界】`make_shared` 和 `make_unique` 都属于 C++11 吗？

**答案：** 不是。`std::make_shared<T>(args...)` 已在 C++11 中；`std::make_unique` 到 C++14 才进入标准。严格 C++11 创建独占对象可在简单表达式中写 `std::unique_ptr<T> p(new T(args...));`，并尽快交给 RAII 所有者。较新编译模式接受 `make_unique` 不能证明它属于 C++11。项目可以自定义类似工厂，但必须明确它是项目接口而非当时的 ISO 标准库成员。

## 487【节点：X20】【易混复习】模板实例化和模板特化有什么区别？

**答案：** 实例化是把模板与具体实参结合，按原模板生成相应实体，例如调用 `maximum(1,2)` 可能隐式实例化整数版本；显式实例化定义也可要求集中生成某个实例。特化则为特定实参提供不同实现，例如 `template<> struct Traits<MyType> {...};`。`extern template` 是显式实例化声明，用来抑制某处通常的隐式生成，不是特化。三者的语法、可见性和 ODR 规则均属于 ISO C++11。

## 488【节点：X21】【易混复习】为什么处理所有指针类型的函数模板应使用重载，而不是“偏特化函数模板”？

**答案：** ISO C++11 允许类模板偏特化，却没有函数模板偏特化语法。函数接口需要为一类形状增加行为时，可写两个重载：

```cpp
template<class T> void process(T);
template<class T> void process(T*);
```

也可以让函数调用一个可偏特化的辅助类模板。函数模板允许显式全特化，但它与重载选择的关系更复杂，通常不能替代形状重载。编译器若接受某种非标准“函数偏特化”写法，应视为扩展而非 ISO C++11。

## 489【节点：X22】【易混复习】`template<typename T>` 与 `typename T::value_type` 中的 `typename` 各做什么？

**答案：** 模板头里的 `typename` 声明 `T` 是类型形参，在此处与 `class T` 等价；依赖限定名之前的 `typename` 则告诉解析器 `T::value_type` 应按类型解释，因为定义模板时还不知道 `T` 的成员种类。依赖对象调用成员模板使用的是另一关键字，例如 `object.template convert<U>()`。这些消歧规则属于 ISO C++11；`typename` 不能把实例化后实际不是类型的成员强行变成类型。

## 490【节点：X23】【易混复习】`std::move` 和 `std::forward` 的使用意图怎样区分？

**答案：** `std::move(value)` 无条件把表达式转换为右值类别，表示当前代码愿意放弃该值的当前状态；`std::forward<T>(value)` 只在转发模板中结合推导结果，调用方传左值就继续传左值，传右值就恢复右值。移动构造实现常对成员使用 `move`，转发包装器对转发引用使用 `forward<T>`。二者位于 `<utility>`，转换规则属于 ISO C++11；是否真正移动仍取决于下游重载。

## 491【节点：X23】【综合巩固】转发包装器若把形参直接传递、统一 `move`、使用 `forward`，三种结果有何不同？

**答案：** 假定 `target` 已定义，下面是模板函数片段：

```cpp
template<class T>
void relay(T&& value)
{
    target(value);                  // 永远按左值
    target(std::move(value));       // 永远按右值候选
    target(std::forward<T>(value)); // 恢复调用方值类别
}
```

具名 `value` 是左值，所以第一种丢失右值信息；第二种可能意外移动调用者传入的左值；第三种才是完美转发的意图。现实代码不会依次执行这三行，因为前一次调用可能改变对象；这里仅作对比片段。规则是 ISO C++11，`forward` 也不会亲自移动资源。

## 492【节点：X24】【易混复习】Lambda 的按值捕获是在创建闭包时还是调用闭包时复制？

**答案：** 在执行 Lambda 表达式、创建闭包对象时保存当时的值，以后调用读取闭包副本，外部变量变化不会自动同步。复制闭包又会复制其按值状态。按值捕获指针只复制地址，仍可能悬空；捕获 `shared_ptr` 复制的是共享所有者，并非目标对象。C++11 不支持 `[name = expression]` 初始化捕获，该语法从 C++14 开始。捕获时机与闭包语义属于 ISO C++11。

## 493【节点：X25】【易混复习】成员函数里的 `[=]` 是否会复制整个当前对象？

**答案：** C++11 中不会。若 Lambda 使用非静态成员，`[=]` 会隐式按值保存 `this` 指针，后续成员访问仍作用于原对象；原对象先析构就产生悬空指针。`[*this]` 的对象副本捕获是 C++17。严格 C++11 若只需独立快照，可先把所需成员复制到局部变量，再按值捕获这个局部变量；若要维持对象生命，则按所有权设计使用 `shared_ptr`。版本划分和 `this` 捕获语义都是 ISO 标准边界。

## 494【节点：X26】【易混复习】Lambda 的 `mutable` 修改的是外部变量还是闭包副本？

**答案：** 它允许修改按值捕获的闭包成员，不会把捕获方式变为引用，也不会修改外部原变量。默认闭包的调用运算符是 `const`；加 `mutable` 后内部状态可随调用变化：

```cpp
int main()
{
    int n = 0;
    auto counter = [n]() mutable { return ++n; };
    return counter() == 1 && counter() == 2 && n == 0 ? 0 : 1;
}
```

`mutable` 的位置和效果属于 ISO C++11，但它不提供线程安全；多个线程共享同一可变闭包仍需同步。

## 495【节点：X27】【易混复习】为什么无捕获 Lambda 能转成函数指针，而有捕获 Lambda 不能？

**答案：** 普通函数指针只保存可调用代码地址，没有空间携带闭包状态。C++11 允许无捕获 Lambda 隐式转换为签名兼容的普通函数指针，例如 `int (*p)(int)=[](int x){return x+1;};`；有捕获 Lambda 需要保存数据，不能直接转换。可用其具体闭包类型或 `std::function` 保存，但后者有类型擦除和复制等成本。C 风格回调常另带 `void*` 上下文，这是接口/ABI 工程模式，不是 Lambda 自动完成的所有权管理。

## 496【节点：X28】【易混复习】`vector` 已经 `reserve(100)` 后，为什么仍可能 `size()==0` 且不能访问 `v[0]`？

**答案：** `capacity()` 表示现有存储不重分配时最多可容纳到多少元素，`size()` 才表示已经构造并属于容器的元素数。`reserve` 只调整容量，不创建元素，所以未使用槽位中没有可访问的 `T` 对象，合法下标仍必须小于 `size()`。大小、容量和对象生命期是 ISO C++11 容器合同；具体分配了多少额外字节以及增长倍率属于实现选择。

## 497【节点：X29】【易混复习】`reserve`、`resize` 和 `shrink_to_fit` 分别承诺什么？

**答案：** `reserve(n)` 请求容量至少为 `n`，不改变元素数，小于当前容量的请求不强制缩小；`resize(n)` 真正改变 `size()`，扩大时构造元素，缩小时销毁尾部元素；`shrink_to_fit()` 请求降低多余容量，但在 C++11 是非强制请求，实现可以不缩。三者的基本合同属于 ISO C++11，实际容量值和是否执行收缩由实现决定。不能用 `reserve` 代替创建元素。

## 498【节点：X30】【易混复习】`map[key]`、`find(key)` 和 `at(key)` 应怎样按意图选择？

**答案：** 需要“没有就建立默认值并修改”时使用非常量 `map[key]`；只想判断或取得可选位置时用 `find`，并与 `end()` 比较；业务要求键必有、缺失按异常处理时用 `at`，它不插入且抛 `std::out_of_range`。`operator[]` 不能用于 `const map`，也要求相应映射值能完成所需默认构造。三种接口行为是 ISO C++11；把缺键视为错误还是普通分支是应用设计。

## 499【节点：X30】【综合巩固】读取配置表时，哪种访问方式会意外改变表？应怎样写出三个明确分支？

**答案：** 用 `config["timeout"]` 读取会在键缺失时插入值初始化的映射值，可能把“配置缺失”悄悄变成零。若缺失是普通分支，写：

```cpp
std::map<std::string, int>::const_iterator it =
    config.find("timeout");
if (it != config.end())
    use(it->second);
else
    use_default();
```

这是函数体片段，假定 `config`、`use` 和 `use_default` 已定义。若缺失必须报错，可调用 `config.at("timeout")` 并在合适边界处理 `out_of_range`；若确实要累计或创建，再使用 `operator[]`。接口语义是 ISO C++11，错误策略是工程选择。

## 500【节点：X31】【易混复习】`map::insert` 遇到已有键时为什么不能用来覆盖旧值？

**答案：** `map` 的键唯一，`insert` 遇到比较等价键时不替换旧元素，而返回 `pair<iterator,bool>`：`second` 为假，`first` 指向已有元素。需要覆盖时，C++11 可检查返回值后给 `result.first->second` 赋新值，或在映射值可默认构造且语义合适时使用 `operator[]`。`insert_or_assign` 和 `try_emplace` 到 C++17 才有。返回规则与版本边界属于 ISO 标准；覆盖策略需按业务明确。

## 501【节点：X32】【易混复习】已经有一个元素对象时，应机械地把 `push_back` 换成 `emplace_back` 吗？

**答案：** 不应。`push_back` 接收一个现成元素并复制或移动进容器，意图直接；`emplace_back` 接收构造参数并在末尾构造，适合调用者手里还没有元素对象的情况。若已有 `T value`，`push_back(std::move(value))` 往往同样清楚高效。`emplace_back` 不保证少一次分配或更快，还可能选择 `explicit` 构造。C++11 中它返回 `void`，返回引用是 C++17 变化；这些接口合同是 ISO 标准，性能结论应实测。

## 502【节点：X33】【易混复习】为什么泛型代码不能假定迭代器就是 `T*`？

**答案：** 迭代器是满足一组操作要求的类型，可能封装节点位置、调试检查、代理状态或真实指针。`vector<int>::iterator` 提供随机访问，但标准不要求类型等于 `int*`；`list<int>::iterator` 不能做 `it+1`。泛型代码应使用 `*it`、`++it`、比较和 `iterator_traits` 等约定接口。迭代器能力和类别是 ISO C++11 合同；具体内部表示属于库实现，不能依赖。

## 503【节点：X34】【易混复习】完整的 erase-remove 惯用法解决了哪两个不同层次的问题？

**答案：** `std::remove` 在迭代器区间层次把保留元素移到前部，并返回新逻辑结尾，但不知道容器，不能缩小它；随后容器成员 `erase(new_end,end())` 才结束尾部元素生命并改变大小。合写为 `v.erase(std::remove(v.begin(),v.end(),value),v.end());`。新逻辑结尾后的值不能继续依赖。算法与容器成员语义均是 ISO C++11；链表可用真正删除节点的成员 `remove`，关联容器应使用成员 `erase`。

## 504【节点：X35】【易混复习】为什么未排序的 `unique` 不能保证全局去重？

**答案：** `std::unique` 只比较相邻元素，把每一段连续等价项压缩成一个；相同值若被其他值隔开就会保留。它也只返回新逻辑结尾，不改变容器大小。若允许改变次序，可先 `sort` 让等价项相邻，再执行 `unique` 和 `erase`。比较谓词必须满足算法所需等价关系。以上是 ISO C++11 算法合同，不是实现偶然行为。

## 505【节点：X36】【易混复习】有序容器的“键等价”为何不一定等同于 `operator==`？

**答案：** `map`、`set` 用比较器建立顺序，当 `comp(a,b)` 和 `comp(b,a)` 都为假时就把两键视为等价，唯一键容器只保留一个。自定义不区分大小写比较器可能让 `"Key"` 与 `"key"` 等价，即使字符串 `==` 为假。比较器必须形成严格弱序，键存入后不能以破坏顺序的方式改变。等价定义和只读键接口属于 ISO C++11；选择哪种业务等价规则由程序设计决定。

## 506【节点：X37】【易混复习】无序容器“没有保证的顺序”是否表示每次遍历都必然随机变化？

**答案：** 不表示。某个实现和当前状态下顺序可能连续多次相同，但 ISO C++11 不承诺它按键、按插入顺序或跨运行稳定；插入、删除和 rehash 也可能改变次序。不能把观察到的稳定性提升为协议。需要稳定测试、文件或网络输出时应显式排序或改用有序容器。无顺序保证是 ISO 合同；排序后输出是工程上的确定性策略。

## 507【节点：X38】【易混复习】哈希容器的平均 `O(1)` 为什么不能当作实时最坏延迟保证？

**答案：** 平均常数依赖哈希分布和装载因子合理。大量碰撞会让单个桶中需要逐个比较，最坏查找、插入或删除可退化到线性；rehash 本身也可能搬迁大量桶关系。`reserve`、`rehash` 和负载因子只能帮助规划，不能提供强制最坏 `O(1)` 的接口。标准给出的复杂度类别属于 ISO C++11；实际哈希成本、缓存行为、攻击输入和延迟目标需要工程测量与安全设计。

## 508【节点：X39】【易混复习】为什么链表插入是 `O(1)`，真实程序中仍常被 `vector` 击败？

**答案：** 链表只有在已经持有正确位置时，局部链接修改才是常数；寻找位置仍可能线性。每个节点通常还需额外指针、独立分配，并使遍历跨越分散内存，缓存局部性较差。`vector` 搬移元素可能更昂贵，但连续遍历、预取和较少分配常带来更好真实性能。容器复杂度与失效保证是 ISO C++11 合同；缓存布局、分配器和基准结果依赖实现、硬件和工作负载，必须实测。

## 509【节点：X40】【版本边界】“我的编译器能通过”为什么不足以证明代码属于 C++11？

**答案：** 编译器可能默认启用 C++14/17/20，或接受厂商扩展。特性归属由相应 ISO 标准版本决定，不由一次编译成功决定：`make_unique`、泛型 Lambda 是 C++14；`string_view`、结构化绑定、`try_emplace` 是 C++17；Concepts、Ranges 是 C++20。应显式选择 C++11 模式并启用严格诊断，再核对标准文档。`-std=c++11 -pedantic-errors` 是 GCC/Clang 工程选项，不是 ISO C++ 源语言语法；其他工具链有等价但不同的配置。

## 510【节点：X40】【综合巩固】交付“严格 C++11”题目或代码前，应做哪四层版本检查？

**答案：** 第一，逐项核对语言语法和库接口首次进入的标准版本，不能凭记忆或默认编译结果；第二，用工具链显式切到 C++11 并启用尽可能严格的扩展诊断；第三，在代码与说明中标出故意展示的后续版本错误示例，不让它伪装成可用代码；第四，区分 ISO 保证与 ABI、编译命令、库实现、性能观察等工程事实。还应至少编译所有声称完整的示例，并对仅为声明、伪代码或错误演示的块明确标注。编译开关和 CI 流程属于非 ISO 工程控制，真正的版本归属仍以标准规则为准。
