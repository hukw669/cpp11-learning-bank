# C++11 第十八批题目（511–540）：异常与对象存储

> 本批区分 ISO C++11 核心语言、C++11 标准库与工程/ABI 概念；平台实现细节不会被写成语言保证。

## 511【节点：EX-01】【工程概念】“错误”“C++ 异常”和“程序缺陷”有什么区别，为什么不能全部用同一种方式处理？

**答案：** “错误”是操作未按预期完成的总称；“异常”是 C++ 的一种非局部错误报告机制；“程序缺陷”则是代码违反自身应满足的规则。文件不存在、网络暂时失败等运行时错误可能需要返回错误码、重试或抛异常；非法内部状态通常应通过测试、断言或终止尽早暴露。

`assert(condition)` 适合检查开发期“不应失败”的内部条件，并且可能因 `NDEBUG` 而被禁用，不能承担用户输入校验或必要业务逻辑。ISO C++11 只规定返回、异常、断言等机制，不替项目决定错误策略；策略要依据能否恢复、接口契约、资源清理和 ABI 边界选择。

## 512【节点：EX-02】【ISO C++11·语法】`throw`、`try` 和 `catch` 怎样组成一次完整的异常处理流程？

**答案：** 抛出写 `throw expression;`，受保护语句和处理器写成：

```cpp
try {
    if (value < 0)
        throw std::invalid_argument("negative");
    use(value);
} catch (const std::invalid_argument& error) {
    std::cerr << error.what();
} catch (...) {
    // 最后的兜底处理器
}
```

执行 `throw` 后，抛出点之后的正常语句不再继续，运行时沿动态调用链寻找第一个匹配处理器并展开已退出的作用域。处理器正常结束后，控制流转到整个 `try`—`catch` 语句之后；如果最终没有处理器匹配，则调用 `std::terminate`。示例分别需要 `<stdexcept>` 和 `<iostream>`。

## 513【节点：EX-03】【ISO C++11·语义】抛出局部对象后，处理器为什么不会得到对该局部对象的悬空引用？

**答案：** `throw expression;` 会用表达式初始化一个由异常运行时管理的独立异常对象。异常对象不是原局部变量的引用，因此离开抛出函数后仍能存在；其类型由抛出表达式的静态类型按异常对象规则确定，顶层 `const` 和引用不会成为异常对象类型的一部分。

```cpp
void fail()
{
    std::runtime_error local("failed");
    throw local;
}
```

这里处理器捕获的是独立异常对象。相反，`throw pointer;` 只复制指针值；若它指向局部数据，指向内容仍会悬空。异常对象初始化还可能涉及复制、移动或允许的复制消除，所以可抛类型应能可靠构造。

## 514【节点：EX-04】【ISO C++11·规则】异常处理器按什么顺序匹配，为什么派生类处理器必须放在基类处理器前？

**答案：** 处理器按源码出现顺序检查，选择第一个允许匹配异常对象的 `catch`。常见排列是：

```cpp
catch (const std::out_of_range& e) { /* 更具体 */ }
catch (const std::exception& e)    { /* 更一般 */ }
catch (...)                        { /* 任意异常 */ }
```

派生异常可匹配无歧义公共基类引用，所以若 `std::exception` 处理器在前，后面的 `std::out_of_range` 处理器永远没有机会。匹配不是普通函数重载：不会为了匹配随意进行数值转换或用户定义转换，例如 `throw 1;` 不会被 `catch(double)` 捕获。

## 515【节点：EX-05】【ISO C++11·惯用法】为什么异常通常写成 `catch (const T& e)`，而不是按值捕获？

**答案：** `catch (const T& e)` 不需要为处理器参数再复制异常对象，并且在 `T` 是多态基类时保留原异常对象的动态类型。按值写 `catch (T e)` 会产生处理器参数副本；若抛出的是派生类而 `T` 是基类，还会发生对象切片。

```cpp
try {
    work();
} catch (const std::exception& e) {
    std::cerr << e.what();
}
```

`const` 表示处理器只观察异常，符合大多数错误处理需求。它不会改变处理器的匹配顺序，也不会让异常所携带的裸指针自动获得所有权。

## 516【节点：EX-06】【ISO C++11·语义】什么是异常传播和栈展开，哪些资源会自动清理？

**答案：** 当前函数没有匹配处理器时，异常沿实际调用链向外传播。传播离开作用域时会进行栈展开：已经完成构造的自动对象按构造逆序析构，数组中已经构造的元素、已构造的成员和基类子对象也按相应逆序清理。

```cpp
std::lock_guard<std::mutex> lock(mutex);
risky_operation(); // 抛出时 lock 的析构函数仍会解锁
```

语言只会自动析构对象，不会猜测一个裸 `new` 指针、文件描述符或手工 `mutex.lock()` 代表什么资源。因此应把这些资源交给 RAII 对象。若在栈展开期间又有析构异常逃出，程序会终止。

## 517【节点：EX-07】【ISO C++11/工程】RAII 为什么能同时覆盖正常返回和异常退出？

**答案：** RAII 把资源的取得放进构造，把释放放进析构，并由一个对象明确拥有资源。自动对象无论因正常离开作用域、`return` 还是异常展开而销毁，都会执行析构，因此所有退出路径共用同一套清理逻辑。

```cpp
std::unique_ptr<int> value(new int(7));
may_throw();
```

即使 `may_throw()` 抛异常，`value` 仍会删除整数。一个可靠的 RAII 类通常禁止不合适的复制，按资源语义实现移动，并使析构不让异常逃出。调用 `release()` 会主动放弃智能指针的管理责任，之后必须由调用方重新接管资源。

## 518【节点：EX-08】【ISO C++11·语法】`throw;` 与 `throw e;` 在处理器中有什么本质区别？

**答案：** 活动处理器中的无操作数 `throw;` 重新抛出当前异常对象，保留其原始动态类型：

```cpp
catch (const std::exception& e) {
    log(e.what());
    throw;
}
```

`throw e;` 则用表达式 `e` 重新初始化一个异常对象。若 `e` 的静态类型是基类，原派生部分可能被切掉。没有正在处理的异常时执行裸 `throw;` 会调用 `std::terminate`，所以它只能出现在能够确定存在当前异常的处理路径中。

## 519【节点：EX-09】【C++11·标准库】常用标准异常类型怎样分层，选择类型时应注意什么？

**答案：** `<exception>` 提供常用基类 `std::exception` 和虚函数 `what()`；`<stdexcept>` 中 `std::logic_error` 的常见派生类有 `invalid_argument`、`domain_error`、`length_error`、`out_of_range`，`std::runtime_error` 用于运行环境相关失败；`std::bad_alloc` 位于 `<new>`。

这些名字表达大致错误类别，但不会自动形成项目契约。容器的 `at()` 越界会抛 `out_of_range`，普通分配失败通常抛 `bad_alloc`；自定义异常通常公开继承 `std::exception` 并保证 `what()` 不抛。调用方仍应按接口文档而不是只按类型名字决定如何恢复。

## 520【节点：EX-10】【ISO C++11·语法】构造函数失败时哪些子对象会销毁，函数 try 块怎样覆盖初始化列表？

**答案：** 构造函数无法建立类不变量时可以抛异常。此时已经构造完成的成员和基类会自动析构，最外层对象因为从未完成构造，其析构函数不会执行。构造函数函数 try 块格式为：

```cpp
C::C(int n)
try : member_(make_member(n))
{
    finish();
}
catch (...) {
    log_failure();
    throw;
}
```

它同时覆盖成员初始化列表和函数体。进入处理器时，失败对象的已构造子对象已经按规则清理，不应再依赖它们。构造函数函数 try 块的处理器不能把失败“处理后返回一个半成品对象”；处理器正常到达末尾时异常仍会重新抛出。

## 521【节点：EX-11】【ISO C++11·规则】为什么析构函数通常不得让异常逃出，清理失败又该怎样报告？

**答案：** 析构函数会在正常退出和异常展开期间执行。若已有异常正在传播，另一个析构异常再逃出，就无法同时传播两者，运行时调用 `std::terminate`。因此资源类通常写成 `~Resource() noexcept`，在内部完成不抛清理。

若关闭、提交等操作的失败必须反馈，应另提供显式 `close()`、`commit()` 等可能抛出或返回错误的接口，让用户在对象析构前处理；析构函数只做最后的尽力清理、记录或按契约终止。C++11 中析构函数的隐式异常说明受成员和基类析构函数影响，不能仅凭“它叫析构函数”就假定任意实现都绝对不抛。

## 522【节点：EX-12】【ISO C++11·语法】`noexcept` 异常说明与 `noexcept(expression)` 运算符分别做什么？

**答案：** 函数声明后的 `noexcept` 是承诺：

```cpp
void release() noexcept;
void transfer() noexcept(condition);
```

若异常逃出一个实际为不抛的函数，程序调用 `std::terminate`；它不是自动捕获并忽略异常。表达式形式 `noexcept(expr)` 则不执行 `expr`，只在编译期产生 `bool`，表示该表达式按语言规则是否被认为不会抛：

```cpp
static_assert(noexcept(obj.swap(other)), "swap may throw");
```

条件式异常说明和查询常用于泛型代码，但承诺必须与真实调用链一致。

## 523【节点：EX-13】【C++11·语言/标准库】为什么移动构造是否 `noexcept` 会影响容器扩容策略？

**答案：** 容器扩容要把旧存储中的元素转移到新存储。如果移动构造可能抛，而复制构造可用，移动到一半失败可能已经改变旧元素，不利于保持强异常保证；实现因而可能选择复制。资源类型在确实安全时通常声明：

```cpp
Widget(Widget&& other) noexcept;
```

`<utility>` 中的 `std::move_if_noexcept(x)` 会在“不抛移动”或“不可复制”时提供右值引用，否则提供 `const T&`，供泛型代码选择较安全路径。不能为了性能给真实会抛的移动操作强行标 `noexcept`，否则原本可处理的失败会变成终止。

## 524【节点：EX-14】【工程概念】异常安全的无泄漏、基本、强和不抛保证分别承诺什么？

**答案：** 无泄漏保证资源不会因失败丢失；基本保证要求异常后对象仍满足不变量，但值可能改变；强保证要求操作像从未发生；不抛保证要求操作不会让异常逃出。保证越强，实现成本通常越高，并非每个接口都适合强保证。

常见强保证方法是“先准备、后提交”：先在临时对象完成所有可能失败的工作，成功后通过不抛的 `swap` 或提交步骤生效。外部 I/O、回调或远程系统已经产生的副作用往往无法简单回滚，所以异常保证必须按接口范围明确记录，不能把 copy-and-swap 当成万能事务。

## 525【节点：EX-15】【C++11·标准库】`std::error_code` 与 `std::system_error` 怎样表达同一失败的非抛出和异常接口？

**答案：** `<system_error>` 中的 `std::error_code` 由数值和 `error_category` 共同确定含义，适合显式返回或输出参数；`std::system_error` 则把错误码与上下文包装成异常。

```cpp
std::error_code ec =
    std::make_error_code(std::errc::permission_denied);

if (ec)
    std::cerr << ec.message();

throw std::system_error(ec, "open configuration");
```

不能只比较 `ec.value()`，因为不同 category 的相同数值可能含义不同。错误码路径需要调用方主动检查，异常路径需要明确捕获边界，两种接口都应形成可验证契约。

## 526【节点：EX-16】【C++11·标准库】怎样把一个线程捕获的异常安全地交给另一个线程重新抛出？

**答案：** `<exception>` 提供 `std::exception_ptr`、`std::current_exception()` 和 `std::rethrow_exception()`。工作线程必须在入口内部捕获：

```cpp
std::exception_ptr failure;
std::thread worker([&] {
    try {
        work();
    } catch (...) {
        failure = std::current_exception();
    }
});
worker.join();

if (failure)
    std::rethrow_exception(failure);
```

`join()` 在此建立工作完成同步，所以主线程随后读取该变量。若多个线程并发访问同一个 `exception_ptr` 变量，仍需另行同步。异常直接逃出线程入口会导致 `std::terminate`；`promise`/`future` 共享状态也能自动保存并在 `get()` 时重抛异常。

## 527【节点：EX-17】【C++11·标准库】怎样在添加高层错误上下文时保留原始异常？

**答案：** 在正在处理底层异常时，可用 `std::throw_with_nested` 抛出带上下文的高层异常：

```cpp
try {
    open_and_parse();
} catch (...) {
    std::throw_with_nested(
        std::runtime_error("loading configuration failed"));
}
```

外层捕获后，可对异常对象调用 `std::rethrow_if_nested(e)`，若其携带嵌套异常便重新抛出内层原因，再递归打印。相关接口位于 `<exception>`。不是每个任意异常对象都必然含内层异常，日志也要避免泄露敏感路径、凭据等底层信息。

## 528【节点：EX-18】【ABI/工程边界】为什么 C++ 异常不应穿过任意 C ABI、插件或不兼容动态库边界？

**答案：** ISO C++11 规定语言异常语义，却不统一各平台的异常对象布局、栈展开器、运行库和二进制 ABI。`extern "C"` 主要指定语言链接和名称规则，不会自动统一类布局、分配器或异常机制。因此稳定入口通常在 C++ 一侧吞并转换所有异常：

```cpp
extern "C" int api_run() noexcept
{
    try {
        work();
        return 0;
    } catch (...) {
        return -1;
    }
}
```

真实接口还应通过稳定状态码、调用者缓冲区或查询函数提供错误详情，并规定资源由哪一侧释放。异常跨兼容的 C++ 共享库是否可行属于具体 ABI、编译器和运行库契约，不是 ISO C++11 的可移植保证。

## 529【节点：MEM-01】【ISO C++11·概念】对象、地址、字节和存储分别是什么，为什么“有一块内存”不等于“其中已有一个对象”？

**答案：** 对象是具有类型和生存期的实体；地址定位其存储；字节是 `sizeof` 使用的最小可寻址单位，且 `sizeof(char) == 1`；存储只是容纳对象表示的区域。对象的类型决定如何解释其中的值，完整对象还可能包含成员、基类子对象和填充字节。

```cpp
int value = 42;
int* address = &value;
const unsigned char* bytes =
    reinterpret_cast<const unsigned char*>(address);
```

这里 `value` 是活动对象，`address` 保存地址，`bytes` 可观察对象表示。仅取得一块大小和对齐合适的原始存储，还必须按对象生存期规则构造 `T`，才能通常把它当作 `T` 使用。

## 530【节点：MEM-02】【ISO C++11·概念】作用域、链接和存储期各回答什么问题？

**答案：** 作用域回答“源码的哪些位置能使用这个名字”；链接回答“不同声明是否表示同一实体”；存储期回答“对象所占存储存在多久”。三个维度相互独立。

```cpp
extern int shared;       // 可声明具有外部链接的对象
static int internal;     // 命名空间作用域下通常为内部链接

void count()
{
    static int calls;    // 块作用域、无链接、静态存储期
    ++calls;
}
```

名字离开作用域不必意味着对象销毁；`static` 在不同上下文也可能影响链接、存储期或类成员性质，不能简单记成一种“静态变量”。

## 531【节点：MEM-03】【ISO C++11·规则】四种存储期是什么，下面每个对象分别属于哪一种？

**答案：** 四种存储期是自动、静态、线程和动态存储期：

```cpp
int global_value;             // 静态存储期
thread_local int per_thread;  // 线程存储期

void f()
{
    int local;                // 自动存储期
    static int persistent;    // 静态存储期
    int* pointer = new int;   // 所指 int 为动态存储期
    delete pointer;
}
```

最后一例的 `pointer` 变量本身仍通常是自动存储期，只有 `new` 创建的整数具有动态存储期。存储期不等于作用域，也不完全等于对象生存期；动态对象不会因保存其地址的局部指针离开作用域而自动释放。

## 532【节点：MEM-04】【工程/实现边界】为什么“局部变量一定在栈上、`new` 对象一定在堆上”不是 ISO C++11 保证？

**答案：** ISO C++11 用对象、存储期和生存期描述程序语义，不要求实现采用某种机器栈或统一进程堆。常见实现把调用帧和许多自动对象放在线程栈，把动态分配交给堆分配器，但优化器可以把对象放入寄存器、标量替换或完全消除。

递归过深可能耗尽线程栈、大量 `new` 可能造成分配器压力，这些是重要工程现象，却取决于编译器、ABI、操作系统和分配器。推理语言正确性时应说“自动存储期对象”和“动态存储期对象”；分析性能或故障时再结合目标平台的栈、堆实现。

## 533【节点：MEM-05】【ISO C++11·语法】默认初始化、值初始化、直接初始化和列表初始化对基本类型有什么区别？

**答案：** 常见形式如下：

```cpp
int a;       // 自动存储期下值不确定，读取会有未定义行为
int b{};     // 值初始化，结果为 0
int c(3);    // 直接初始化
int d{3};    // 列表初始化，并检查窄化

int* p = new int;    // 所指 int 的值不确定
int* q = new int();  // 所指 int 为 0
```

静态和线程存储期对象在其他初始化之前会先零初始化；类类型则由选中的构造函数建立状态。分配器或操作系统碰巧返回全零字节不能替代语言初始化保证，读取未初始化自动标量不是得到“随机但合法的值”。

## 534【节点：MEM-06】【ISO C++11·语义】原始存储、对象生存期、放置 new 和显式析构之间是什么关系？

**答案：** 原始存储只有大小和对齐；在其中通过构造开始 `T` 对象的生存期后，程序才能通常按 `T` 使用。低层手工流程可以是：

```cpp
void* raw = ::operator new(sizeof(T));
T* object = new (raw) T(arguments);

use(*object);

object->~T();
::operator delete(raw);
```

放置 new 需要 `<new>`，它只构造、不分配；显式析构只结束对象生存期、不释放底层存储。地址必须满足 `T` 的对齐，构造和析构必须恰好配对，异常路径也要释放原始存储。普通业务代码应优先交给 RAII 容器或智能指针。

## 535【节点：MEM-07】【ISO C++11·辨析】空指针、悬空指针和野指针有什么区别，`p != nullptr` 能证明什么？

**答案：** 空指针明确不指向对象，C++11 应写 `T* p = nullptr;`；悬空指针曾指向有效对象，但对象生存期已经结束；“野指针”是工程俗称，通常指未初始化或含不可证明有效地址的指针。

```cpp
int* p = nullptr;
{
    int local = 1;
    p = &local;
} // p 现在悬空，但通常仍不等于 nullptr
```

因此 `p != nullptr` 只排除空指针，不能证明对象仍存活、类型正确或地址可解引用。删除后把一个指针置空有助于避免其再次使用，却不会同步修复其他别名。

## 536【节点：MEM-08】【工程概念】为什么函数参数或返回值中的 `T*` 不能单独说明所有权？

**答案：** `T*` 只表达“一个可能指向 `T` 的地址”，不说明它是借用、独占所有、共享所有、数组首元素还是可空观察者。看到裸指针就 `delete` 可能删除栈对象、内部对象或已由其他所有者管理的对象。

接口应让类型和文档共同表达契约，例如 `std::unique_ptr<T> create()` 转移独占所有权，`std::shared_ptr<T>` 表达共享所有权，`void inspect(const T*)` 可约定只借用且允许空。借用接口还必须说明被指对象的有效期以及哪些操作会使指针失效。

## 537【节点：MEM-09】【ISO C++11·语法】`new`/`delete` 与 `new[]`/`delete[]` 为什么必须配对？

**答案：** new 表达式先取得存储再构造对象，delete 表达式先析构对象再释放相应存储。数组形式还要记录并逐个析构元素：

```cpp
T* one = new T(arguments);
delete one;

T* many = new T[count]();
delete[] many;
```

混用 `delete` 与 `delete[]`、重复删除、删除并非相应 new 表达式产生的地址，都会导致未定义行为。通过基类指针删除派生对象还要求基类提供合适的虚析构函数。日常代码优先使用自动对象、容器、`unique_ptr<T>` 或 `unique_ptr<T[]>`。

## 538【节点：MEM-10】【C++11·标准库】普通 `new` 与 `new (std::nothrow)` 怎样报告分配失败？

**答案：** 普通 new 表达式的分配阶段最终失败时通常抛出 `<new>` 中的 `std::bad_alloc`。不抛出分配形式写：

```cpp
T* object = new (std::nothrow) T;
if (!object)
    handle_allocation_failure();
```

`std::nothrow` 只改变分配函数失败的报告方式；如果存储已经取得而 `T` 的构造函数自身抛异常，该异常仍可传播。项目应选择异常、显式空指针或上层降级策略，而不是默认认为内存永远足够。

## 539【节点：MEM-11】【C++11·标准库/C 互操作】`malloc`、`calloc`、`realloc` 和 `free` 为什么不能直接替代 C++ 对象管理？

**答案：** `<cstdlib>` 中这些函数管理原始字节存储，不调用 C++ 构造函数和析构函数；C++ 也不允许把返回的 `void*` 隐式转换成任意对象指针。它们适合 C API 互操作或低层分配器，而不是直接创建有非平凡构造/析构的对象。

`realloc` 可能移动存储并使旧地址失效，失败时旧块仍有效，所以不能在未保存原值时直接覆盖唯一指针。`malloc` 必须与 `free` 配对，不能与 `delete` 混用。若要在这类存储中建立 C++ 对象，还要正确处理对齐、放置 new、生存期、显式析构和异常回滚。

## 540【节点：MEM-12】【ISO C++11·低层语法】放置 new 的第二个参数是什么，为什么 `delete object;` 不是对应释放方式？

**答案：** 标准放置 new 形式 `new (address) T(args)` 接收调用者提供的地址，只在该地址构造对象，不负责取得存储：

```cpp
void* raw = ::operator new(sizeof(T));
T* object = new (raw) T(7);

object->~T();
::operator delete(raw);
```

对象是通过放置 new 建立的，底层存储来自单独的 `::operator new` 调用，所以应先显式析构，再用与原分配匹配的释放函数释放。直接 `delete object` 会把两套协议混在一起。还必须保证对齐、只析构一次，并在构造抛出时回收 `raw`。
