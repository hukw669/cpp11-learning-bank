## 031.【B0.1 程序、源文件和可执行文件】某目录含 `main.cpp`、`math.cpp`、`math.h`、`main.o`、`math.o` 和 `calculator.exe`。若只允许保留人编写的代码，哪些文件应优先保留？

**答案：** 应优先保留 `main.cpp`、`math.cpp` 和 `math.h`。前两者是源文件，头文件 `math.h` 也属于源代码的一部分；`main.o`、`math.o` 是翻译产生的目标文件，`calculator.exe` 是链接后的可执行文件，通常可以根据源代码和相同工具配置重新生成。是否能成功重建还取决于所需工具、库和构建参数，而不只取决于文件扩展名。

## 032.【B0.1 程序、源文件和可执行文件】程序员把 `hello.cpp` 中的输出从 `"A"` 改成 `"B"`，但没有重新构建，直接运行原来的 `hello.exe`。通常会执行哪一版代码？为什么？

**答案：** 通常仍执行旧可执行文件中的代码，也就是修改源文件前已经被翻译进去的版本。编辑 `.cpp` 只改变源代码文本，不会自动改写现有目标文件或可执行文件；必须重新完成受影响文件的编译并再次链接，新的行为才会进入新的可执行文件。若开发工具启用了自动构建，那也是工具替用户执行了这些步骤，而不是运行时直接读取 `.cpp`。

## 033.【B0.1 程序、源文件和可执行文件】只看到三个 `.cpp` 文件，能否断定它们一定生成一个可执行文件？

**答案：** 不能。这三个源文件可能共同组成一个程序，也可能被分配给多个程序，甚至暂时没有被加入任何最终链接。ISO C++11 不规定项目目录和构建分组；哪些翻译单元被链接到哪个可执行文件，由实际构建命令或构建系统决定。因此，源文件数量不能直接推出可执行文件数量。

## 034.【B0.3 必须先掌握的术语】`std::cout` 是一个单独的标识符吗？编译器在什么阶段检查这个名字能否找到？

**答案：** `std::cout` 是限定名，不是一个单独的标识符；其中 `std` 和 `cout` 分别是标识符，`::` 表示从 `std` 命名空间查找 `cout`。名字查找及相应的类型检查发生在编译期。程序进入运行期前，这个名字必须已经按当前翻译单元可见的声明得到解释。

## 035.【B1.1 实际工具链流程】把下列现象分别归入最相关的阶段：找不到被包含的头文件、发现 `int x = ;`、找不到已调用函数的定义、操作系统启动程序。

**答案：** 找不到被包含的头文件通常发生在预处理阶段；`int x = ;` 不符合 C++ 语法，通常在编译阶段诊断；调用处已有声明但最终找不到函数定义，通常在链接阶段报告；操作系统启动已生成的程序属于加载与运行阶段。汇编位于编译和链接之间，通常负责产生目标文件。

## 036.【B1.1 实际工具链流程】下面代码中的错误语句会导致 C++ 编译错误吗？

```cpp
#if 0
int broken = ;
#endif

int ready = 1;
```

**答案：** 不会由这条被排除的语句导致编译错误。预处理器先计算 `#if 0`，不把其中的记号送入后续翻译，因此编译器看到的是合法的 `int ready = 1;`。这说明条件编译发生在正式语法和类型检查之前；它不是运行时的 `if`。

## 037.【B1.2 翻译单元】`a.cpp` 和 `b.cpp` 都包含带 Include guard 的 `common.h`。整个程序中会形成几个翻译单元？`common.h` 的内容只会出现一次吗？

**答案：** 通常形成两个翻译单元：一个以 `a.cpp` 为起点，另一个以 `b.cpp` 为起点。Include guard 只防止头文件在同一个翻译单元内反复展开；`common.h` 的主体仍会分别进入这两个翻译单元。因此，保护宏不能让一个不允许跨翻译单元重复定义的普通实体自动符合单一定义规则。

## 038.【B1.2 翻译单元】`main.cpp` 包含 `first.h`，而 `first.h` 又包含 `second.h`。若只编译 `main.cpp`，这是一个翻译单元还是三个？

**答案：** 是一个翻译单元。预处理从 `main.cpp` 开始，把 `first.h` 的内容纳入，又继续把 `second.h` 的内容纳入，最后把合成后的结果交给编译器。两个头文件不会因此分别成为独立运行或独立链接的单元；只有另一个源文件也被编译时，才通常会形成另一个翻译单元。

## 039.【B1.3 声明、定义与分离编译】下列三个文件一起参与构建时，函数 `identity` 的声明和定义能否正确配合？

```cpp
// math.h
int identity(int);

// math.cpp
#include "math.h"
int identity(int value) { return value; }

// main.cpp
#include "math.h"
int main() { return identity(3); }
```

**答案：** 可以。两个源文件通过同一头文件看到完全相同的函数声明，`math.cpp` 提供唯一的函数定义，`main.cpp` 只负责调用。两个翻译单元分别编译后，链接器可把调用解析到该定义。让定义所在的源文件也包含声明头文件，还有助于编译器在声明与定义不一致时尽早诊断。

## 040.【B1.3 声明、定义与分离编译】上一题的源码都正确，但构建时只编译并链接 `main.cpp`，遗漏了 `math.cpp`。再次复制一份 `int identity(int);` 声明能修复问题吗？

**答案：** 不能。`main.cpp` 已经通过头文件获得所需声明，所以继续复制声明不会提供函数实体。问题发生在链接输入：必须编译 `math.cpp` 并把相应目标文件加入链接。这个反例说明“调用处编译成功”和“整个程序能找到定义”是两个不同条件。

## 041.【B1.4 头文件保护】`left.h` 与 `right.h` 都包含 `common.h`，而 `main.cpp` 同时包含 `left.h` 和 `right.h`。Include guard 应放在哪里才能阻止 `common.h` 在该翻译单元中展开两次？

**答案：** `common.h` 自己应拥有唯一的 Include guard；通常每个头文件也都应保护自己的主体。预处理第一次经由某条包含路径进入 `common.h` 时定义保护宏，第二条路径再次进入时便跳过主体。只在 `main.cpp` 周围加条件并不能可靠保护所有其他包含者。若改用 `#pragma once`，应知道它常见但不是 ISO C++11 标准指令。

## 042.【B1.5 单一定义规则 ODR】头文件中直接写普通非 `inline` 函数定义，并被两个源文件包含，可能出现什么问题？怎样最小修改？

```cpp
// answer.h
int answer() { return 42; }
```

**答案：** 每个包含者都会得到一份 `answer` 定义，两个翻译单元进入同一程序时会产生不允许并存的程序级定义，常表现为链接时“重复定义”。最小、基础的修正是让头文件只保留 `int answer();` 声明，并把带函数体的定义移到一个 `.cpp` 文件中。Include guard 只能防止单个翻译单元内重复展开，不能消除不同翻译单元各自得到的定义。

## 043.【B2.3 命名空间】下面最后一行为什么无法确定使用哪个 `count`？怎样做最小纠正？

```cpp
namespace east { int count = 1; }
namespace west { int count = 2; }

using namespace east;
using namespace west;

int selected = count;
```

**答案：** 两条 using namespace 指令都让各自命名空间中的 `count` 参与未限定名字查找，最后一行因此产生二义性。把它改为 `int selected = east::count;` 或 `int selected = west::count;` 即可明确选择。这个例子说明命名空间并未消失；使用限定名仍是解决冲突最直接的方法。

## 044.【B2.3 命名空间】下面哪一行名字查找失败？应怎样修改而不引入整个命名空间？

```cpp
namespace layout {
    int width = 80;
    int height = 25;
}

using layout::width;
int w = width;
int h = height;
```

**答案：** `int h = height;` 查找失败。using 声明 `using layout::width;` 只引入 `width`，不会同时引入 `height`。可把最后一行改为 `int h = layout::height;`，或再写一条明确的 `using layout::height;`。这与 `using namespace layout;` 让命名空间内许多名字参与查找不同。

## 045.【B2.3 命名空间】一个有 Include guard 的头文件在全局作用域写了 `using namespace std;`。保护宏能否阻止这条指令影响包含者？

**答案：** 不能。Include guard 只控制该头文件在一个翻译单元中展开几次；第一次展开时，using namespace 指令仍成为包含者翻译单元的一部分，并改变后续的名字查找。它可能让调用方自己的名字与 `std` 中的名字冲突。普通头文件应优先写 `std::名字`，避免把全局 using namespace 指令强加给所有包含者。

## 046.【B2.4 基本字面量】下面两行中哪一行不符合 C++11？这说明 `nullptr` 具有什么边界？

```cpp
int* pointer = nullptr;
int number = nullptr;
```

**答案：** 第一行符合 C++11，第二行不符合。`nullptr` 是专门的空指针字面量，可转换为相应指针类型，但不是可拿来初始化普通整数的数字零。若需要整数零应写 `0`；若需要表达空指针则应写 `nullptr`。这种区分使代码意图和类型检查都更明确。

## 047.【B2.4 基本字面量】普通字符串字面量 `"A\\nB\nC"` 中，两处看似相近的 `\n` 会产生相同字符吗？

**答案：** 不会。源码中的 `\\n` 先用 `\\` 表示一个普通反斜杠，后面的 `n` 仍是字母，因此得到反斜杠和 `n` 两个字符；随后真正的 `\n` 是一个换行字符。转义从源码记号层面决定字面量内容，不能只根据显示出来的斜杠数量猜测运行时字符。

## 048.【B2.4 基本字面量】下面的原始字符串为什么能在内容中保留反斜杠和 `)"`？

```cpp
R"tag(C:\tmp\)"quoted")tag"
```

**答案：** `tag` 是自定义分隔符，只有完整的 `)tag"` 才结束这个原始字符串，所以内容中的普通 `)"` 不会提前终止它。原始字符串内部不处理普通反斜杠转义，因此 `\t` 也不会变成制表符；字面量内容是 `C:\tmp\)"quoted"`。选择自定义分隔符时，必须确保结束序列不会意外出现在内容中。

## 049.【B2.5 预处理器基础】下面代码为什么可以通过后续语法检查？把 `ENABLED` 改为 `1` 后会怎样？

```cpp
#define ENABLED 0

#if ENABLED
int incomplete = ;
#endif

int complete = 1;
```

**答案：** 当 `ENABLED` 替换为 `0` 时，条件编译排除中间那行，编译器不会看到不完整的声明，只检查 `int complete = 1;`。若把宏值改为 `1`，该行会进入翻译单元并因语法不完整而得到编译诊断。宏和条件编译操作的是记号，不会理解被排除代码的 C++ 类型或意图。

## 050.【B3.1 布尔和字符类型】某协议字段需要保存从 `0` 到 `255` 的非负整数。只在普通 `char` 和 `unsigned char` 中选择时，哪一个更合适？能否因此断言一个字节恰好是 8 位？

**答案：** `unsigned char` 更合适。标准保证它从 `0` 开始，并至少能够表示到 `255`；普通 `char` 的有符号表现由实现决定，不能依赖它在所有平台都把这些值解释为非负数。但这仍不能证明一个字节恰好是 8 位：C++ 的一个字节由 `char` 的大小定义，所含位数由实现的 `CHAR_BIT` 决定，可能多于 8 位。

## 051.【B3.1 布尔和字符类型】能否仅凭名字断言 `sizeof(char16_t) == 2`、`sizeof(char32_t) == 4` 在所有 C++11 实现中都成立？

**答案：** 不能。`char16_t` 和 `char32_t` 是 C++11 的独立基本类型，但 `sizeof` 以实现定义的 C++ 字节计数，而一个字节不保证正好是 8 位。因此，类型名称中的 16 和 32 不能直接换算成固定的 2 个或 4 个 C++ 字节。应查询具体实现，不能把常见机器结果当成标准保证。

## 052.【B3.1 布尔和字符类型】判断下面三行的字面量与对象类型是否对应。它们是否会自动完成任意文本编码转换？

```cpp
wchar_t wide = L'A';
char16_t unit16 = u'A';
char32_t unit32 = U'A';
```

**答案：** 三行的字面量前缀与对象类型对应，均为 ISO C++11 写法：`L` 对应宽字符字面量，`u` 对应 `char16_t`，`U` 对应 `char32_t`。但这些类型和前缀只规定相应的语言表示，并不提供一个自动识别输入编码、转换文件内容或计算用户可见字符数量的系统。

## 053.【B3.2 整数类型】判断：“`long` 的名字比 `int` 长，所以 `sizeof(long)` 必须严格大于 `sizeof(int)`。”

**答案：** 错误。标准要求 `long` 的可表示范围和存储大小关系不小于 `int` 所需的相应关系，但允许二者占用相同字节数；它们即使大小相同也仍是不同类型。类似地，不能仅凭类型名推断固定的位宽，应该依赖标准下限或查询当前实现。

## 054.【B3.2 整数类型】假设某个符合要求的实现报告 `CHAR_BIT == 16`。此时 `sizeof(char)` 是多少？能否继续把一个字节当成 8 位？

**答案：** `sizeof(char)` 仍然是 `1`，但这个实现中的一个 C++ 字节包含 16 位。不能再把一个字节解释成 8 位，也不能套用其他平台上“若干字节等于若干位”的换算。`CHAR_BIT` 与 `sizeof` 必须一起理解：前者给每字节位数，后者按这种字节计数对象大小。

## 055.【B3.4 浮点类型】判断：“把 `float` 全部改成 `double`，所有十进制小数就一定能被精确保存，浮点相等比较也就永远可靠。”

**答案：** 错误。`double` 通常提供不低于 `float` 的精度和范围，但更高精度不等于能精确表示所有十进制小数。许多十进制分数在常见二进制浮点表示中仍需舍入，连续计算还会传播舍入误差。因此，选择更高精度只能减少某些误差，不能建立“任意十进制值都精确”或“可普遍直接比较精确相等”的保证。

## 056.【B3.5 `void` 与空指针类型】严格 ISO C++11 下，下面三行中哪一行合法？为什么？

```cpp
sizeof(void);
void elements[3];
void* pointer = nullptr;
```

**答案：** 只有第三行合法。`void` 是不完整类型，没有可供 `sizeof` 查询的对象大小，因此 `sizeof(void)` 不符合 ISO C++11；数组元素必须是可以形成对象的完整类型，所以不能定义 `void` 数组。`void*` 本身则是完整的指针类型，可以保存空指针值。某些编译器若接受 `sizeof(void)`，那是扩展，不能当作标准 C++11。

## 057.【B3.5 `void` 与空指针类型】有人写 `int* p = nullptr;` 后声称 `nullptr` 的类型就是 `int*`。该推断正确吗？

**答案：** 不正确。`nullptr` 自身具有专门的类型 `std::nullptr_t`；它只是能转换为这里所需的 `int*`。同一个 `nullptr` 也可用于其他指针类型，所以不能从目标变量类型反推字面量本身就是该指针类型。要直接写出 `std::nullptr_t` 这一类型名，应包含 `<cstddef>`。

## 058.【B3.5 `void` 与空指针类型】下面最后一行为什么不符合 C++11？不学习新的强制转换语法时，怎样最小纠正？

```cpp
int value = 3;
void* erased = &value;
int* restored = erased;
```

**答案：** `int*` 可以隐式转为 `void*`，但 C++ 不允许 `void*` 隐式转回具体对象指针，所以最后一行类型检查失败。在这个最小例子中，可直接写 `int* restored = &value;`，或在擦除类型前保留原来的 `int*`。这体现了 `void*` 会丢失静态类型信息，不应替代本来可以保持具体类型的接口。

## 059.【B3.6 大小、范围和对齐】若两个类型的 `sizeof` 结果相同，能否推出它们的对齐要求和数值范围也相同？

**答案：** 不能。`sizeof` 只给出对象占用多少 C++ 字节，结果类型为 `std::size_t`；`alignof` 才查询对齐要求，`std::numeric_limits<T>` 才提供数值类型的范围和其他表示特征。两个类型可以大小相同而对齐或范围不同，也可以范围关系相近但类型不同。大小、位数、范围和对齐必须分别判断。

## 060.【B3.7 枚举基础】下面哪些初始化符合 C++11？如何在不把状态误当整数的前提下修正错误行？

```cpp
enum Color { red, green };
enum class State : unsigned { off, on };

int color_code = red;
int state_code = State::on;
State state = 1;
```

**答案：** `int color_code = red;` 合法，因为普通枚举的枚举常量可隐式转换为整数。后两行不合法：`enum class` 的值不会隐式转换为整数，整数也不能隐式转换为该作用域枚举。若程序需要保存状态，应把最后两行改成 `State state = State::on;` 并继续使用 `State` 类型，而不是先把它降为普通整数。
