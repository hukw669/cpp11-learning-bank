## NETW001：怎样串联应用层、传输层和 IP 层？

**问题：** 计算机网络中的应用层和 IP 层分别负责什么？DNS、HTTP、端口、IP 地址、ARP、MAC 地址和路由器怎样连成一次完整通信？

**核心答案：** 应用层规定“交换什么数据、数据表示什么、双方按什么步骤交互”；传输层用端口把数据交给正确进程，并按所选协议提供可靠字节流、无连接报文或其他传输语义；IP 层把数据封装为独立数据报，依据目的 IP 地址跨网络逐跳转发。主线是：

```text
应用数据
  ↓ 应用协议规定格式和语义
TCP、UDP 或 QUIC 等传输
  ↓ 端口标识应用端点
IP 数据报
  ↓ 目的 IP 决定路由，TTL/Hop Limit 限制跳数
当前链路的帧
  ↓ ARP/NDP 找到下一跳的链路层地址
逐跳转发，直到目的主机解封装给应用
```

IP 只提供无连接、尽力而为的数据报服务，不建立或维护应用连接，也不承诺到达、顺序、唯一性或自动重传；需要的可靠性由 TCP、QUIC 或应用协议等上层机制实现。

### 1. 分层解决的是不同问题

| 层次 | 主要问题 | 常见标识或协议 |
| --- | --- | --- |
| 应用层 | 数据是什么意思，客户端和服务器怎样交互 | 域名、URL、HTTP 方法、DNS 记录、邮件命令 |
| 传输层 | 数据交给哪个进程，采用何种端到端传输语义 | TCP/UDP 端口、TCP、UDP、QUIC |
| 网际层 | 数据报送往哪个 IP 端点，下一跳走哪里 | IPv4、IPv6、ICMP、路由表 |
| 链路层 | 当前这一跳怎样在具体链路上传输 | 以太网帧、Wi-Fi 帧、链路层地址 |
| 物理层 | 比特怎样变成电、光或无线信号 | 铜缆、光纤、无线电 |

分层不是说每个协议只能机械地归入一个格子，而是用职责边界帮助推理。例如 ARP 服务于 IPv4 的下一跳解析，处在 IPv4 与具体链路的边界；IPv6 则把邻居发现建立在 ICMPv6 之上。

### 2. 应用层规定数据语义和交互流程

应用程序不能只把一串字节交给对方，还必须共同约定这些字节的含义。应用层通常规定：

- **角色与交互顺序：** 谁是客户端、服务器或消息代理，谁先发送，何时应答。
- **消息格式与边界：** 请求、响应、命令、字段、正文和编码怎样组织。
- **业务语义：** `GET`、DNS `A` 记录、SMTP `MAIL FROM` 等操作分别表示什么。
- **命名与定位：** URL、域名、邮箱地址、MQTT 主题等怎样表示资源或服务。
- **状态与错误：** 是否保持会话、怎样缓存、超时、重试以及表达错误。
- **安全要求：** 是否认证对端、加密内容、校验完整性；这些能力可能由应用协议自身或 TLS 等安全层提供。

应用层不负责选择 IP 下一跳，也不能仅凭“使用 TCP”就获得业务层的恰好一次处理。传输层解决字节或报文怎样端到端运送，应用层仍要定义消息边界、幂等性、事务和失败恢复。

#### 2.1 常见协议、传输依赖与默认端口

| 协议 | 主要作用 | 常见承载 | 典型端口 |
| --- | --- | --- | --- |
| HTTP | Web 资源请求、响应与 API 语义 | HTTP/1.1、HTTP/2 通常经 TCP；HTTP/3 经 QUIC/UDP | 80；安全部署常用 443 |
| HTTPS | HTTP 使用安全传输 | HTTP/1.1、HTTP/2：TLS/TCP；HTTP/3：集成 TLS 的 QUIC/UDP | 443（TCP 或 UDP 取决于版本） |
| DNS | 查询名称对应的资源记录 | UDP 与 TCP；也可封装为 DoT、DoH | 53/UDP、53/TCP；DoT 常用 853/TCP，DoH 常用 443 |
| DHCPv4 | 分配 IPv4 租约并下发网络参数 | UDP，可在尚无可用地址时广播，并可经中继转发 | 服务器 67、客户端 68 |
| DHCPv6 | 为 IPv6 主机提供地址或其他配置 | UDP，协议流程与 DHCPv4 不同 | 服务器 547、客户端 546 |
| FTP | 文件传输，控制连接与数据连接分离 | TCP | 控制连接 21；主动模式的数据连接常从服务器 20 发起，被动模式由服务器另选端口 |
| SFTP | 在 SSH 上进行文件访问与传输 | SSH/TCP | 通常 22 |
| SMTP | 提交、发送和邮件服务器间转发 | TCP，可使用 STARTTLS 或隐式 TLS | 中继 25、提交 587、隐式 TLS 提交 465 |
| POP3 | 从邮箱服务器读取/下载邮件 | TCP，可升级 TLS 或使用隐式 TLS | 110；隐式 TLS 995 |
| IMAP | 在服务器端管理邮箱并进行多设备同步 | TCP，可升级 TLS 或使用隐式 TLS | 143；隐式 TLS 993 |
| SSH | 安全远程登录、命令执行、隧道和多路通道 | TCP | 22 |
| WebSocket | 建立长期、全双工、带消息帧的通道 | RFC 6455 基线是在 TCP 上握手后传输；`wss` 再使用 TLS | `ws` 常随 HTTP 用 80，`wss` 常随 HTTPS 用 443 |
| MQTT | 面向物联网的代理式发布/订阅消息 | 需要有序、无损、双向字节流，常用 TCP、TLS/TCP 或 WebSocket | 1883；TLS 常用 8883 |
| NTP | 网络时间同步 | 通常 UDP | 123 |
| SNMP | 网络设备查询、管理和通知 | 通常 UDP | 代理 161、Trap/Inform 162 |
| TFTP | 简单文件传输，无 FTP 的完整会话能力 | UDP | 初始请求 69，后续传输使用协商出的端口 |

表中的端口是 IANA 注册或常见部署的**默认约定**，不是协议身份，更不是强制绑定。HTTP 可以监听 `8080`，SSH 可以监听其他端口；反过来，看到 443 也不能仅凭端口断定负载一定是某个具体 HTTP 版本。真正的协议识别还可能依赖配置、URI、DNS 服务发现、TLS ALPN、代理或报文内容。

#### 2.2 HTTP 与 HTTPS：语义、版本和安全承载要分开

HTTP 是无状态的应用层请求—响应协议。“无状态”指协议语义不要求服务器记住上一条请求，不代表网站不能用 Cookie、Token、服务端 Session 或数据库建立登录状态。HTTP 主要规定：

- 方法，如 `GET`、`POST`、`PUT`、`PATCH`、`DELETE`。
- 目标资源、字段、内容表示和缓存条件。
- `2xx`、`3xx`、`4xx`、`5xx` 等响应状态语义。
- 代理、网关、缓存等中间节点怎样转发消息。

HTTP 的核心语义可跨版本保持，但线上的消息编码和承载不同：

```text
HTTP/1.1 ─→ TCP ─→ IP
HTTP/2   ─→ TCP ─→ IP        （在一个连接中复用多个流）
HTTP/3   ─→ QUIC ─→ UDP ─→ IP（QUIC 提供可靠流、多路复用和安全）
```

因此，“HTTP 只能使用 TCP”不成立。HTTP/1.1、HTTP/2 常跑在 TCP 上，而 [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html) 定义的 HTTP/3 使用 QUIC；QUIC 虽以 UDP 为承载，却自行提供可靠流、拥塞控制和加密等能力。

HTTPS 也不是 TCP、UDP 之外的一种传输协议，更准确的理解是“通过安全连接访问 `https` 资源的 HTTP”：

```text
HTTP/1.1 或 HTTP/2 + TLS + TCP
HTTP/3 + QUIC（集成 TLS 1.3）+ UDP
```

TLS 提供机密性、完整性和身份认证。Web 场景通常认证服务器；是否用客户端证书实现双向认证取决于部署策略。端口 443 是默认约定，不是 HTTPS 的定义。

#### 2.3 DNS：名称系统不只是“域名换 IP”

DNS 是分布式命名系统，记录类型不只有 IPv4 地址 `A`，还包括 IPv6 地址 `AAAA`、别名 `CNAME`、邮件交换 `MX`、名称服务器 `NS` 等。客户端通常先询问递归解析器，解析器再使用缓存并查询相应权威服务器。

一次常见解析路径是“桩解析器 → 递归解析器 → 根、顶级域和权威服务器”。递归解析器可按 TTL 缓存结果，因此修改权威记录不保证所有客户端立刻看到新值；缓存命中、负缓存、多个权威回答和 CDN 调度也会让实际结果不同。

把 DNS 简写为“UDP 53”不完整：普通查询常优先使用 UDP，但响应被截断后可重试 TCP，区域传送使用 TCP，[RFC 7766](https://www.rfc-editor.org/rfc/rfc7766.html) 还要求通用 DNS 实现支持 TCP。现代部署也可能使用 DNS over TLS（DoT）或 DNS over HTTPS（DoH），因此不能从端口 53 推断全部 DNS 流量。

#### 2.4 DHCP：主机一开始怎样获得网络配置

DHCPv4 客户端刚接入网络时可能还没有可用 IPv4 地址，典型过程常概括为：

```text
DHCPDISCOVER → DHCPOFFER → DHCPREQUEST → DHCPACK
```

服务器不仅能提供地址，还能提供租期、子网掩码、默认路由器和 DNS 服务器等参数。客户端早期报文可使用广播；当服务器不在同一广播域时，路由器或专用设备可作为 DHCP Relay 转发请求。DHCP 给出的是有期限的租约，客户端需要续租；它不等于永久占有地址。

DHCPv6 是独立协议，使用 UDP 546/547，并非把 DHCPv4 的广播流程原样搬到 IPv6。IPv6 还可能使用无状态地址自动配置（SLAAC），实际网络可只用 SLAAC、只用 DHCPv6，或组合使用。历史上的 RARP 能力有限，不能当作当前常规主机配置方案。

#### 2.5 FTP、FTPS 与 SFTP：名字相似，协议族不同

FTP 基于 TCP，并把控制与数据分开：控制连接通常连服务器 21 端口，数据连接则根据模式另行建立。

- **主动模式：** 服务器从自己的数据端主动连接客户端指定端口，容易受到客户端 NAT 或防火墙限制。
- **被动模式：** 客户端再连接服务器告知的数据端口，更适合常见 NAT/防火墙部署。
- **FTPS：** FTP 再使用 TLS，仍保留 FTP 的协议模型。
- **SFTP：** SSH File Transfer Protocol，运行在 SSH 通道上，通常只需一条 TCP 22 连接；它既不是 FTP，也不是“FTP 开启 TLS”。

传统 FTP 本身不加密控制命令、口令和文件内容，不能因为它使用 TCP 就认为传输安全。协议规范允许的模式不代表所有部署都会开放；服务器、防火墙和 NAT 必须共同配置数据端口范围，实际 FTP 可用性才成立。

#### 2.6 邮件协议：SMTP 管发送，POP3/IMAP 管邮箱访问

```text
发件客户端 ──SMTP 提交──→ 发件服务器
发件服务器 ──SMTP 中继──→ 收件服务器
收件客户端 ──POP3 或 IMAP──→ 访问收件服务器邮箱
```

- **SMTP** 是“推送”协议：25 常用于服务器间中继，587 常用于经过认证的邮件提交，465 常用于隐式 TLS 提交。三者的使用策略由服务商和部署配置决定。
- **POP3** 模型简单，侧重读取或下载邮箱内容；是否从服务器删除邮件由客户端行为决定，不能简单等同于“下载后必删”。
- **IMAP** 支持服务器端文件夹、标志、搜索和多设备状态同步，更适合让邮件长期保留在服务器。
- 110/143 是传统明文起始端口，协议可通过 STARTTLS 升级；995/993 是常见隐式 TLS 端口。是否允许明文认证属于部署安全策略，不是看到协议名就能断定。

#### 2.7 SSH 与 SFTP：一条安全连接中的多种通道

SSH 通常先通过 TCP 22 建立连接，再协商算法和密钥、认证服务器，随后认证用户并复用多个逻辑通道。它可承载交互式终端、远程命令、端口转发和 SFTP 子系统。

“SSH 已加密”不等于“服务器一定可信”：客户端仍需核对主机密钥或证书。首次连接盲目接受未知主机密钥会削弱对中间人攻击的防护；密码、公钥或其他用户认证方式则是另一个阶段。

#### 2.8 WebSocket：握手后是双向消息通道

经典 WebSocket 按 [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html) 在 TCP 上建立。客户端先发 HTTP/1.1 Upgrade 握手，服务器以 `101 Switching Protocols` 接受；成功后，同一连接改用 WebSocket 帧，双方都能随时发送文本、二进制和控制消息，不再是一问一答的普通 HTTP 消息流。

```text
HTTP Upgrade 握手 → WebSocket 数据帧 ↔ WebSocket 数据帧
```

`ws` 常借用 80，`wss` 常借用 TLS 保护的 443。现代规范也定义了在 HTTP/2、HTTP/3 上引导 WebSocket 的方式，所以“WebSocket 永远只能 HTTP/1.1 Upgrade”是对经典部署的简化，而不是完整协议边界。它适合聊天、协作、行情和游戏等双向实时场景；连接保活、断线重连和消息补偿仍需应用自行设计。

#### 2.9 MQTT：Broker 中转的发布—订阅协议

MQTT 客户端不直接按对方地址订阅消息，而是连接 Broker，并围绕层级主题发布或订阅：

```text
传感器 ──PUBLISH home/room1/temp──→ Broker ──分发──→ 订阅者
```

- QoS 0 表示至多一次，可能丢失。
- QoS 1 表示至少一次，接收方必须容忍重复。
- QoS 2 在 MQTT 协议交换范围内实现恰好一次交付，但不自动保证业务数据库事务只执行一次。

[MQTT 5.0 规范](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html) 要求底层提供有序、无损、双向字节流，但不强制唯一的具体传输协议；TCP、TLS 和 WebSocket 都可满足常见部署。1883 与 8883 分别是常见非 TLS 和 TLS 端口。MQTT 运行在 WebSocket 上时，外层端口还可能是 80/443，因此也不能只看端口识别 MQTT。

#### 2.10 怎样判断应用协议应使用哪种承载

协议设计不会单纯按“TCP 可靠、UDP 不可靠”二选一，还要综合：

- 是否需要有序字节流，还是需要保留独立报文边界。
- 丢包时应重传还是宁愿丢弃旧数据以降低时延。
- 是否需要多路复用、拥塞控制、连接迁移和加密。
- 是否必须穿过浏览器、代理、NAT 或企业防火墙。
- 应用层能否自行实现请求编号、重试、去重和超时。

标准定义可互操作的报文与行为；监听端口、是否开放明文、认证方式、超时、缓存和代理拓扑属于部署选择。回答面试题时应先说规范边界，再说明“常见部署通常怎样做”。

### 3. 传输层为什么是应用层与 IP 层的桥梁？

IP 地址把数据送到一个网络接口所在的主机，但同一台主机可能同时运行浏览器、DNS 客户端、Web 服务器和邮件服务器。TCP、UDP 的端口用于复用与分用，让操作系统把收到的数据交给相应套接字。

通信流常用以下信息区分：

```text
传输协议 + 源 IP + 源端口 + 目的 IP + 目的端口
```

例如客户端访问 `203.0.113.20:443`：

- 目的 IP 帮助网络把数据报送向服务器。
- 目的端口帮助服务器把传输数据交给 HTTPS 服务。
- 源 IP 和临时源端口帮助响应回到正确客户端套接字。
- IPv4 首部的 `Protocol` 字段、IPv6 的 `Next Header` 字段指出后续是 TCP、UDP、ICMP 或其他协议。

TCP 提供可靠、有序的字节流；UDP 提供轻量的无连接数据报，不保证可靠和有序；QUIC 在 UDP 之上由用户空间协议实现连接、可靠流、拥塞控制和加密。不能因为 QUIC 使用 UDP，就断言 HTTP/3 的应用数据“不可靠”。

### 4. IP 是无连接、尽力而为的数据报服务

发送主机把上层数据封装成 IP 数据报，每个数据报原则上独立处理。IP 的核心职责是：

- 用 IP 地址标识源和目的端点。
- 让异构链路组成一个可路由的互联网。
- 由主机和路由器依据转发表逐跳选择出口与下一跳。
- 用 TTL 或 Hop Limit 防止数据报在路由环路中无限转发。
- 用协议标识把负载交给正确的上层协议。

IP 本身不保证：

- 数据报一定到达。
- 多个数据报按发送顺序到达。
- 数据报只到达一次。
- 丢失后自动重传。
- 维护 TCP 那样的端到端连接状态。

“尽力而为”也不等于网络完全不检查错误。IPv4 有首部校验和，许多链路有帧校验，TCP/UDP/QUIC 也各有校验或认证机制；这些机制各自覆盖不同范围，不能推导出 IP 已提供可靠传输。

### 5. IPv4 首部必须认识哪些字段？

| 字段 | 作用 |
| --- | --- |
| Version | 标识 IPv4 |
| IHL | IPv4 首部长度 |
| DSCP/ECN | 服务分类与显式拥塞通知相关信息 |
| Total Length | 整个 IPv4 数据报的字节数 |
| Identification、Flags、Fragment Offset | 标识和定位 IPv4 分片；`DF` 表示不可分片，`MF` 表示后续还有分片 |
| TTL | 每次路由转发至少递减；归零则丢弃，通常产生 ICMP Time Exceeded |
| Protocol | 标识 TCP、UDP、ICMP 等上层协议 |
| Header Checksum | 只校验 IPv4 首部；TTL 改变后路由器需相应更新 |
| Source Address、Destination Address | 源和最终目的 IPv4 地址 |
| Options | 可选首部信息，导致首部长度可变 |

IPv6 基本首部结构不同：没有 IPv4 的首部校验和与基本首部分片字段，把选项和分片等放入扩展首部；TTL 对应的字段明确称为 Hop Limit。不要把 IPv4 字段表原样套到 IPv6。

### 6. CIDR、子网与最长前缀匹配

CIDR 用“地址/前缀长度”描述网络：

```text
192.0.2.130/24
```

`/24` 表示前 24 位是网络前缀，对应网络 `192.0.2.0/24`。主机用本接口前缀判断目的地址是否在链路上：

- 同一链路：下一跳就是目的主机。
- 不同链路：下一跳通常是默认网关。

路由器可能同时有这些路由：

```text
10.0.0.0/8       → 下一跳 A
10.20.0.0/16     → 下一跳 B
10.20.30.0/24    → 下一跳 C
0.0.0.0/0        → 默认下一跳 D
```

目的地址 `10.20.30.40` 同时匹配前三项，但路由器选择前缀最长、最具体的 `/24`。只有没有更具体匹配时才使用 `0.0.0.0/0` 默认路由。

传统 A、B、C 类地址划分已经被 CIDR 和可变前缀长度取代。它可以作为历史背景，但现代子网计算和路由转发应以网络前缀与最长匹配为主。

### 7. 一次 IPv4 逐跳转发怎样发生？

发送端和每台路由器大致执行：

1. 读取目的 IP 地址。
2. 在转发表中选择最具体的匹配项，得到出口接口和下一跳。
3. 若下一跳位于以太网等需要链路层地址的本地链路，查询邻居缓存；缺少映射时用 ARP 解析下一跳 IPv4 地址。
4. 把 IP 数据报封装进该链路的新帧并发送。
5. 路由器收到帧后移除旧链路层封装，检查并处理 IP 首部。
6. 路由器递减 TTL；若仍可转发，则重新查表并为下一条链路构造新帧。
7. 最后一跳的目的主机解封装，并依据 Protocol 字段交给 TCP、UDP 或 ICMP。

“路由”和“转发”也应区分：

- 路由控制过程通过静态配置、OSPF、BGP 等信息建立和更新路由。
- 转发数据面针对每个数据报查询最终转发表并执行下一跳动作。

主机通常也有自己的路由表；不是只有路由器才做“本地还是网关”的选择。

### 8. 端到端 IP 与逐跳 MAC 怎样变化？

假设主机 A 经路由器 R1、R2 访问主机 B：

| 链路 | 帧源地址 | 帧目的地址 | IP 源地址 | IP 目的地址 |
| --- | --- | --- | --- | --- |
| A → R1 | A 的链路层地址 | R1 入口地址 | A 的 IP | B 的 IP |
| R1 → R2 | R1 出口地址 | R2 入口地址 | A 的 IP | B 的 IP |
| R2 → B | R2 出口地址 | B 的链路层地址 | A 的 IP | B 的 IP |

在没有 NAT、代理、隧道等额外机制时，端到端源/目的 IP 通常保持不变；旧帧在每一跳结束，新帧的链路层源/目的地址随下一跳改变。因此：

- 发送到外网时，源主机解析的是默认网关的链路层地址，而不是远端网站的 MAC 地址。
- MAC 地址通常只在当前链路内有意义，路由器不会把原以太网首部一路转发到互联网终点。
- IP 并不要求底层必须是以太网；某些链路没有以太网式 MAC 地址，此表描述的是常见以太网路径。

### 9. ARP、IPv6 NDP 与 ICMP 各负责什么？

#### ARP：找当前 IPv4 下一跳的链路层地址

ARP 在支持它的本地链路上完成：

```text
下一跳 IPv4 地址 → 对应链路层地址
```

目标在同一子网时解析目标主机；目标在其他网络时解析默认网关。ARP 请求通常在本链路广播，响应提供映射并可被缓存。它不查询远端路径，也不把任意互联网 IPv4 地址解析为远端 MAC。

IPv6 不使用 ARP。IPv6 Neighbor Discovery 通过 ICMPv6 的 Neighbor Solicitation、Neighbor Advertisement 等消息完成邻居地址解析、可达性检测和路由器发现。

#### ICMP：报告控制信息和辅助诊断

ICMP/ICMPv6 用于报告或携带：

- 目的不可达。
- TTL/Hop Limit 超时。
- IPv4 需要分片但 DF 已置位，或 IPv6 Packet Too Big。
- 参数问题。
- Echo Request/Reply，即常见 `ping`。

`traceroute` 利用逐步增加 TTL/Hop Limit 并观察中间路由器的超时报文来推断路径。ICMP 可能被设备限速或过滤，所以“没有 ICMP 响应”不必然等于目标完全不可达；反过来，ICMP 能报告问题也不代表 IP 获得了自动重传和可靠交付。

### 10. MTU、IPv4 分片与路径 MTU

MTU 是某条链路一次能够承载的网络层数据包大小上限。路径 MTU（PMTU）是整条路径所有链路 MTU 的最小值。

- IPv4 数据报超过下一链路 MTU 时，中间路由器在允许分片的条件下可以分片；目的主机负责重组。设置 DF 后不能分片，路由器应丢弃并返回相应 ICMP 信息。
- IPv6 路由器不进行路径中的分片。发送源需要根据 PMTU 调整包大小；必要时由源使用 Fragment 扩展首部。
- 现代协议通常尽量避免 IP 分片，因为任一分片丢失会影响整个原始数据报，还会增加处理和过滤复杂度。
- 传输层把应用数据分成 TCP 段或 QUIC/UDP 数据，与 IP 因 MTU 产生的分片不是同一件事。

路径 MTU 发现依赖 ICMP “需要分片”或 ICMPv6 Packet Too Big 等反馈。粗暴屏蔽全部 ICMP 可能形成 PMTU 黑洞：小握手包可通过，大数据包却持续失败。

### 11. NAT、NAPT/PAT 改变了什么？

基本 NAT 只转换 IP 地址；家庭和办公网络中更常见的是 NAPT/PAT，同时转换地址和 TCP/UDP 端口：

```text
192.168.1.10:51000  →  203.0.113.5:62001
192.168.1.20:51000  →  203.0.113.5:62002
```

NAT 设备维护映射状态，出站时修改源地址/端口和相关校验信息，回包时反向转换目的地址/端口。它让多个私网主机共享公网地址，但也改变了原始端到端地址可见性；外部主动建立连接通常需要静态映射、端口转发或其他穿越机制。

NAT 与防火墙不是同一个概念。状态映射可能顺带阻止未匹配的入站流量，但安全策略应由明确的防火墙规则表达，不能把“用了 NAT”当作完整安全保证。

### 12. 从输入网址到看到网页的完整过程

以首次访问 `https://www.example.com/` 为例，常见路径是：

1. **取得网络配置：** 若主机尚无配置，可通过 DHCP 获得地址、前缀、默认网关和 DNS 服务器；也可能由静态配置或 IPv6 自动配置完成。
2. **解析名称：** 浏览器或系统检查相关缓存并请求 DNS 解析器，获得目标的 IPv4/IPv6 地址；实际结果可能指向 CDN、代理或负载均衡入口。
3. **选择路由和第一跳：** 主机查路由表，判断目的是否在本地链路；对外网通常选择默认网关，再用 ARP 或 IPv6 NDP 获得第一跳链路层地址。
4. **建立安全传输：** HTTP/1.1、HTTP/2 常建立 TCP 后进行 TLS 握手；HTTP/3 建立基于 UDP 的 QUIC 连接并完成集成的 TLS 握手。HTTPS 常用目的端口 443。
5. **发送应用请求：** 浏览器构造 HTTP 请求。传输协议增加端口和自身控制信息，IP 增加端到端地址，链路层为当前一跳增加帧首尾。
6. **逐跳送达：** 各路由器移除旧帧、递减 TTL/Hop Limit、最长前缀匹配、解析下一跳并重新封装。若经过 NAT，地址和端口可能被转换。
7. **服务器解封装：** 服务器按链路层 → IP → TCP/UDP/QUIC → TLS/HTTP 的方向处理，将请求交给 Web 服务，并按相反方向发送响应。
8. **浏览器处理响应：** 浏览器验证安全连接、解释状态码和字段、解码内容、渲染页面，并继续解析和请求脚本、样式、图片等子资源。

这个流程中的缓存、代理、CDN、负载均衡、连接复用和协议协商属于常见部署细节，不改变“应用语义 → 传输端口 → IP 路由 → 当前链路逐跳发送”的基本主线。

### 13. 对常见简化说法的纠正

| 简化或过时说法 | 更准确的结论 |
| --- | --- |
| IP 负责连接建立、保持和终止 | 普通 IP 是无连接数据报服务；连接状态由 TCP、QUIC、应用或其他上层协议维护 |
| DNS 就是 UDP 53 | DNS 同时使用 UDP 与 TCP；完整实现必须支持 TCP，也存在 DoT/DoH 等其他承载 |
| HTTP 一定使用 TCP | HTTP/1.1、HTTP/2 常基于 TCP；HTTP/3 基于 QUIC/UDP |
| IPv4 地址主要按 A/B/C 类划分 | 分类地址是历史模型；现代路由和子网以 CIDR 前缀为主 |
| RARP 是当前主机自动配置方案 | RARP 已陈旧，BOOTP/DHCP 等机制提供了更完整的配置能力 |
| ARP 属于某一层就能解释全部网络 | ARP 只解析本地 IPv4 下一跳，位于 IPv4 与链路边界；IPv6 使用 NDP |
| NAT 只替换 IP 地址 | 基本 NAT 可以只换地址，但常见 NAPT/PAT 还会转换 TCP/UDP 端口 |
| 数据链路层和物理层天然可靠 | 不同链路能力不同；以太网通常检错后丢弃坏帧，Wi-Fi 可有链路重试，但都不能据此保证端到端交付 |
| 每一跳都沿用原 MAC 地址 | 每条链路构造新的帧；端到端 IP 通常不变，逐跳链路层地址会变 |
| UDP 不可靠，所以 QUIC 也不可靠 | QUIC 以 UDP 为底座，但自行提供可靠流、拥塞控制、连接与安全机制 |

标准规定协议字段、语义和互操作行为；缓存大小、路由表内部数据结构、网卡卸载、NAT 表实现、具体是否使用以太网等属于实现或部署选择。学习时要先掌握标准边界，再观察常见实现。
