- [ ] `EX-01` **错误、异常和程序缺陷的区别** `【工程概念】`
  - **语法边界**：无独立语法；分类后分别落到返回值或错误码、`throw`/`catch`、`assert(condition)` 或终止接口。
  - **定义与目的**：错误是任务未能按预期完成的统称；异常是 C++ 提供的一种非局部错误报告机制；程序缺陷是代码违反自身应满足的规则。先分类，才能决定重试、返回错误、抛异常、断言还是终止。
  - **机制**：文件不存在、网络超时等运行时失败可能可恢复；内存耗尽可能只能降级或终止；调用者传入非法下标属于前置条件违反；把加法写成减法属于逻辑缺陷。`assert` 适合检查“不应发生”的开发期条件，不适合作为用户输入校验。
  - **最小例子**：配置文件缺失可以返回错误或抛 `std::runtime_error`；内部树结构断裂可用 `assert(node != nullptr)` 暴露缺陷。
  - **常见失败/边界**：不要把所有错误都包装成异常，也不要忽略返回值；异常是否适合取决于接口契约、恢复位置、性能和 ABI 边界，而不是“异常一定高级”。
  - **依赖**：`BASE-01`、`BASE-03`。

- [ ] `EX-02` **`throw`、`try`、`catch` 的基本语法** `【C++11·语言】`
  - **语法/接口格式**：`try { statements } catch (const ExceptionType& e) { handler } catch (...) { fallback }`；抛出写 `throw expression;`。
  - **定义与目的**：`throw` 报告无法在当前位置完成的操作，`try` 标记受监控语句块，`catch` 在调用链上的合适位置处理特定异常。
  - **语义**：执行 `throw expression;` 后，当前正常控制流停止；运行时寻找第一个匹配的处理器，找到后进入相应 `catch`，处理完再执行整个 try 语句之后的代码。
  - **最小例子**：`try { if (n < 0) throw std::invalid_argument("n"); } catch (const std::invalid_argument& e) { std::cerr << e.what(); }`，需包含 `<stdexcept>` 和 `<iostream>`。
  - **常见失败/边界**：`try` 必须紧接一个或多个 `catch`；抛出后不会自动从原位置继续；始终找不到处理器时调用 `std::terminate`。
  - **依赖**：`BASE-03`。

- [ ] `EX-03` **异常对象如何产生** `【C++11·语言】`
  - **语法/接口格式**：`throw expression;` 用表达式初始化独立异常对象；无操作数的 `throw;` 只用于重新抛出当前正在处理的异常。
  - **定义与目的**：`throw expression` 会根据表达式初始化一个独立的异常对象，使异常即使离开抛出点的局部作用域仍然可被捕获。
  - **语义**：初始化异常对象时会去掉顶层引用和顶层 `const`；对象的存储由实现管理，在最后一个处理器结束或相关 `exception_ptr` 被销毁后才可释放。
  - **最小例子**：`std::runtime_error e("bad"); throw e;` 抛出的不是对局部变量 `e` 的悬空引用，而是由它初始化的异常对象。
  - **常见失败/边界**：初始化异常对象本身若再次失败可能导致终止；不要抛指向局部缓冲区的裸指针，因为复制的是指针值而不是其指向内容。
  - **依赖**：`BASE-05`、`BASE-06`。

- [ ] `EX-04` **异常处理器匹配规则** `【C++11·语言】`
  - **语法/接口格式**：处理器依次写为 `catch (const Derived& e) { ... }`、`catch (const Base& e) { ... }`、`catch (...) { ... }`；更具体的类型应放在更一般的类型之前。
  - **定义与目的**：处理器按源码顺序检查，选择第一个能匹配异常对象类型的 `catch`，因此排列顺序会影响行为。
  - **语义**：可进行同类型匹配、派生类到无歧义公共基类的匹配、数组/函数到指针以及少量指针限定转换；不会为了匹配随意调用用户定义转换，也不会做普通数值转换。`catch (...)` 匹配任何异常。
  - **最小例子**：应先写 `catch (const std::out_of_range&)`，再写 `catch (const std::exception&)`，最后才写 `catch (...)`。
  - **常见失败/边界**：基类处理器放在派生类处理器前会遮蔽后者；`throw 1;` 不会被 `catch(double)` 捕获；指针异常与对象异常是不同类型。
  - **依赖**：`EX-02`、继承与多态。

- [ ] `EX-05` **按 `const` 引用捕获异常** `【C++11·语言】`
  - **语法/接口格式**：惯用处理器参数格式是 `catch (const T& e) { use(e); }`；按值形式是 `catch (T e)`，通常不用于多态异常。
  - **定义与目的**：惯用形式 `catch (const T& e)` 直接观察异常对象，避免额外复制，并保留派生对象的动态类型。
  - **语义**：按值 `catch (T e)` 会复制一个处理器参数；若 `T` 是基类，还会把派生部分切掉。按非常量引用捕获虽然可行，但通常没有修改异常对象的需要。
  - **最小例子**：`catch (const std::exception& e) { std::cerr << e.what(); }` 可统一处理许多标准派生异常。
  - **常见失败/边界**：`const` 引用避免的是处理器参数切片，不会改变处理器匹配顺序；捕获裸指针时写引用也不能自动管理指针所指资源。
  - **依赖**：`BASE-04`、继承与多态、`EX-04`。

- [ ] `EX-06` **异常传播与栈展开** `【C++11·语言】`
  - **语法/接口格式**：没有单独的“栈展开”关键字；在作用域内先构造 RAII 对象再调用可能抛出的函数，例如 `{ Guard guard(resource); risky(); }`，异常传播时自动执行 `guard` 的析构函数。
  - **定义与目的**：抛出点所在函数没有匹配处理器时，异常沿动态调用链向外传播；退出各作用域时执行栈展开以清理已经构造完成的自动对象。
  - **语义**：局部对象按构造逆序析构；数组中已经构造的元素也按逆序清理；尚未构造完成的最外层对象本身不析构，但其已完成的基类和成员会被销毁。
  - **最小例子**：`std::lock_guard<std::mutex> lock(m); risky();` 中 `risky()` 抛出时，`lock` 的析构函数仍解锁互斥量。
  - **常见失败/边界**：原始 `new`、文件描述符或手工 `lock()` 不会因栈展开自动释放；`longjmp` 等非 C++ 控制转移也不等价于异常展开。
  - **依赖**：`BASE-03`、`BASE-05`、`EX-02`。

- [ ] `EX-07` **RAII 为什么能防止异常泄漏资源** `【C++11·语言/工程概念】`
  - **语法/接口格式**：资源包装类通常写成 `class Guard { public: explicit Guard(Resource); ~Guard() noexcept; Guard(const Guard&) = delete; Guard& operator=(const Guard&) = delete; };`，使用时声明自动对象 `Guard guard(resource);`。
  - **定义与目的**：RAII 把资源所有权放入对象，让构造函数获得资源、析构函数无条件释放资源，从而让正常返回和异常路径共享同一套清理逻辑。
  - **机制**：自动对象在栈展开中仍会析构，因此 `unique_ptr`、文件包装器和锁守卫都能在任意退出路径释放其资源。
  - **最小例子**：`std::unique_ptr<int> p(new int(7)); may_throw();` 即使 `may_throw()` 抛出，`p` 也会执行 `delete`。
  - **常见失败/边界**：RAII 类的析构必须可靠且通常不得抛异常；`release()` 后资源已脱离管理，责任重新交给调用者。
  - **依赖**：`BASE-09`、`EX-06`。

- [ ] `EX-08` **重新抛出异常** `【C++11·语言】`
  - **语法/接口格式**：`catch (...) { log(); throw; }` 重新抛出当前异常；`throw e;` 是按表达式重新创建异常对象，二者不能混同。
  - **定义与目的**：处理器可记录局部信息后继续把同一异常交给更外层处理，正确语法是在活动处理器中单独写 `throw;`。
  - **语义**：`throw;` 重新激活当前异常对象并保留其动态类型；`throw e;` 根据表达式 `e` 初始化新的异常对象，若 `e` 的静态类型是基类就可能切片。
  - **最小例子**：`catch (const std::exception& e) { log(e.what()); throw; }`。
  - **常见失败/边界**：在没有正在处理的异常时执行裸 `throw;` 会调用 `std::terminate`；为了“继续传播”不要写 `throw e;`。
  - **依赖**：`EX-04`、`EX-05`。

- [ ] `EX-09` **标准异常类型体系** `【C++11·标准库】`
  - **语法/接口格式**：包含 `<stdexcept>` 后可写 `throw std::runtime_error("message");`；通用处理器常写 `catch (const std::exception& e) { e.what(); }`，并包含 `<exception>`。
  - **定义与目的**：`<exception>` 中的 `std::exception` 是常用异常基类并提供虚函数 `what()`；`<stdexcept>` 提供按错误性质分类的常用派生类型。
  - **体系**：`logic_error` 表示可由程序逻辑预先避免的错误，其下有 `invalid_argument`、`domain_error`、`length_error`、`out_of_range`；`runtime_error` 表示运行环境相关失败。`bad_alloc` 来自 `<new>`。
  - **最小例子**：容器边界检查 `v.at(i)` 失败抛 `std::out_of_range`；普通 `new` 分配失败通常抛 `std::bad_alloc`。
  - **常见失败/边界**：标准类型名称不自动决定接口契约；若自定义异常，通常公开继承 `std::exception` 并确保 `what()` 不抛异常。
  - **依赖**：继承与虚函数、`EX-04`。

- [ ] `EX-10` **构造函数失败与函数 try 块** `【C++11·语言】`
  - **语法/接口格式**：构造函数函数 try 块格式为 `C::C(Args args) try : member_(init) { body } catch (...) { handler }`，其 `try` 同时覆盖成员初始化列表和构造函数体。
  - **定义与目的**：构造函数没有可用于报告失败的返回值；无法建立类不变量时应抛异常，使调用者不会得到一个“半有效对象”。
  - **语义**：构造失败时，已构造的基类和成员会自动析构，但最外层对象的析构函数不会运行。函数 try 块可包围构造函数的初始化列表和函数体：`C::C() try : member(make()) {} catch (...) { ... }`。
  - **最小例子**：`File::File(const char* p) { if (!open(p)) throw std::runtime_error("open"); }`，更好的实现是让成员自身采用 RAII。
  - **常见失败/边界**：构造函数函数 try 块的处理器结束时若没有显式抛出，构造函数异常仍会自动重新抛出；不要在处理器里依赖已经析构的成员。
  - **依赖**：`BASE-05`、`EX-06`。

- [ ] `EX-11` **析构函数与异常** `【C++11·语言】`
  - **语法/接口格式**：析构函数通常声明为 `~T() noexcept { cleanup_without_throwing(); }`；需要向调用者报告清理失败时，另设显式接口如 `void close();`。
  - **定义与目的**：析构承担清理职责，必须能在正常退出和异常展开期间可靠执行；通常应设计为不让异常逃出。
  - **语义**：若栈展开期间另一个析构异常逃出，会有两个同时传播的异常，C++ 调用 `std::terminate`。C++11 中隐式声明的析构函数通常具有条件式不抛异常说明。
  - **最小例子**：析构中调用可能失败的 `close()` 时，可记录错误；若关闭失败必须反馈，提供显式 `close()` 让用户在析构前调用并处理结果。
  - **常见失败/边界**：简单写 `catch (...) {}` 会吞掉重要错误；应明确记录、终止或通过显式操作报告，而不是让析构承担所有错误通信。
  - **依赖**：`BASE-05`、`EX-06`。

- [ ] `EX-12` **`noexcept` 与 `noexcept(expression)`** `【C++11·新增】`
  - **语法/接口格式**：函数承诺写 `Return f(Args...) noexcept;` 或 `noexcept(condition)`；查询表达式写 `bool b = noexcept(expression);`，查询不会执行该表达式。
  - **定义与目的**：异常说明 `noexcept` 表示函数承诺异常不会逃出；条件式 `noexcept(condition)` 允许按编译期布尔条件决定承诺。
  - **语义**：异常逃出 `noexcept` 函数时调用 `std::terminate`，并不保证实现一定先完成完整栈展开。运算符 `noexcept(expr)` 不执行 `expr`，只产生编译期 `bool`。
  - **最小例子**：`void swap(X& a, X& b) noexcept(noexcept(a.swap(b))) { a.swap(b); }`；可用 `static_assert(noexcept(f()), "f may throw");` 检查。
  - **常见失败/边界**：`noexcept` 不是“忽略异常”，也不是自动优化开关；承诺必须与实际调用链一致。旧式动态异常说明 `throw()` 与现代写法语义细节不同，不应混用概念。
  - **依赖**：`BASE-03`、`EX-06`。

- [ ] `EX-13` **`noexcept` 与移动操作的关系** `【C++11·新增】`
  - **语法/接口格式**：移动构造常声明为 `T(T&& other) noexcept;`；泛型转移可包含 `<utility>` 后写 `T next(std::move_if_noexcept(old));`。
  - **定义与目的**：容器扩容时需要把旧元素转移到新存储；若移动可能抛出而拷贝可用，选择拷贝更容易维持强异常保证。
  - **机制**：`std::move_if_noexcept(x)` 在类型具有不抛移动构造或不可拷贝时产生右值引用，否则产生 `const T&`，使泛型代码可选择较安全的路径。
  - **最小例子**：资源所有类的移动构造通常写成 `X(X&& other) noexcept`，前提是成员转移确实不会抛异常。
  - **常见失败/边界**：给实际可能抛出的移动操作强行标 `noexcept` 会把可处理异常变成终止；标准容器的具体选择还受类型特征和操作要求约束。
  - **依赖**：`BASE-06`、`EX-12`、标准容器。

- [ ] `EX-14` **异常安全保证** `【工程概念】`
  - **语法边界**：无独立语法；通常用“临时对象完成可能失败的工作，再以不抛的 `swap` 或提交操作生效”，并用 `noexcept` 标明真正的不抛边界。
  - **定义与目的**：异常安全描述操作失败后的状态：无泄漏保证资源不丢失；基本保证保持不变量但值可改变；强保证表现得像操作从未发生；不抛保证表示操作一定不抛。
  - **机制**：“先准备、后提交”让所有可能失败的工作在临时对象上完成，最后用不抛操作提交；copy-and-swap 是典型形式。
  - **最小例子**：先构造 `std::vector<T> temp(new_data)`，全部成功后 `data.swap(temp)`，异常发生时原 `data` 不变。
  - **常见失败/边界**：强保证不是所有操作都值得或能够提供；回调、I/O 和外部系统副作用通常无法简单回滚。文档必须说明承诺级别。
  - **依赖**：`BASE-06`、`BASE-09`、`EX-07`。

- [ ] `EX-15` **`std::error_code` 与 `std::system_error`** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<system_error>`；错误值可写 `std::error_code ec = std::make_error_code(std::errc::permission_denied);`，异常形式可写 `throw std::system_error(ec, "operation");`。
  - **定义与目的**：`std::error_code` 是由数值和 `error_category` 组成的非抛出错误值；`std::error_condition` 表示可移植条件；`std::system_error` 把错误码和文本包装成异常。
  - **机制**：系统或库接口可写入 `error_code&` 以让调用者显式检查，也可在失败时抛 `system_error`；`std::errc` 提供一组通用条件枚举。
  - **最小例子**：`std::error_code ec = std::make_error_code(std::errc::permission_denied); if (ec) std::cerr << ec.message();`，需 `<system_error>`。
  - **常见失败/边界**：数值只有结合所属 category 才有意义；不要只比较 `value()`；错误码路径若被忽略会静默失败，异常路径则要保证边界处理。
  - **依赖**：类、枚举、`EX-09`。

- [ ] `EX-16` **跨线程保存和重新抛出异常** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<exception>`；保存写 `std::exception_ptr ep; try { work(); } catch (...) { ep = std::current_exception(); }`，恢复传播写 `if (ep) std::rethrow_exception(ep);`。
  - **定义与目的**：异常不会自动离开线程入口传播到创建线程，`std::exception_ptr` 用于保存当前异常并在另一个控制流中重新抛出。
  - **机制**：在线程内部 `catch (...) { ep = std::current_exception(); }`，同步并 `join` 后由接收线程执行 `if (ep) std::rethrow_exception(ep);`；`future`/`promise` 也会通过共享状态传递异常。
  - **最小例子**：子线程捕获并写入仅由该线程写、主线程在 `join()` 后读的 `exception_ptr`，此时 `join` 提供完成同步。
  - **常见失败/边界**：让异常直接逃出线程函数会终止进程；多个线程读写同一 `exception_ptr` 变量仍需同步；空 `exception_ptr` 不能传给 `rethrow_exception`。
  - **依赖**：`EX-06`、`TH-01`～`TH-06`。

- [ ] `EX-17` **嵌套异常** `【C++11·新增/标准库】`
  - **语法/接口格式**：在活动处理器中写 `std::throw_with_nested(HighLevelError("context"));`；捕获外层对象后写 `std::rethrow_if_nested(e);` 尝试重新抛出其内层异常。
  - **定义与目的**：嵌套异常在添加高层上下文时保留底层原始原因，避免只剩“加载配置失败”而丢失“权限不足”等根因。
  - **机制**：在活动处理器中调用 `std::throw_with_nested(HighLevel("load failed"))`；捕获高层异常后可用 `std::rethrow_if_nested(e)` 递归取得内层异常。
  - **最小例子**：底层 `open()` 抛出后，配置加载层捕获并 `throw_with_nested(std::runtime_error("config"))`。
  - **常见失败/边界**：递归打印时每层都要再次捕获；并非所有抛出对象都含嵌套异常；记录敏感底层信息时需考虑日志安全。
  - **依赖**：`EX-08`、`EX-09`。

- [ ] `EX-18` **异常与 C ABI 等接口边界** `【工程概念】`
  - **语法边界**：无独立语法；边界适配常写成 `extern "C" int api() noexcept { try { work(); return 0; } catch (...) { return -1; } }`，用状态码或调用者提供的缓冲区传递失败信息。
  - **定义与目的**：语言或二进制边界需要稳定、双方都理解的失败协议；C++ 异常布局和展开机制属于具体 ABI，不能假定任意 C、插件或不同工具链调用方都兼容。
  - **机制**：在导出入口内部捕获全部异常，转换为状态码、错误对象或调用者提供的缓冲区，并确保所有资源仍由创建它们的一侧正确释放。
  - **最小例子**：`extern "C" int api() { try { work(); return 0; } catch (...) { return -1; } }`；真实接口还应提供可查询的稳定错误信息。
  - **常见失败/边界**：`extern "C"` 主要指定语言链接，不自动统一类布局、标准库、异常、运行库和分配器；异常逃出真实 C 调用栈、线程入口或不兼容共享库是不可移植设计。
  - **依赖**：`EX-06`、`BUILD-12`。

# MEM：对象、存储与动态内存

- [ ] `MEM-01` **对象、地址、字节和存储的区别** `【C++11·语言】`
  - **语法/接口格式**：声明对象写 `T object{};`，取得地址写 `T* address = &object;`；只观察对象表示可写 `const unsigned char* bytes = reinterpret_cast<const unsigned char*>(address);`。
  - **定义与目的**：对象是具有类型和生存期的一块存储区域或子对象；地址用于定位存储位置；字节是 `sizeof` 使用的最小可寻址单位；存储只是容纳对象表示的空间。
  - **机制**：对象的值通过其类型解释，底层存储则是一串字节。一个完整对象还可能包含基类子对象、成员子对象和填充字节。
  - **最小例子**：`int x = 42; int* p = &x;` 中 `x` 是对象，`&x` 是地址，`sizeof x` 给出其对象表示占用的字节数，`p` 保存该地址。
  - **常见失败/边界**：地址相同不代表类型、对象身份或指针算术含义相同；有一块足够大的字节缓冲区，也不等于其中已经存在任意 `T` 对象。
  - **依赖**：`BASE-01`。

- [ ] `MEM-02` **作用域、链接和存储期不是同一概念** `【C++11·语言】`
  - **语法/接口格式**：作用域由声明位置和 `{ ... }` 等结构决定；链接常见形式有 `extern int external_name;` 与命名空间作用域的 `static int internal_name;`；存储期通过声明位置、`static`、`thread_local` 或动态分配形成。
  - **定义与目的**：作用域决定名字在源码哪里可见；链接决定不同声明是否指向跨作用域或跨翻译单元的同一实体；存储期决定对象的存储存在多久。
  - **机制**：三者分别描述“能否写出这个名字”“多个名字是否代表同一实体”“对象何时获得和释放存储”，必须独立判断。
  - **最小例子**：函数内 `static int count;` 的名字具有块作用域和无链接，但对象具有静态存储期；命名空间作用域 `extern int x;` 可声明具有外部链接的对象。
  - **常见失败/边界**：`static` 在不同位置会影响存储期、链接或类成员性质，不能只记成“静态变量”；名字不可见也不代表对象已销毁。
  - **依赖**：`BASE-03`。

- [ ] `MEM-03` **四种存储期** `【C++11·语言】`
  - **语法/接口格式**：典型声明为 `{ T automatic; }`、`static T persistent;`、`thread_local T per_thread;` 和 `T* pointer = new T;`；最后一行中 `pointer` 本身通常是自动对象，其所指对象具有动态存储期。
  - **定义与目的**：自动、静态、线程和动态存储期描述对象所占存储的持续时间；C++11 新增 `thread_local` 对应线程存储期。
  - **机制**：普通块内局部对象和形参通常是自动存储期；命名空间对象与局部 `static` 是静态存储期；`thread_local` 每线程一份；`new` 表达式取得的存储具有动态存储期。
  - **最小例子**：`int g; thread_local int t; void f(){ int a; static int s; int* p = new int; delete p; }` 分别展示四种存储期，其中指针变量 `p` 自身仍是自动存储期。
  - **常见失败/边界**：存储期不等于作用域，也不完全等于对象生存期；动态存储不会因指针变量离开作用域自动释放。
  - **依赖**：`MEM-02`。

- [ ] `MEM-04` **“栈”和“堆”是实现模型，不是完整标准术语** `【工程概念】`
  - **语法边界**：无独立语法；标准层面应讨论自动对象、静态对象、线程局部对象以及 `new`/`delete` 或分配器管理的动态对象，具体是否放在机器栈或某种堆中由实现决定。
  - **定义与目的**：栈和堆是常见运行时实现区域，便于理解性能和系统限制；ISO C++ 主要规定对象语义，不强制具体内存布局。
  - **机制**：实现通常用每线程调用栈保存调用帧和自动对象，用进程堆或专用分配器满足动态分配；优化器还可能把对象放入寄存器或完全消除。
  - **最小例子**：递归过深常耗尽线程栈；大量 `new` 通常经过动态分配器，但这两种现象属于实现和操作系统行为。
  - **常见失败/边界**：不要从“局部变量”推导其可观察地址一定在某个栈区，也不要把所有动态分配都假定成一次操作系统调用。
  - **依赖**：`MEM-03`。

- [ ] `MEM-05` **初始化与未初始化对象** `【C++11·语言】`
  - **语法/接口格式**：常见形式有默认初始化 `T a;`、值初始化 `T b{};`、直接初始化 `T c(args);` 和列表初始化 `T d{args};`；不同形式的零初始化与构造行为必须按 `T` 的类别判断。
  - **定义与目的**：初始化在对象生存期开始时建立初始状态；默认初始化、值初始化、零初始化、直接初始化和列表初始化会按类型及语法触发不同规则。
  - **机制**：`int a;` 在自动存储期下默认初始化后值不确定；`int b{};` 值初始化为零；静态/线程存储期对象在其他初始化前先零初始化；`int c(3);` 是直接初始化；`int d{3};` 是列表初始化并禁止窄化。
  - **最小例子**：`new int` 得到未确定初值的 `int`，`new int()` 或 `new int{}` 得到零；类类型则由选中的构造函数建立状态。
  - **常见失败/边界**：读取未初始化自动标量会产生未定义行为；“分配到的内存碰巧为零”不构成语言保证；列表初始化的 `initializer_list` 重载选择还可能与普通构造不同。
  - **依赖**：基本类型、构造函数。

- [ ] `MEM-06` **对象生存期开始和结束** `【C++11·语言】`
  - **语法/接口格式**：普通对象由 `T object(args);` 开始生存并在离开作用域时自动析构；手工存储管理可写 `T* p = new (address) T(args); p->~T();`，但必须包含 `<new>` 并保证地址、对齐和调用次数正确。
  - **定义与目的**：生存期决定何时可把某块存储当成特定对象使用；存储已经存在并不自动意味着该类型对象已经存在。
  - **机制**：对象获得适当对齐和大小的存储并完成所需初始化后开始生存期；类对象析构开始、伪析构调用或存储被释放/重用时结束生存期。
  - **最小例子**：先用 `operator new(sizeof(T))` 取得存储，再以放置 new `new (raw) T(args)` 建立 `T`；使用完调用 `p->~T()`，最后释放原始存储。
  - **常见失败/边界**：对尚未构造或已经析构的对象调用成员通常是未定义行为；引用和指针的生存期不延长所指对象，少数临时量引用延长规则除外。
  - **依赖**：`BASE-05`、`MEM-01`。

- [ ] `MEM-07` **空指针、悬空指针和野指针** `【C++11·语言】`
  - **语法/接口格式**：空指针初始化写 `T* p = nullptr;`，使用前可写 `if (p) { use(*p); }`；释放后可令观察指针 `p = nullptr;`，但语法本身无法找出其他仍悬空的别名或未初始化的野指针。
  - **定义与目的**：空指针明确不指向对象；悬空指针曾指向对象但其生存期已结束；“野指针”是工程俗称，通常指未初始化或含无效地址的指针。
  - **机制**：`nullptr` 可转换为任何对象或函数指针类型；`delete p` 后 `p` 的值不会自动变成 `nullptr`；数组只允许在元素范围和尾后一位内形成规定的指针运算。
  - **最小例子**：`int* p = nullptr; { int x; p = &x; }` 后 `p` 悬空；`int* q;` 未初始化时不能解引用或作为有效地址使用。
  - **常见失败/边界**：检查 `p != nullptr` 不能判断它是否悬空；尾后一位指针可用于比较和循环终点但不可解引用；把释放后的一个别名置空不会修复其他别名。
  - **依赖**：`BASE-04`、`MEM-06`。

- [ ] `MEM-08` **原始指针不自动表达所有权** `【工程概念】`
  - **语法边界**：无独立语法；`T*` 既可能是非拥有观察者也可能由约定承担释放责任，明确所有权时应优先使用 `std::unique_ptr<T>`、`std::shared_ptr<T>` 或容器，并在接口契约中说明借用和生存期。
  - **定义与目的**：`T*` 只表示能通过某个地址访问 `T`，类型本身不说明是借用、独占所有、共享所有、数组首地址还是可空观察者。
  - **机制**：所有权必须由接口契约、RAII 类型或明确命名表达；拥有动态对象优先用 `unique_ptr`/`shared_ptr`，短期非拥有访问可用引用或有文档的裸指针。
  - **最小例子**：`void inspect(const Widget*);` 可约定只借用且允许空；`std::unique_ptr<Widget> create();` 则明确把独占所有权交给调用者。
  - **常见失败/边界**：看到裸指针就 `delete` 可能重复释放或释放非动态对象；返回内部裸指针必须说明其有效期和使其失效的操作。
  - **依赖**：`BASE-04`。

- [ ] `MEM-09` **`new`、`delete`、`new[]`、`delete[]`** `【C++11·语言】`
  - **语法/接口格式**：单对象写 `T* p = new T(args); delete p;`；数组写 `T* a = new T[n](); delete[] a;`。分配形式必须与对应释放形式配对，且每个动态对象只释放一次。
  - **定义与目的**：`new` 表达式取得存储并构造对象，`delete` 表达式先析构再释放存储；数组形式对多个元素执行相应过程。
  - **机制**：`T* p = new T(args); delete p;` 与 `T* a = new T[n]; delete[] a;` 必须成对；若对象构造抛出，与该 new 表达式匹配的释放函数会回收已取得的存储。
  - **最小例子**：`std::string* p = new std::string("x"); delete p; p = nullptr;`；实际所有权代码优先直接使用自动对象或智能指针。
  - **常见失败/边界**：混用 `delete`/`delete[]`、重复删除、删除非 new 地址、通过不合适的静态类型删除都是未定义行为；删除多态基类指针要求基类具有合适的虚析构函数。
  - **依赖**：`BASE-04`、`BASE-05`、`MEM-06`。

- [ ] `MEM-10` **分配失败** `【C++11·标准库】`
  - **语法/接口格式**：普通 `new T` 失败通常抛 `std::bad_alloc`；包含 `<new>` 后可写 `T* p = new (std::nothrow) T; if (!p) { handle_failure(); }` 选择返回空指针的形式。
  - **定义与目的**：动态分配可能因资源不足失败，程序必须选择异常路径、显式空指针路径或更高层降级策略。
  - **机制**：普通 `new T` 的分配函数失败通常抛 `std::bad_alloc`；`new (std::nothrow) T` 在分配失败时返回空指针；全局 new-handler 机制可在最终失败前尝试释放资源。
  - **最小例子**：`int* p = new (std::nothrow) int[huge]; if (!p) { /* 降级 */ }`，需 `<new>`。
  - **常见失败/边界**：`nothrow` 只改变分配失败的报告方式，构造函数主动抛出的异常仍可传播；在现代操作系统上“new 成功”也不代表未来物理内存访问绝不会失败，这是平台策略边界。
  - **依赖**：`MEM-09`、`EX-09`。

- [ ] `MEM-11` **`malloc`、`calloc`、`realloc`、`free` 在 C++ 中的边界** `【C++11·标准库】`
  - **语法/接口格式**：包含 `<cstdlib>`；基本形式为 `void* p = std::malloc(bytes); std::free(p);`、`std::calloc(count, size)` 和 `void* resized = std::realloc(p, new_bytes);`，返回的原始存储不会自动调用 C++ 构造或析构函数。
  - **定义与目的**：`<cstdlib>` 中的 C 分配函数管理未类型化原始存储，主要用于 C 接口、底层分配器或与既有 C 代码互操作。
  - **机制**：`malloc` 分配字节，`calloc` 额外把所有字节置零，`realloc` 可能原地调整或搬移字节块，`free` 释放；它们不会调用 C++ 构造函数或析构函数。
  - **最小例子**：`void* raw = std::malloc(sizeof(T)); T* p = new (raw) T(); p->~T(); std::free(raw);`，还必须先检查 `raw` 非空。
  - **常见失败/边界**：绝不能 `free(new T)` 或 `delete malloc(...)`；`realloc` 不适合搬移一般非平凡 C++ 对象；全字节零不保证等于所有类型的语义零值或有效对象状态。
  - **依赖**：`MEM-06`、`MEM-09`。

- [ ] `MEM-12` **放置 new 与显式析构** `【C++11·语言】`
  - **语法/接口格式**：包含 `<new>` 后可写 `void* raw = ::operator new(sizeof(T)); T* p = new (raw) T(args); p->~T(); ::operator delete(raw);`；构造、析构、释放的顺序和次数必须严格配对。
  - **定义与目的**：标准放置 new 在调用者提供的地址构造对象，不另行分配存储，用于容器、对象池和联合存储等底层实现。
  - **机制**：`T* p = new (buffer) T(args);` 需要 `<new>`；不再使用时调用 `p->~T();`，原始缓冲区的释放方式由缓冲区所有者决定。
  - **最小例子**：`alignas(T) unsigned char buf[sizeof(T)]; T* p = new (buf) T(); p->~T();`。
  - **常见失败/边界**：地址必须满足大小与对齐要求；同一存储不能同时当成两个生存期重叠的不相容对象；对放置 new 的结果写普通 `delete p` 通常错误，因为它没有独立动态分配。
  - **依赖**：`MEM-06`、`MEM-09`。

- [ ] `MEM-13` **RAII 所有权模型** `【C++11·工程核心】`
  - **语法/接口格式**：拥有资源的类通常把句柄作为成员，在构造函数中取得、在 `~Owner() noexcept` 中释放，并按策略声明 `Owner(const Owner&) = delete;`、移动构造/赋值或深拷贝操作。
  - **定义与目的**：RAII 让资源所有权跟随对象生存期，消除每条返回、异常和错误分支上的手工清理重复。
  - **机制**：构造函数建立有效资源状态，析构函数释放；不可共享资源通常禁止拷贝、允许移动，从类型层面表达唯一所有者。
  - **最小例子**：`std::lock_guard<std::mutex> guard(m);` 在作用域开始加锁并在任意退出路径解锁。
  - **常见失败/边界**：构造后再“晚一点交给 RAII”会留下泄漏窗口；析构函数必须可靠；资源释放错误若需反馈，应另设显式成员函数。
  - **依赖**：`BASE-05`、`BASE-09`。

- [ ] `MEM-14` **`std::unique_ptr` 独占所有权** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<memory>`；单对象写 `std::unique_ptr<T> p(new T(args));`，转移写 `std::unique_ptr<T> q = std::move(p);`，数组写 `std::unique_ptr<T[]> a(new T[n]);`，访问和释放控制使用 `*p`、`p->member`、`get()`、`reset()`、`release()`。
  - **定义与目的**：`unique_ptr<T,D>` 表示一个可空的独占资源所有者，不可拷贝、可移动，析构时通过删除器 `D` 释放资源。
  - **机制**：`get()` 只观察；`release()` 交出指针且不释放；`reset(q)` 先释放旧对象再接管 `q`；`unique_ptr<T[]>` 用 `delete[]` 并提供下标访问。
  - **最小例子**：`std::unique_ptr<Widget> p(new Widget); std::unique_ptr<Widget> q = std::move(p);` 后 `p` 为空、`q` 拥有对象。
  - **常见失败/边界**：对 `get()` 的结果再次创建所有者会双重释放；`release()` 后必须立刻交给另一个所有者；数组应使用 `unique_ptr<T[]>` 而不是错误的单对象形式。
  - **依赖**：`BASE-06`、`MEM-13`。

- [ ] `MEM-15` **C++11 没有 `std::make_unique`** `【版本边界】`
  - **语法/接口格式**：严格 C++11 直接初始化为 `std::unique_ptr<T> p(new T(args));`；`auto p = std::make_unique<T>(args);` 是 C++14 接口，除非项目自行提供并明确命名空间与实现，否则不能当作 C++11 标准库使用。
  - **定义与目的**：`std::make_unique` 从 C++14 才进入标准；严格 C++11 代码不能假定 `<memory>` 提供它。
  - **机制**：C++11 可先独立构造所有者：`std::unique_ptr<T> p(new T(args));`；项目也可提供经测试的 C++11 辅助模板，但数组、删除器和重载设计要明确。
  - **最小例子**：`std::unique_ptr<Widget> p(new Widget(1, 2)); use(std::move(p));`，把所有权建立成单独完整表达式更容易审计。
  - **常见失败/边界**：不要悄悄依赖编译器在 C++11 模式下提供的 C++14 扩展；自制简版 `make_unique` 不一定覆盖数组和所有构造情形。
  - **依赖**：`MEM-14`。

- [ ] `MEM-16` **`std::shared_ptr` 共享所有权** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<memory>`；可写 `std::shared_ptr<T> p(new T(args)); std::shared_ptr<T> q = p;`，访问用 `*p`/`p->member`/`get()`，放弃当前所有权用 `reset()`，诊断性计数查询用 `use_count()`。
  - **定义与目的**：`shared_ptr<T>` 让多个所有者共同保持托管对象存活，适合确实无法确定唯一所有者的共享生命周期。
  - **机制**：控制块通常保存强计数、弱计数、删除器和分配器；复制增加强计数，最后一个强所有者销毁时调用删除器，最后相关弱引用消失后控制块才释放。
  - **最小例子**：`std::shared_ptr<X> a(new X); std::shared_ptr<X> b = a;`，`a.use_count()` 可观察计数，但不能用它做并发正确性判断。
  - **常见失败/边界**：从同一裸指针分别构造两个 `shared_ptr` 会形成两个控制块并双重删除；共享所有权有计数和同步成本，且不自动让 `X` 的字段线程安全。
  - **依赖**：`BASE-06`、`MEM-13`。

- [ ] `MEM-17` **`std::make_shared`** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<memory>` 后写 `std::shared_ptr<T> p = std::make_shared<T>(args);`，或用 `auto p = std::make_shared<T>(args);`；模板参数 `T` 是要构造的对象类型。
  - **定义与目的**：`make_shared<T>(args...)` 一步构造对象和共享所有者，减少裸 `new` 暴露并提供良好的异常安全。
  - **机制**：实现通常把对象和控制块合并在一次分配中，改善分配次数和局部性；构造失败时已取得的资源由库自动回收。
  - **最小例子**：`std::shared_ptr<Widget> p = std::make_shared<Widget>(1, "x");`。
  - **常见失败/边界**：不能直接为 `make_shared` 指定任意自定义删除器；对象销毁后，只要 `weak_ptr` 仍存在，合并分配块中的存储可能暂不归还；需要特殊分配器时考虑 `allocate_shared`。
  - **依赖**：`MEM-16`、`EX-14`。

- [ ] `MEM-18` **`std::weak_ptr` 与循环引用** `【C++11·新增/标准库】`
  - **语法/接口格式**：由共享指针建立观察者写 `std::weak_ptr<T> weak = shared;`；使用前写 `if (std::shared_ptr<T> locked = weak.lock()) { use(*locked); }`，还可用 `expired()` 查询但不能据此替代随后一次 `lock()`。
  - **定义与目的**：`weak_ptr` 是对共享对象的非拥有观察，不增加强计数，用于缓存、观察者和打破双向关系的所有权环。
  - **机制**：`lock()` 原子地尝试取得一个临时 `shared_ptr`；对象已销毁时返回空；`expired()` 只给出瞬时观察，随后状态仍可能变化。
  - **最小例子**：树中父节点可拥有子节点 `shared_ptr`，子节点用 `weak_ptr` 指回父节点；使用时 `if (auto p = parent.lock()) { ... }`。
  - **常见失败/边界**：两个对象互持 `shared_ptr` 会使计数永不归零；先调用 `expired()` 再另行使用并不安全，应直接检查 `lock()` 的结果。
  - **依赖**：`MEM-16`。

- [ ] `MEM-19` **智能指针自定义删除器** `【C++11·标准库】`
  - **语法/接口格式**：独占形式为 `std::unique_ptr<T, Deleter> p(raw, Deleter{});`，删除器类型属于 `unique_ptr` 类型；共享形式为 `std::shared_ptr<T> q(raw, Deleter{});`，删除器保存在控制块中。
  - **定义与目的**：删除器把“如何释放”编码进所有者，允许智能指针管理 `FILE*`、套接字包装、第三方句柄或必须调用专用销毁函数的对象。
  - **机制**：`unique_ptr<T,D>` 的删除器是类型的一部分；`shared_ptr<T>` 把删除器保存在控制块中而不改变 `shared_ptr<T>` 的模板类型。
  - **最小例子**：`std::unique_ptr<FILE, int(*)(FILE*)> f(std::fopen("a.txt","r"), &std::fclose);`，使用前检查 `f`。
  - **常见失败/边界**：删除器必须接受正确句柄并安全处理约定的空值；有状态删除器可能增大 `unique_ptr`；释放函数必须与资源来源严格配对。
  - **依赖**：`BASE-07`、`MEM-14`、`MEM-16`。

- [ ] `MEM-20` **`enable_shared_from_this`** `【C++11·标准库】`
  - **语法/接口格式**：类写 `class T : public std::enable_shared_from_this<T> { public: std::shared_ptr<T> self() { return shared_from_this(); } };`；对象必须先由合适的 `std::shared_ptr<T>` 建立共享所有权后才能调用。
  - **定义与目的**：公开继承 `std::enable_shared_from_this<T>` 后，已由兼容 `shared_ptr` 管理的对象可以通过 `shared_from_this()` 取得共享同一控制块的新所有者。
  - **机制**：首个合适 `shared_ptr` 会设置基类内部弱引用；`shared_from_this()` 再从该弱引用构造共享所有者。
  - **最小例子**：`struct X : std::enable_shared_from_this<X> { std::shared_ptr<X> self(){ return shared_from_this(); } }; auto p = std::make_shared<X>();`。
  - **常见失败/边界**：在对象尚未被 `shared_ptr` 管理时调用会抛 `std::bad_weak_ptr`；在构造函数中调用通常过早；写 `shared_ptr<X>(this)` 仍会创建错误的第二控制块。
  - **依赖**：`MEM-16`。

- [ ] `MEM-21` **`std::allocator` 与 `allocator_traits`** `【C++11·标准库】`
  - **语法/接口格式**：可写 `std::allocator<T> alloc; typedef std::allocator_traits<decltype(alloc)> Traits; T* p = Traits::allocate(alloc, n); Traits::construct(alloc, p, args); Traits::destroy(alloc, p); Traits::deallocate(alloc, p, n);`。
  - **定义与目的**：分配器把原始存储管理与对象构造分离，使标准容器能适配不同存储来源；`allocator_traits` 为泛型代码统一访问分配器能力。
  - **机制**：`allocate(n)` 取得容纳 `n` 个 `T` 的未构造存储，`construct` 在指定位置建立对象，`destroy` 结束对象生存期，`deallocate` 归还原始存储。
  - **最小例子**：`std::allocator<T> a; T* p=a.allocate(1); std::allocator_traits<decltype(a)>::construct(a,p,args...); ... destroy(...); a.deallocate(p,1);`。
  - **常见失败/边界**：已分配元素数和释放参数要匹配；不能读取尚未构造的槽位；自定义分配器还涉及复制、传播和相等性规则，初学者不应凭猜测实现。
  - **依赖**：模板、`MEM-06`、`MEM-12`。

- [ ] `MEM-22` **对齐、`alignof` 和 `alignas`** `【C++11·新增】`
  - **语法/接口格式**：查询写 `std::size_t alignment = alignof(T);`；指定声明对齐写 `alignas(N) T object;` 或为原始缓冲区写 `alignas(T) unsigned char storage[sizeof(T)];`，其中对齐参数必须满足语言约束。
  - **定义与目的**：对齐要求限制对象起始地址；正确对齐让处理器和 ABI 能合法、高效地访问对象。
  - **机制**：`alignof(T)` 得到类型对齐要求；`alignas(T)` 或 `alignas(N)` 可提高声明实体的对齐，但不能用无效值削弱其自然对齐。
  - **最小例子**：`alignas(double) unsigned char storage[sizeof(double)];` 为在该缓冲中放置构造 `double` 提供大小和对齐基础。
  - **常见失败/边界**：仅有足够 `sizeof(T)` 的字节数仍可能未对齐；把任意 `char*` 强转成 `T*` 并解引用可能未定义；实际结构体布局还受 ABI 影响。
  - **依赖**：`MEM-01`、结构体布局。

- [ ] `MEM-23` **C++11 对过度对齐对象分配的限制** `【版本边界】`
  - **语法/接口格式**：C++11 可在声明中写 `struct alignas(N) T { ... };`，但没有 C++17 的 `std::align_val_t` 版 `operator new`/`delete`；过度对齐类型的动态分配要核对实现保证或使用成对的定制/平台分配接口。
  - **定义与目的**：过度对齐类型的要求大于实现普通动态分配保证的基本对齐；C++11 缺少后来标准化的对齐版全局分配接口。
  - **机制**：C++17 才引入带 `std::align_val_t` 的 `operator new/delete`。严格 C++11 中，扩展对齐动态存储通常要用平台接口、自定义分配器或类专用 `operator new`。
  - **最小例子**：`struct alignas(64) X { int v; };` 在静态或自动存储中由实现满足声明要求；动态创建时必须确认目标 C++11 实现是否支持该扩展对齐。
  - **常见失败/边界**：不能看到 `alignas(64)` 就假定所有 C++11 `new X` 在所有工具链上都符合；平台分配函数必须与其对应释放函数配对。
  - **依赖**：`MEM-09`、`MEM-22`。

- [ ] `MEM-24` **对象表示、填充字节和可平凡复制类型** `【C++11·语言】`
  - **语法/接口格式**：包含 `<cstring>` 与 `<type_traits>`；对可平凡复制类型可先检查 `static_assert(std::is_trivially_copyable<T>::value, "required");`，再用 `std::memcpy(&destination, &source, sizeof(T));` 复制对象表示。
  - **定义与目的**：对象表示是组成对象的 `sizeof(T)` 个字节；结构体可在成员间或末尾含填充；可平凡复制类型允许按标准规定复制其对象表示。
  - **机制**：可把可平凡复制对象的字节复制到 `char`/`unsigned char` 数组并复制回来恢复原值；类型特征 `std::is_trivially_copyable<T>` 可用于检查。
  - **最小例子**：`unsigned char buf[sizeof(int)]; std::memcpy(buf,&x,sizeof x); std::memcpy(&y,buf,sizeof y);` 可让 `y` 获得 `x` 的原值。
  - **常见失败/边界**：填充字节值可能不稳定，所以 `memcmp(&a,&b,sizeof a)==0` 不是一般结构体值相等的可靠定义；包含指针的对象字节也不是可移植序列化格式。
  - **依赖**：结构体、`MEM-01`。

- [ ] `MEM-25` **严格别名与字节观察** `【C++11·语言】`
  - **语法/接口格式**：观察对象字节可写 `const unsigned char* bytes = reinterpret_cast<const unsigned char*>(&object);` 并在 `[0, sizeof object)` 内读取；传递对象值优先用正确类型访问或对适用类型使用 `std::memcpy`，不要把任意 `reinterpret_cast<U*>` 的结果解引用。
  - **定义与目的**：别名规则限制可用哪些类型的左值访问对象，使编译器能够假定不相关类型通常不指向同一对象并据此优化。
  - **机制**：通常可通过对象本身类型、相应有符号/无符号类型、相关基类类型，或 `char`/`unsigned char` 左值观察对象表示；任意不相关类型指针解引用不合法。
  - **最小例子**：查看 `float` 字节可 `unsigned char bytes[sizeof f]; std::memcpy(bytes,&f,sizeof f);`，不要写 `*reinterpret_cast<unsigned*>(&f)` 做类型双关。
  - **常见失败/边界**：指针强制转换语法成功不代表解引用合法；联合体类型双关的可移植规则需谨慎；`std::byte` 是 C++17，不属于本图的 C++11 工具。
  - **依赖**：`BASE-04`、`MEM-24`。

- [ ] `MEM-26` **`volatile` 的真正含义** `【C++11·语言】`
  - **语法/接口格式**：声明写 `volatile T object;` 或 `volatile T* device = address;`，通过 volatile 左值进行访问；它不是互斥或原子语法，共享并发状态应使用 `<atomic>` 或锁接口。
  - **定义与目的**：`volatile` 表示对该对象的访问具有实现相关的可观察副作用，主要服务于内存映射设备寄存器等特殊环境。
  - **机制**：编译器必须按抽象机对 volatile 访问的规则处理，具体硬件效果由实现和平台文档决定；它不把复合表达式变为不可分割操作。
  - **最小例子**：嵌入式平台可能声明 `volatile std::uint32_t* status` 读取设备寄存器，但地址、宽度和屏障要求都来自平台规范。
  - **常见失败/边界**：`volatile int counter` 不能防止线程数据竞争，`++counter` 也不是原子操作；线程同步应使用 `std::atomic`、互斥量和明确的 happens-before 关系。
  - **依赖**：`BASE-04`。

- [ ] `MEM-27` **常见内存错误** `【工程概念】`
  - **语法边界**：无独立语法；泄漏、越界、重复释放、释放后使用和分配尺寸溢出要通过 `std::unique_ptr`、容器、范围/容量检查、成对资源接口及 ASan/Valgrind 等诊断手段预防和发现。
  - **定义与目的**：内存错误包括泄漏、越界、释放后使用、重复释放、分配/释放器不匹配、悬空引用、未初始化读取和异常路径遗失所有权。
  - **机制**：它们常由所有权不清、容量与长度混淆、对象生存期误判或手工清理路径不完整造成；后果可能是静默破坏、崩溃、信息泄漏或可利用漏洞。
  - **最小例子**：`int* p=new int; delete p; *p=1;` 是释放后使用；`int a[3]; a[3]=0;` 越界；循环覆盖唯一指针而未释放旧对象会泄漏。
  - **常见失败/边界**：程序“运行正常”不能证明没有未定义行为；把指针置空只能防止该变量再次使用，不能修复别名；优先用容器、智能指针和 RAII 消除错误类别。
  - **依赖**：`MEM-07`～`MEM-19`。

- [ ] `MEM-28` **内存诊断工具** `【工具链】`
  - **语法/接口格式**：GCC/Clang 常见构建格式为 `c++ -std=c++11 -g -fsanitize=address,undefined -fno-omit-frame-pointer source.cpp -o app`，运行期工具示例为 `valgrind --leak-check=full ./app`；选项名称和支持范围以具体工具链为准。
  - **定义与目的**：Sanitizer 和 Valgrind 在测试运行时检测部分内存与未定义行为问题，是代码审查和测试的补充，不属于 ISO C++11。
  - **机制/命令**：GCC/Clang 常用 `-std=c++11 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer` 编译并直接运行；Linux 上也可用 `valgrind --leak-check=full ./app`。
  - **工具分工**：ASan 关注越界和释放后使用，LSan 关注泄漏，UBSan 检查部分未定义行为，Valgrind Memcheck 以插桩/仿真方式检查内存访问；支持范围依编译器和平台而异。
  - **常见失败/边界**：工具只能检查实际执行到的路径且可能漏报；优化、第三方库和自定义分配器会影响结果；ASan 与 TSan 通常不是同一次构建组合使用。
  - **依赖**：`MEM-27`、`BUILD-16`。

- [ ] `TH-01` **进程、线程和并发的基本概念** `【工程概念】`
  - **语法边界**：无独立语法；C++11 线程内并发主要通过 `std::thread` 创建执行线程，并由 `std::mutex`、`std::condition_variable`、`std::atomic<T>` 等接口建立同步。
  - **定义与目的**：进程通常是操作系统资源与地址空间的隔离单位，线程是其中的一条执行序列；并发表示多个任务在重叠时间推进，并行表示它们在同一时刻真正执行。
  - **机制**：同一进程内线程通常共享全局对象、动态存储和打开的资源，但各自拥有执行状态和调用栈；调度器可在一个或多个 CPU 核心上切换或并行运行线程。
  - **最小例子**：单核机器也能通过时间片并发运行两个线程，但不一定并行；双核机器可能让二者同时执行。
  - **常见失败/边界**：进程与线程的具体资源模型由操作系统规定，不是 ISO C++11 的完整概念；共享地址空间带来通信便利，也带来数据竞争和生存期风险。
  - **依赖**：`BASE-01`。

- [ ] `TH-02` **`std::thread` 创建线程** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<thread>`；创建写 `std::thread worker(callable, args...);`，之后必须在该 `thread` 对象析构前执行 `worker.join();`、`worker.detach();` 或把所有权移动给其他对象。
  - **定义与目的**：`std::thread` 是 C++11 标准库对执行线程及其所有权的包装，可用任意满足调用要求的可调用对象启动新线程。
  - **机制**：构造 `std::thread t(f, args...)` 后，新线程以库保存的函数和参数副本调用 `f`；普通函数、函数对象、Lambda 和成员函数均可作为入口。
  - **最小例子**：`std::thread t([](int n){ std::cout << n; }, 7); t.join();`；成员函数可写 `std::thread t(&Worker::run, &worker, 7);`。
  - **常见失败/边界**：线程可能在构造返回前就开始执行；被捕获对象必须活得足够久；创建失败会抛 `std::system_error`；使用前包含 `<thread>`。
  - **依赖**：`BASE-03`、`BASE-07`。

- [ ] `TH-03` **线程参数的复制、移动与 `std::ref`** `【C++11·标准库】`
  - **语法/接口格式**：默认按值保存参数写 `std::thread t(function, value);`；显式按引用传递需包含 `<functional>` 并写 `std::thread t(function, std::ref(object));`，只读引用包装为 `std::cref(object)`。
  - **定义与目的**：线程对象默认持有参数的衰减副本，使调用不依赖构造表达式中的临时引用；需要共享原对象时必须显式表达引用语义。
  - **机制**：数组和函数参数发生衰减，顶层引用/`const` 通常被去除后复制或移动到内部存储；`std::ref(x)`/`std::cref(x)` 生成可复制的引用包装器。
  - **最小例子**：`void add(int& x){ ++x; } int x=0; std::thread t(add,std::ref(x)); t.join();`，之后 `x==1`。
  - **常见失败/边界**：`std::ref` 不延长对象生存期；分离线程引用局部变量极易悬空；即便引用有效，多线程同时访问它仍需同步。
  - **依赖**：引用、移动语义、`TH-02`。

- [ ] `TH-04` **`joinable`、`join` 和 `detach`** `【C++11·标准库】`
  - **语法/接口格式**：状态查询写 `if (worker.joinable()) worker.join();`；确需后台分离时写 `worker.detach();`。二者都使该 `thread` 对象不再关联可汇合线程，且不可对同一对象重复调用。
  - **定义与目的**：可连接状态表示 `thread` 对象仍关联一个执行线程；`join()` 等待其结束并回收关联，`detach()` 则让执行线程脱离该 C++ 对象独立运行。
  - **机制**：默认构造、已移动出、已 `join` 或已 `detach` 的对象不可连接；对正常结束但尚未 join 的线程，其 `thread` 对象仍是 joinable。
  - **最小例子**：`std::thread t(work); if (t.joinable()) t.join();`。工程上可写 RAII join 守卫，确保异常路径也收尾。
  - **常见失败/边界**：joinable 的 `std::thread` 析构会调用 `std::terminate`；对不可连接对象调用 `join/detach` 会抛 `std::system_error`；`detach` 不提供对象生存期或进程退出保障。
  - **依赖**：`TH-02`。

- [ ] `TH-05` **`std::thread` 是可移动但不可复制对象** `【C++11·标准库】`
  - **语法/接口格式**：转移关联线程写 `std::thread destination = std::move(source);`；`std::thread copy = source;` 不合法。向仍为 `joinable()` 的目标做移动赋值会导致 `std::terminate`，应先妥善处理目标线程。
  - **定义与目的**：一个执行线程只能由一个 `std::thread` 对象拥有连接责任，因此线程句柄采用独占、可转移的所有权模型。
  - **机制**：移动构造把关联线程交给新对象并使源对象不可连接；复制构造和复制赋值被删除。
  - **最小例子**：`std::thread a(work); std::thread b = std::move(a); b.join();`，此时 `a.joinable()==false`。
  - **常见失败/边界**：把另一个线程移动赋值给仍 joinable 的目标对象会调用 `std::terminate`，必须先 `join` 或 `detach`；容器中的线程也要在容器销毁前全部收尾。
  - **依赖**：`BASE-06`、`TH-04`。

- [ ] `TH-06` **线程入口异常处理** `【C++11·语言/标准库】`
  - **语法/接口格式**：在线程入口内部捕获：`std::thread t([] { try { work(); } catch (...) { handle_or_store(std::current_exception()); } });`；跨线程传递可使用 `std::exception_ptr` 或 `promise`/`future` 共享状态。
  - **定义与目的**：每个线程入口是异常传播的边界；线程内部应把失败转成线程间明确传递的状态，而不是让异常直接逃出。
  - **机制**：异常若越过 `std::thread` 调用的最外层函数，会调用 `std::terminate`；创建线程不会自动捕获该异常，`join()` 也不会重新抛出。
  - **最小例子**：在线程 Lambda 内 `try { work(); } catch (...) { ep = std::current_exception(); }`，主线程 `join()` 后 `std::rethrow_exception(ep)`。
  - **常见失败/边界**：日志后直接吞掉异常可能让主线程误判成功；共享错误状态需要同步；也可用 `promise/future` 自动携带值或异常。
  - **依赖**：`EX-06`、`TH-02`。

- [ ] `TH-07` **共享状态与数据竞争** `【C++11·语言】`
  - **语法/接口格式**：共享普通对象的访问通常统一写入临界区 `std::lock_guard<std::mutex> lock(mutex); use_or_modify(shared);`；适合独立原子化的状态可声明为 `std::atomic<T> shared(initial);`。
  - **定义与目的**：共享状态是多个线程能访问的同一内存；C++ 数据竞争发生在潜在并发的冲突访问之间，其中至少一个写、至少一个访问非原子，且没有 happens-before 顺序。
  - **机制**：数据竞争使整个程序行为未定义；正确同步可来自互斥量、原子操作、线程启动/完成关系或其他标准规定的同步操作。
  - **最小例子**：两个线程执行普通 `++counter` 会竞争，因为每次递增包含读和写；用同一 `std::mutex` 保护或使用合适的 `std::atomic<int>`。
  - **常见失败/边界**：`volatile`、睡眠、日志和“通常不会同时发生”都不是同步；多个线程只读一个已安全发布且不再修改的对象通常没有数据竞争。
  - **依赖**：`TH-01`、`MEM-06`。

- [ ] `TH-08` **互斥量类型** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<mutex>`；类型包括 `std::mutex`、`std::recursive_mutex`、`std::timed_mutex`、`std::recursive_timed_mutex`，基本接口为 `lock()`、`try_lock()`、`unlock()`，定时类型另有 `try_lock_for()`/`try_lock_until()`。
  - **定义与目的**：互斥量让同一时刻至多一个线程进入受保护临界区，以串行化共享状态访问并建立可见性。
  - **类型与机制**：`std::mutex` 是普通非递归锁；`recursive_mutex` 允许同一线程重复加锁并要求同次数解锁；`timed_mutex` 和 `recursive_timed_mutex` 增加 `try_lock_for/until`。
  - **最小例子**：`m.lock(); try { ++shared; } catch (...) { m.unlock(); throw; } m.unlock();` 展示语义，实际应使用锁守卫避免手工清理。
  - **常见失败/边界**：同一线程再次锁普通 `mutex` 可能死锁或未定义；解锁未拥有的锁是错误；递归锁容易掩盖设计问题，超时锁也不能自动消除死锁。
  - **依赖**：`TH-07`。

- [ ] `TH-09` **锁的 RAII 管理** `【C++11·标准库】`
  - **语法/接口格式**：固定作用域持锁写 `std::lock_guard<std::mutex> lock(mutex);`；需要延迟锁、解锁或移动所有权时写 `std::unique_lock<std::mutex> lock(mutex, std::defer_lock); lock.lock();`。
  - **定义与目的**：锁包装器把加锁状态绑定到对象生存期，确保正常返回和异常展开都会解锁。
  - **机制**：`lock_guard<Mutex>` 构造即加锁、析构即解锁，简单且不可移动；`unique_lock<Mutex>` 可延迟加锁、尝试加锁、主动解锁和移动，也是 `condition_variable` 等待所需类型。
  - **最小例子**：`{ std::lock_guard<std::mutex> lock(m); ++shared; }` 离开块后自动解锁。
  - **常见失败/边界**：锁守卫只保护所有线程都遵守同一协议的数据；不要把被保护数据的引用泄漏到锁外；`unique_lock` 的灵活性有状态和少量开销。
  - **依赖**：`BASE-09`、`TH-08`。

- [ ] `TH-10` **`std::lock` 与多个互斥量** `【C++11·标准库】`
  - **语法/接口格式**：可写 `std::unique_lock<std::mutex> a(m1, std::defer_lock); std::unique_lock<std::mutex> b(m2, std::defer_lock); std::lock(a, b);`，由两个 `unique_lock` 在作用域退出时分别解锁。
  - **定义与目的**：需要同时持有多个互斥量时，`std::lock` 使用避免死锁的算法完成组合加锁，减少不同调用点锁顺序不一致的风险。
  - **机制**：先构造 `unique_lock` 并传 `std::defer_lock`，再 `std::lock(l1,l2)`；`adopt_lock` 表示包装器接管当前线程已持有的锁，`try_to_lock` 表示只尝试一次。
  - **最小例子**：`std::unique_lock<std::mutex> a(m1,std::defer_lock), b(m2,std::defer_lock); std::lock(a,b);`。
  - **常见失败/边界**：`adopt_lock` 用于未持有的锁会破坏前置条件；把同一互斥量重复传入不成立；持多锁期间调用未知回调仍可能引入新的锁环。
  - **依赖**：`TH-09`。

- [ ] `TH-11` **死锁、活锁与饥饿** `【工程概念】`
  - **语法边界**：无独立语法；预防通常落到统一加锁顺序、`std::lock`、缩短 `std::lock_guard` 临界区，以及谨慎使用 `try_lock()` 与退避策略，标准接口不自动保证公平性。
  - **定义与目的**：死锁是参与者永久相互等待；活锁是一直动作但没有进展；饥饿是某线程长期得不到资源或调度机会。
  - **机制**：常见死锁来自循环等待，例如线程 A 持有 `m1` 等 `m2`，线程 B 持有 `m2` 等 `m1`；反复同时退让重试可能形成活锁；不公平竞争可能饥饿。
  - **预防方法**：规定全局锁顺序、用 `std::lock` 组合获取、缩短临界区、不持锁执行阻塞 I/O/未知回调，并明确锁层级。
  - **常见失败/边界**：超时和 `try_lock` 只能帮助恢复或诊断，错误重试策略仍会活锁；测试未复现不证明不存在时序故障。
  - **依赖**：`TH-08`～`TH-10`。

- [ ] `TH-12` **条件变量** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<condition_variable>` 与 `<mutex>`；等待方写 `std::unique_lock<std::mutex> lock(mutex); cv.wait(lock, [&] { return ready; });`，修改谓词状态后由通知方调用 `cv.notify_one();` 或 `cv.notify_all();`。
  - **定义与目的**：条件变量让线程在共享谓词不成立时阻塞，并在状态可能改变时被通知，避免持续忙等。
  - **机制**：`wait(lock,pred)` 等价于在循环中检查谓词，并在等待时原子地释放互斥量、被唤醒后重新加锁；`notify_one/all` 只是提示重新检查。
  - **最小例子**：消费者写 `std::unique_lock<std::mutex> l(m); cv.wait(l,[&]{return ready;}); use(data);`；生产者持锁写 `data` 和 `ready=true` 后通知。
  - **常见失败/边界**：允许虚假唤醒，所以必须使用谓词或 `while`；`std::condition_variable` 要配合 `unique_lock<std::mutex>`，更通用的锁需 `condition_variable_any`。
  - **依赖**：`TH-09`。

- [ ] `TH-13` **丢失唤醒与谓词状态** `【工程概念】`
  - **语法边界**：无独立语法；正确协议由受同一互斥量保护的状态谓词与 `cv.wait(lock, predicate)`、`cv.notify_one()`/`notify_all()` 共同组成，通知本身不保存“事件次数”。
  - **定义与目的**：通知本身不保存业务事件；真正持久的信息是受互斥量保护的共享状态，等待者依据它判断是否需要睡眠。
  - **机制**：若生产者先设置 `ready=true` 并通知，消费者稍后进入 `wait(lock,pred)`，谓词已真便不会睡眠，因此不会丢失事件。
  - **最小例子**：错误写法是没有 `ready` 状态而直接 `cv.wait(lock)`；正确写法是 `cv.wait(lock,[&]{ return !queue.empty() || stopped; });`。
  - **常见失败/边界**：在不同互斥量下读写谓词会重新引入竞争；只用原子标志配普通条件变量也必须精心建立等待/通知协议，否则容易错过通知。
  - **依赖**：`TH-12`。

- [ ] `TH-14` **一次初始化** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<mutex>`；声明 `std::once_flag flag;`，各线程调用 `std::call_once(flag, callable, args...);`，只有一次正常返回的调用完成初始化，抛异常的尝试不算完成。
  - **定义与目的**：一次初始化确保无论多少线程竞争，初始化动作在成功意义上只完成一次，并让完成结果对随后返回的调用者可见。
  - **机制**：共享 `std::once_flag` 与 `std::call_once(flag, init)`；若 `init` 抛异常，该次调用是异常返回，flag 不会标记成功，后续调用可重试。
  - **最小例子**：`std::once_flag flag; std::call_once(flag, []{ resource.reset(new R); });`。简单单例也可使用 C++11 线程安全的函数局部静态初始化。
  - **常见失败/边界**：`once_flag` 不可复制也不能普通重置；初始化函数内递归等待同一 flag 可能造成问题；一次初始化不使资源后续的可变操作自动线程安全。
  - **依赖**：局部静态对象、`TH-07`。

- [ ] `TH-15` **线程局部存储 `thread_local`** `【C++11·新增】`
  - **语法/接口格式**：声明写 `thread_local T per_thread;`；命名空间作用域、块作用域静态对象或类的静态数据成员可按相应规则使用 `thread_local`，每个线程访问自己的对象实例。
  - **定义与目的**：`thread_local` 让每个线程拥有一个独立对象实例，适合线程缓存、每线程统计和不能安全共享的上下文。
  - **机制**：命名空间或块作用域可声明线程存储期对象；每个线程首次需要时完成相应初始化，并在线程退出时销毁其已构造实例。
  - **最小例子**：`thread_local std::size_t requests = 0; void serve(){ ++requests; }`，不同线程的计数互不影响。
  - **常见失败/边界**：它不限制名字作用域，也不让它所指向的共享对象私有；大量线程局部缓存会放大内存；跨翻译单元初始化和析构依赖应尽量避免。
  - **依赖**：`MEM-03`、`TH-01`。

- [ ] `TH-16` **`future`、`promise` 与异步结果** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<future>`；生产者写 `std::promise<R> promise; std::future<R> future = promise.get_future(); promise.set_value(value);`，消费者写 `R result = future.get();`；失败可用 `promise.set_exception(std::current_exception());`。
  - **定义与目的**：`promise<T>` 是结果生产端，`future<T>` 是一次性消费端，二者通过共享状态在线程间传递值、异常或完成信号。
  - **机制**：`p.get_future()` 取得 future；生产者 `set_value` 或 `set_exception`；消费者 `get()` 等待并取出结果，若状态保存异常则在调用线程重新抛出。
  - **最小例子**：`std::promise<int> p; auto f=p.get_future(); std::thread t([&]{p.set_value(7);}); int x=f.get(); t.join();`。
  - **常见失败/边界**：同一 promise 的 future 和结果通常只能设置一次；普通 `future::get()` 只能成功调用一次；promise 未设置结果便销毁时，消费者得到 `broken_promise`。
  - **依赖**：移动语义、`EX-16`、`TH-02`。

- [ ] `TH-17` **`std::async` 与启动策略** `【C++11·新增/标准库】`
  - **语法/接口格式**：包含 `<future>`；明确异步启动写 `std::future<R> result = std::async(std::launch::async, callable, args...);`，延迟执行写 `std::launch::deferred`，组合策略用按位或。
  - **定义与目的**：`std::async` 把可调用任务与返回 `future` 的共享状态组合起来，适合直接表达“以后取得结果”。
  - **机制**：`launch::async` 要求异步执行；`launch::deferred` 推迟到等待或 `get` 时在调用该等待操作的线程执行；不指定时实现可从两种策略中选择。
  - **最小例子**：`auto f=std::async(std::launch::async, []{return compute();}); use(f.get());`。
  - **常见失败/边界**：默认策略不能保证新线程或立即执行；由 `async` 创建的某些 future 在析构时可能等待任务完成，临时 future 会意外串行化；它不是可控线程池接口。
  - **依赖**：`TH-16`。

- [ ] `TH-18` **`std::packaged_task` 与 `std::shared_future`** `【C++11·新增/标准库】`
  - **语法/接口格式**：任务包装写 `std::packaged_task<R(Args...)> task(callable); std::future<R> result = task.get_future(); task(args...);`；需要多个消费者时写 `std::shared_future<R> shared = result.share();`。
  - **定义与目的**：`packaged_task<R(Args...)>` 把可调用对象执行结果连接到 future；`shared_future<T>` 让多个观察者复制并等待同一共享状态。
  - **机制**：调用 packaged task 会把返回值或异常存入共享状态；普通 `future` 可通过 `share()` 转成可复制的 `shared_future`，之后原 future 失效。
  - **最小例子**：`std::packaged_task<int()> task([]{return 7;}); auto f=task.get_future(); std::thread t(std::move(task)); int x=f.get(); t.join();`。
  - **常见失败/边界**：`packaged_task` 可移动但不可复制；同一共享状态的 `get_future` 只能取得一次；多个线程可调用各自的 `shared_future` 副本读取结果，但对返回对象本身的可变使用仍需同步。
  - **依赖**：`BASE-07`、`TH-16`。

- [ ] `TH-19` **超时、睡眠和时钟** `【C++11·标准库】`
  - **语法/接口格式**：包含 `<chrono>` 与 `<thread>` 后可写 `std::this_thread::sleep_for(duration);`、`sleep_until(time_point);`；future/条件变量等定时等待使用 `wait_for(...)` 或 `wait_until(...)` 并检查返回状态。
  - **定义与目的**：`<chrono>` 提供类型安全的时长和时钟，线程与条件变量用它表达相对等待、绝对期限和退避。
  - **机制**：`std::this_thread::sleep_for(d)` 至少阻塞所指定时长附近，`sleep_until(tp)` 等到时间点；`steady_clock` 保证单调，适合超时，`system_clock` 适合墙上时间。
  - **最小例子**：`if (!cv.wait_for(lock,std::chrono::seconds(1),pred)) { /* timeout */ }`。
  - **常见失败/边界**：调度会使实际睡眠更久；系统时钟可被校时跳变；超时不是同步正确性的替代，带谓词的等待仍要处理状态竞争。
  - **依赖**：`std::chrono`、`TH-12`。

- [ ] `TH-20` **标准容器的并发访问边界** `【C++11·标准库规则】`
  - **语法/接口格式**：同一容器上的不安全组合操作应由外部锁包围，例如 `std::lock_guard<std::mutex> lock(mutex); container.push_back(value);`；能否无锁并发调用必须依据该容器与具体成员函数的标准保证判断。
  - **定义与目的**：标准库规定数据竞争避免责任，但容器不是自动加锁的数据结构；调用者必须根据是否访问同一容器及是否改变结构来同步。
  - **机制**：不同容器对象可并发操作；除 `vector<bool>` 外，可并发修改同一容器中的不同元素；结构变化、可能失效迭代器的操作以及同一元素冲突访问通常需要外部同步。
  - **最小例子**：预先固定大小的 `std::vector<int> v(2)` 可由两个线程分别写 `v[0]` 和 `v[1]`；任何线程同时 `push_back` 则必须同步。
  - **常见失败/边界**：`vector<bool>` 的位压缩使不同逻辑元素可能共享存储；“只调用一个看似读取的成员”也要确认没有另一线程改变容器结构或对象生存期。
  - **依赖**：`BASE-08`、`TH-07`。

- [ ] `TH-21` **C++11 中的协作式停止** `【工程概念】`
  - **语法边界**：无独立语法；C++11 没有 `stop_token`，常用 `std::atomic<bool> stop(false);` 表示停止请求，并配合 `std::condition_variable::notify_all()` 唤醒阻塞工作线程后再 `join()`。
  - **定义与目的**：协作式停止由工作线程在安全点检查请求并自行退出，避免强行终止造成锁未释放和对象状态损坏。
  - **机制**：使用 `std::atomic<bool>` 停止标志，或在互斥量保护下设置 `stopped` 并通知条件变量；所有者请求停止后仍应 `join()`。
  - **最小例子**：等待谓词写成 `!queue.empty() || stopped`；醒来后若 `stopped && queue.empty()` 就退出循环。
  - **常见失败/边界**：C++11 没有 `std::jthread`、`stop_token` 或标准线程中断；只设置标志却不唤醒阻塞线程会无法及时停止；分离线程尤其难以安全关闭。
  - **依赖**：`TH-04`、`TH-12`、`AT-06`。

- [ ] `TH-22` **生产者—消费者、任务队列和线程池** `【工程模式】`
  - **语法边界**：无独立语法；典型实现组合队列、`std::mutex`、`std::condition_variable`、若干 `std::thread` 和停止标志，并用 `cv.wait(lock, predicate)` 统一处理任务到达与关闭条件。
  - **定义与目的**：任务队列把提交任务与执行线程解耦；固定或可控数量工作线程可复用创建成本、限制并发量并形成背压。
  - **机制**：队列、互斥量、条件变量和停止状态构成核心；生产者持锁入队后通知，消费者按谓词等待、取出任务后在锁外执行。
  - **最小流程**：`submit → lock/push → notify_one`；工作线程 `wait(queue非空或停止) → pop → unlock → run`；关闭时设置停止、`notify_all`、最后 join 全部线程。
  - **常见失败/边界**：线程池不是 C++11 标准库组件；必须定义队列容量、拒绝策略、任务异常传播、关闭时处理剩余任务的语义，并避免在持队列锁时执行用户任务。
  - **依赖**：`TH-02`～`TH-18`。

- [ ] `TH-23` **原生线程句柄** `【C++11·接口/平台相关】`
  - **语法/接口格式**：标准侧写 `std::thread::native_handle_type handle = worker.native_handle();`；随后调用的平台线程 API、句柄类型及有效期由具体标准库和操作系统规定，不属于可移植 C++11。
  - **定义与目的**：`thread::native_handle()` 暴露实现底层线程句柄，以便设置标准库没有覆盖的亲和性、调度策略或线程名称。
  - **机制**：返回类型是实现定义的 `native_handle_type`；在常见 Linux 实现中可能关联 pthread，在 Windows 实现中可能关联 Windows 句柄，但不能跨实现假定。
  - **最小例子**：先由平台条件编译取得 `t.native_handle()`，再调用对应平台 API；可移植核心代码仍只使用 `join`、`get_id` 等标准接口。
  - **常见失败/边界**：原生操作可能破坏标准库假设或需要额外生命周期管理；平台句柄是否可复制、关闭及何时有效必须查实现文档。
  - **依赖**：`TH-02`。

# AT：原子操作与 C++11 内存模型

- [ ] `AT-01` **为什么需要内存模型** `【C++11·语言】`
  - **定义与目的**：内存模型规定多个执行线程何时可以访问同一对象、哪些结果可被观察以及什么情况属于未定义行为，为编译器、处理器和程序员建立共同契约。
  - **语法边界**：内存模型没有单独关键字；相关程序形式是普通对象声明 `int data = 0;`、原子对象声明 `std::atomic<bool> ready(false);`，以及 `std::mutex` 等同步接口。是否正确取决于访问之间的关系，而不是某一行特殊语法。
  - **机制**：编译器可在保持单线程可观察行为的前提下重排或消除操作，处理器也可能乱序执行并使用缓存；同步关系限制这些变化对其他线程的可见效果。
  - **最小例子**：线程 A 先写 `data=42` 再写标志，线程 B 看到标志后读数据；若标志只是普通 `bool`，程序可能有数据竞争，源码顺序不足以保证 `42` 可见。
  - **常见失败/边界**：不要把内存序简单解释成“刷新 CPU 缓存”；C++ 规定的是抽象机可观察关系，实际指令由编译器和目标架构决定。
  - **依赖**：`TH-07`。

- [ ] `AT-02` **内存位置和冲突访问** `【C++11·语言】`
  - **定义与目的**：内存位置是判断两个访问是否可能数据竞争的基本单位；通常一个标量对象是一个位置，相邻非零宽度位域可能共同构成一个位置。
  - **语法边界**：内存位置是语言语义单位，没有查询它的标准接口；`struct S { int a; int b; };` 的两个非位域成员通常是不同位置，而 `struct B { unsigned a:1; unsigned b:1; };` 的相邻非零宽度位域可能属于同一位置。
  - **机制**：两个动作访问重叠存储，且至少一个修改对象、开始或结束对象生存期，就可能冲突；冲突动作若跨线程、非原子且没有 happens-before，便形成数据竞争。
  - **最小例子**：两个线程分别写结构体中的两个普通 `int` 成员通常访问不同内存位置；分别写同一组相邻位域则可能冲突。
  - **常见失败/边界**：成员在物理上紧邻不一定是同一内存位置；反之位域看似不同名字也可能共享位置；对象生存期变化同样参与冲突判断。
  - **依赖**：`MEM-01`、`TH-07`。

- [ ] `AT-03` **`sequenced-before`** `【C++11·语言】`
  - **定义与目的**：`sequenced-before` 描述同一线程内两个求值的抽象先后；它解决表达式内部顺序，不能单独说明跨线程可见性。
  - **语法边界**：标准没有 `sequenced_before()` 查询函数；用两个完整表达式 `i = 1; ++i;` 明确建立顺序。内建 `lhs && rhs`、`lhs || rhs`、`lhs, rhs` 和 `cond ? a : b` 具有各自规定，而普通 `f(a(), b())` 的两个实参在 C++11 中没有彼此求值顺序保证。
  - **机制**：一个完整表达式的求值先于下一个完整表达式；`&&`、`||`、内建逗号运算符和条件运算符的被选分支有规定顺序，而许多函数实参和算术操作数在 C++11 中没有彼此顺序保证。
  - **最小例子**：`i = 1; ++i;` 两个完整表达式有顺序；`(i++) + (++i)` 对同一标量的修改彼此未排序，在 C++11 中行为未定义。
  - **常见失败/边界**：加分组括号只改变语法结合，不建立求值先后；编译器实际执行顺序偶然固定也不是标准保证。
  - **依赖**：表达式求值顺序。

- [ ] `AT-04` **`synchronizes-with` 和 `happens-before`** `【C++11·语言】`
  - **定义与目的**：`synchronizes-with` 是标准同步操作建立的跨线程边；`happens-before` 把单线程顺序、同步边及其传递闭包组合起来，决定写入何时必须可见。
  - **语法边界**：两种关系都不是可直接调用或查询的 API；典型建立形式是线程 A `m.unlock()` 与线程 B 后续成功的 `m.lock()`，或 `flag.store(v, std::memory_order_release)` 与读取到该发布值的 `flag.load(std::memory_order_acquire)`。
  - **机制**：互斥量的解锁同步于后来成功获得该锁的加锁；符合条件的 release 原子操作同步于读取它的 acquire 操作。A 先于 B、B 先于 C，则 A happens-before C。
  - **最小例子**：线程 A 持锁写 `x` 后解锁，线程 B 随后锁住同一互斥量再读 `x`，A 的写 happens-before B 的读。
  - **常见失败/边界**：真实时间“先发生”或线程睡眠不建立标准同步；同步必须作用于同一个协议对象，并满足具体操作的配对条件。
  - **依赖**：`TH-08`、`AT-03`。

- [ ] `AT-05` **数据竞争为什么是未定义行为** `【C++11·语言】`
  - **定义与目的**：C++ 把数据竞争规定为未定义行为，使实现可假定普通对象不会被无同步并发冲突访问，并进行寄存器缓存、合并和重排等优化。
  - **语法边界**：数据竞争不是语法错误，也没有 ISO C++11 运行时检测接口；共享普通对象的冲突访问必须统一放进 `std::lock_guard<std::mutex>` 等临界区，或把适合独立原子化的对象声明为 `std::atomic<T>`。
  - **机制**：一旦发生数据竞争，结果不受“最后一次写胜出”等简单规则约束；编译器无需维持程序员对逐条机器指令的直觉。
  - **最小例子**：`while (!ready) {}` 中普通 `bool ready` 被另一线程修改时，编译器可因竞争未定义而把读取提升出循环，导致永不退出。
  - **常见失败/边界**：给优化关闭、加入 `volatile` 或偶尔打印都不能修复；应使用互斥量或原子并证明 happens-before。
  - **依赖**：`AT-02`、`AT-04`。

- [ ] `AT-06` **`std::atomic<T>` 与 `std::atomic_flag`** `【C++11·新增/标准库】`
  - **定义与目的**：原子对象提供不可被其他线程观察为“撕裂”的访问，并允许指定内存顺序；`atomic_flag` 是最小原子布尔标志且保证无锁。
  - **语法/接口格式**：包含 `<atomic>`；典型声明和操作为 `std::atomic<T> a(initial); T x = a.load(order); a.store(value, order); T old = a.exchange(value, order);`。标志写 `std::atomic_flag f = ATOMIC_FLAG_INIT; f.test_and_set(order); f.clear(order);`；C++11 没有 `atomic_flag::test()`。
  - **机制**：`load` 读取、`store` 写入、`exchange` 原子替换；`std::atomic<T>` 不可复制。C++11 应显式初始化，例如 `std::atomic<int> count(0)`，`atomic_flag` 使用 `ATOMIC_FLAG_INIT`。
  - **最小例子**：`std::atomic<bool> ready(false); ready.store(true); if (ready.load()) { ... }`，未指定顺序时默认为 `seq_cst`。
  - **常见失败/边界**：除 `atomic_flag` 外不保证底层无锁；同一存储混入无同步非原子访问仍会竞争；原子化一个指针不会自动保护其所指对象。
  - **依赖**：模板、`TH-07`。

- [ ] `AT-07` **原子读—改—写操作** `【C++11·标准库】`
  - **定义与目的**：读—改—写操作把读取旧值、计算并写回新值作为一个不可分割原子动作，避免普通“读后写”丢失更新。
  - **语法/接口格式**：整型原子的核心形式为 `T old = a.fetch_add(arg, order);`，并有 `fetch_sub`、`fetch_and`、`fetch_or`、`fetch_xor`；整型和适用的指针原子还支持 `++a`、`a++` 等专用运算。返回值规则必须按具体接口确认。
  - **机制**：整型原子支持 `fetch_add/sub/and/or/xor` 以及递增递减；指针原子支持按元素步长的加减。返回旧值还是新值取决于具体操作和前后置形式。
  - **最小例子**：`int ticket = next.fetch_add(1);` 为每个调用者取得不同旧编号；普通 `next = next + 1` 不能替代并发原子递增。
  - **常见失败/边界**：没有通用的原子乘法等所有运算，需要比较交换循环；操作原子性不代表它与其他普通数据之间已有发布关系，仍要选择正确内存序。
  - **依赖**：`AT-06`。

- [ ] `AT-08` **比较交换** `【C++11·标准库】`
  - **定义与目的**：比较交换在当前值等于期望值时写入目标值，否则返回实际当前值，是实现条件更新和无锁算法的核心原语。
  - **语法/接口格式**：完整形式为 `bool ok = a.compare_exchange_weak(expected, desired, success_order, failure_order);` 或 `compare_exchange_strong(...)`；也有只给一个 `order` 或使用默认顺序一致序的重载。`expected` 必须是可修改的 `T&`。
  - **机制**：`compare_exchange_weak(expected, desired)` 允许无原因失败，适合循环；`strong` 不允许这种伪失败，适合一次尝试。失败时 `expected` 会被当前值覆盖。
  - **最小例子**：`int old=x.load(); while(!x.compare_exchange_weak(old,old+1)) {}`；每次失败后 `old` 已更新，可重新计算目标值。
  - **常见失败/边界**：失败内存序不能是 `release` 或 `acq_rel`，也不能比成功序更强；ABA 会让“值相同”掩盖中间发生过变化；循环还要考虑竞争退避。
  - **依赖**：`AT-06`。

- [ ] `AT-09` **原子对象的修改顺序** `【C++11·语言】`
  - **定义与目的**：每个原子对象都存在一个所有线程一致同意的修改全序，保证同一对象的写入不会被各线程以互相矛盾的顺序观察。
  - **语法边界**：修改顺序由 `a.store(...)`、`a.exchange(...)`、成功的 `a.compare_exchange_* (...)` 和其他读—改—写操作自动形成，没有枚举或查询整个顺序的标准 API；它只针对同一个原子对象。
  - **机制**：store、exchange、成功的比较交换和其他读—改—写都进入该对象的修改顺序；读取能看到哪个修改还受所用内存序及 happens-before 约束。
  - **最小例子**：若对同一原子 `x` 的修改顺序为 `1 → 2 → 3`，某线程不能先观察到 `3` 后又无依据地观察到更早的 `1`。
  - **常见失败/边界**：这是每个原子对象各自的顺序，不自动把 `x` 与另一个原子 `y` 的所有修改合成一个全局顺序；`seq_cst` 才增加更强的全局约束。
  - **依赖**：`AT-06`。

- [ ] `AT-10` **默认顺序一致 `memory_order_seq_cst`** `【C++11·语言】`
  - **定义与目的**：顺序一致是默认原子内存序，提供最直观的推理模型；所有顺序一致操作参与一个与相关 happens-before 和修改顺序一致的单一总序。
  - **语法/接口格式**：省略顺序时写 `a.store(value); T x = a.load();`，等价地可显式写 `a.store(value, std::memory_order_seq_cst); T x = a.load(std::memory_order_seq_cst);`。
  - **机制**：`x.store(1)` 和 `x.load()` 未显式传内存序时使用 `memory_order_seq_cst`；实现会按目标硬件需要生成足够约束。
  - **最小例子**：初学者可先只使用默认原子操作构建计数器和简单标志，再在有基准和证明时放宽内存序。
  - **常见失败/边界**：`seq_cst` 不会把非原子数据竞争变合法，也不保证业务复合操作整体原子；它可能比弱序更受限，但不应在未证明前盲目优化掉。
  - **依赖**：`AT-04`、`AT-06`。

- [ ] `AT-11` **释放—获取语义** `【C++11·语言】`
  - **定义与目的**：release/acquire 用一个原子对象发布并获取此前建立的普通数据，提供比全局顺序一致更局部的同步关系。
  - **语法/接口格式**：发布方写 `data = value; flag.store(true, std::memory_order_release);`；获取方写 `if (flag.load(std::memory_order_acquire)) { use(data); }`。两端必须通过同一原子通信，且 acquire 必须读取到相应发布值或符合规则的释放序列值。
  - **机制**：线程 A 在普通写后对标志执行 release；线程 B 的 acquire 读取到该 release 写入的值或相应释放序列中的值时，二者同步，A 之前的写对 B 之后的读可见。
  - **最小例子**：A：`data=42; ready.store(true,std::memory_order_release);`；B：`if(ready.load(std::memory_order_acquire)) assert(data==42);`。
  - **常见失败/边界**：B 若读取到旧的 `false` 就没有这条同步边；把 acquire/release 放在不相关原子上不能配对；发布后继续无同步修改 `data` 仍可能竞争。
  - **依赖**：`AT-04`、`AT-09`。

- [ ] `AT-12` **`memory_order_acq_rel`** `【C++11·语言】`
  - **定义与目的**：`acq_rel` 用于同时读取旧状态并发布新状态的原子读—改—写操作，一端获得前驱发布的数据，另一端向后继发布本线程数据。
  - **语法/接口格式**：只用于适合的读—改—写，例如 `T old = a.exchange(next, std::memory_order_acq_rel);` 或 `a.compare_exchange_weak(expected, desired, std::memory_order_acq_rel, std::memory_order_acquire)`；纯 `load`/`store` 不能随意使用该顺序。
  - **机制**：成功的 `fetch_add`、`exchange` 或比较交换可用 `memory_order_acq_rel`；其 acquire 部分约束之后操作，release 部分约束之前操作。
  - **最小例子**：状态机用 `state.exchange(next,std::memory_order_acq_rel)` 取得旧状态并发布新状态，但正确性仍需完整协议证明。
  - **常见失败/边界**：纯 `store` 不能使用 acquire/acq_rel，纯 `load` 不能使用 release/acq_rel；比较交换失败只执行读取，失败序应单独选择。
  - **依赖**：`AT-07`、`AT-11`。

- [ ] `AT-13` **`memory_order_relaxed`** `【C++11·语言】`
  - **定义与目的**：relaxed 只要求目标原子操作本身不可分割并遵守该对象的修改顺序，不建立普通数据的跨线程发布/获取。
  - **语法/接口格式**：典型接口为 `a.store(value, std::memory_order_relaxed); T x = a.load(std::memory_order_relaxed);` 和 `a.fetch_add(1, std::memory_order_relaxed);`；它们不能代替发布/获取协议。
  - **机制**：适用于只需要唯一编号、统计近似值或其他不携带附加状态的计数；不同线程可安全 `fetch_add`，但周围普通读写不因它自动可见。
  - **最小例子**：`requests.fetch_add(1,std::memory_order_relaxed);` 适合计数请求总量，而计数值不作为“其他数据已准备好”的信号。
  - **常见失败/边界**：用 relaxed `ready` 发布普通 `data` 是典型错误；原子计数精确并不代表读取时获得一致的多字段快照。
  - **依赖**：`AT-09`～`AT-11`。

- [ ] `AT-14` **`memory_order_consume`** `【C++11·语言/实务谨慎】`
  - **定义与目的**：consume 试图只沿数据依赖链传播可见性，比 acquire 约束更弱，理论上适合通过原子指针发布其所指数据。
  - **语法/接口格式**：接口形式为 `Node* p = head.load(std::memory_order_consume);`，发布端通常使用 `head.store(p, std::memory_order_release);`。工程代码一般把读取改成 `memory_order_acquire`，不要自行发明依赖保持技巧。
  - **机制**：读取 release 发布的指针后，依赖该值计算出的访问获得规定关系；与值无依赖的其他访问不受同样约束。
  - **最小例子**：概念上 `Node* p=head.load(memory_order_consume); use(p->value);`，`p->value` 地址依赖所加载的指针。
  - **常见失败/边界**：依赖传播规则复杂，编译器长期常按 acquire 实现，代码变换也可能破坏依赖；工程中通常直接使用 `memory_order_acquire`，以识别而非手写 consume 为目标。
  - **依赖**：`AT-11`。

- [ ] `AT-15` **内存栅栏** `【C++11·标准库】`
  - **定义与目的**：栅栏在没有把强内存序直接附着到某次数据访问时约束周围操作；它是专家级构件，必须与原子通信配合。
  - **语法/接口格式**：包含 `<atomic>` 后调用 `std::atomic_thread_fence(std::memory_order_release);`、`std::atomic_thread_fence(std::memory_order_acquire);` 等；信号相关接口为 `std::atomic_signal_fence(order)`。二者返回 `void`。
  - **机制**：`std::atomic_thread_fence(order)` 参与线程间内存排序；release fence 与 acquire fence 只有通过满足标准条件的原子写读链才能建立同步。`atomic_signal_fence` 主要约束同线程与信号处理器相关的编译器变换。
  - **最小例子**：多数发布场景直接写 release store/acquire load 更清晰；只有协议需要把栅栏与 relaxed 原子分离时才考虑 fence。
  - **常见失败/边界**：单独插入 fence 不会修复普通变量数据竞争，也不是任意硬件“全缓存刷新”；`atomic_signal_fence` 不提供一般线程间硬件同步。
  - **依赖**：`AT-11`～`AT-13`。

- [ ] `AT-16` **安全发布与消息传递** `【工程模式】`
  - **定义与目的**：安全发布确保接收线程不仅拿到对象地址，还能看到构造和初始化阶段写入的完整状态。
  - **语法边界**：安全发布不是独立关键字；严格 C++11 的典型形式是先完成 `payload = make_data();`，再执行 `ready.store(true, std::memory_order_release);`，接收端用 `ready.load(std::memory_order_acquire)` 成功后才访问 `payload`，或统一通过同一 `std::mutex`。
  - **机制**：可用同一互斥量保护指针和对象、`call_once`/局部静态初始化，或先完整初始化对象再 release 发布指针、由 acquire 获取。
  - **最小例子**：`payload=make_data(); ready.store(true,release);` 与接收方 `if(ready.load(acquire)) use(payload);`，并保证发布后没有无同步修改。
  - **常见失败/边界**：先公开指针再完成字段初始化会暴露半构造状态；双重检查锁在没有精确原子协议时容易错误；对象安全发布后，其后续可变访问仍需同步。
  - **依赖**：`AT-04`、`AT-11`。

- [ ] `AT-17` **原子引用计数不等于对象线程安全** `【C++11·标准库规则】`
  - **定义与目的**：`shared_ptr` 控制块的计数同步只保护所有权管理，不保护被指向对象的业务字段。
  - **语法边界**：`std::shared_ptr<T> local = shared;` 只安全管理控制块；`local->field` 的并发访问仍需在 `T` 内声明 `std::mutex mutex_;` 并用 `std::lock_guard<std::mutex> lock(mutex_);`，或把适合独立原子化的字段声明为 `std::atomic<U>`。
  - **机制**：多个线程可操作各自的 `shared_ptr` 副本并共享同一控制块；最后一个所有者销毁对象的过程由控制块协调，但 `p->x++` 仍是普通内存访问。
  - **最小例子**：两个线程各持一个 `shared_ptr<Counter>` 时，对 `Counter::value` 的写仍需成员互斥量或把该字段设计成原子。
  - **常见失败/边界**：并发读写同一个 `shared_ptr` 对象本身也可能竞争，应使用不同副本或 C++11 的原子自由函数；`use_count()` 不能用作可靠同步判断。
  - **依赖**：`MEM-16`、`AT-05`。

- [ ] `AT-18` **`shared_ptr` 的原子自由函数** `【C++11·标准库】`
  - **定义与目的**：C++11 在 `<memory>` 中为 `shared_ptr` 提供专用原子自由函数，使多个线程能安全替换和读取同一个共享指针槽位。
  - **语法/接口格式**：包含 `<memory>`；核心形式是 `std::shared_ptr<T> p = std::atomic_load(&slot);`、`std::atomic_store(&slot, value);`、`std::atomic_exchange(&slot, value)` 和 `std::atomic_compare_exchange_weak(&slot, &expected, desired)`；`*_explicit` 版本另接收合法内存序。
  - **机制**：`atomic_load`、`atomic_store`、`atomic_exchange`、`atomic_compare_exchange_weak/strong` 及其显式内存序版本对 `shared_ptr*` 工作；还可查询 `atomic_is_lock_free`。
  - **最小例子**：发布方 `std::atomic_store(&current,new_ptr);`，读取方 `auto snapshot=std::atomic_load(&current);`，后续通过快照保持对象存活。
  - **常见失败/边界**：同一 `shared_ptr` 槽位不能一部分访问用原子函数、一部分直接无同步读写；`std::atomic<std::shared_ptr<T>>` 特化属于 C++20，不是 C++11。
  - **依赖**：`MEM-16`、`AT-06`。

- [ ] `AT-19` **无锁不等于更快** `【工程概念】`
  - **定义与目的**：无锁描述进度性质或实现是否依赖锁，不直接说明延迟、吞吐、功耗、可维护性或实际竞争成本。
  - **语法边界**：可用 `bool lock_free = atomic_object.is_lock_free();` 查询该原子对象的实现性质；该布尔值不表达 lock-free、wait-free 等整个算法进度保证，也不是性能基准接口。
  - **机制**：`atomic<T>::is_lock_free()` 查询该对象实现；CAS 循环在竞争下可能反复失败，产生缓存行争夺和忙等。ABA 表示值从 A 变 B 又回 A，使单纯值比较看不出中间变化。
  - **最小例子**：低竞争临界区中的 `std::mutex` 可能比复杂 CAS 链更快、更公平且更容易证明；必须以目标负载基准测量。
  - **常见失败/边界**：`is_lock_free` 为真也不等于 wait-free；内存回收是无锁指针结构的独立难题，危险指针、epoch 等方案不属于 C++11 标准库。
  - **依赖**：`AT-06`～`AT-13`。

- [ ] `AT-20` **伪共享与缓存行** `【硬件/性能工程】`
  - **定义与目的**：伪共享是不同线程修改逻辑独立变量时，因变量落在同一硬件缓存一致性单元而反复使彼此缓存失效。
  - **语法边界**：C++11 只有通用对齐语法 `struct alignas(N) Slot { std::atomic<long> value; };`，其中 `N` 必须来自目标平台约定或测量；标准没有可移植的缓存行大小查询。`std::hardware_destructive_interference_size` 是 C++17。
  - **机制**：即使没有 C++ 数据竞争，缓存行所有权在核心间来回迁移也会降低吞吐；常见于相邻原子计数器或线程数组槽位。
  - **最小例子**：两个线程频繁递增 `counters[0]` 和 `counters[1]`，语义正确但若两元素同缓存行，性能可能远差于分离布局。
  - **常见失败/边界**：C++11 没有 `hardware_destructive_interference_size`（该常量从 C++17 才有）；手写 `alignas(64)` 是目标平台假设，会增加内存并需基准验证。
  - **依赖**：`AT-01`。

- [ ] `AT-21` **ThreadSanitizer** `【工具链】`
  - **定义与目的**：ThreadSanitizer（TSan）在测试执行中动态跟踪内存访问和同步事件，报告部分数据竞争和线程误用；它不属于 ISO C++11。
  - **语法边界**：TSan 没有 ISO C++11 头文件或函数；GCC/Clang 常见命令形式为 `c++ -std=c++11 -g -O1 -fsanitize=thread -fno-omit-frame-pointer source.cpp -pthread`，这些选项属于具体工具链而非语言标准。
  - **机制/命令**：受支持的 GCC/Clang 环境常用 `-std=c++11 -g -O1 -fsanitize=thread -fno-omit-frame-pointer` 编译、链接并运行测试。
  - **最小实践**：让并发测试覆盖高竞争、不同关闭顺序和异常路径，保存 TSan 报告中的两条访问栈及线程创建栈，再定位缺失的 happens-before。
  - **常见失败/边界**：未执行到的时序不会被发现；自定义汇编或 TSan 不认识的同步可能产生漏报/误报；通常不能与 ASan 放在同一个构建中，工具干净也不是正确性证明。
  - **依赖**：`AT-05`、`BUILD-16`。

# IO：标准文件与流式 I/O

- [ ] `IO-01` **流、设备和缓冲区的抽象** `【C++11·标准库】`
  - **定义与目的**：流把数据看成按顺序传输的字符序列，使同一套格式化接口可面对终端、文件或内存字符串；缓冲区减少底层设备调用并解耦生产与消费速度。
  - **语法边界**：抽象本身没有单独语法；统一的使用形态是 `std::ostream& out`、`std::istream& in`，通过 `out << value`、`in >> value` 或 `out.rdbuf()`/`in.rdbuf()` 连接格式层与 `std::basic_streambuf` 缓冲层。
  - **机制**：输入流从关联的 stream buffer 取得字符，输出流把字符交给 buffer；格式层把 `int` 等对象与字符表示互相转换。
  - **最小例子**：`std::cout << 42` 把整数格式化为字符并写到标准输出关联的缓冲；`std::ofstream` 使用相似语法写文件。
  - **常见失败/边界**：流传输的是字符表示，不会自动定义跨平台二进制协议；缓冲意味着“写入流对象成功”不一定等于数据已经持久化到设备。
  - **依赖**：`BASE-01`、`BASE-03`。

- [ ] `IO-02` **流类与头文件** `【C++11·标准库】`
  - **定义与目的**：标准流类按输入、输出、设备类型分层，都是 `basic_*<CharT,Traits>` 模板的常用 `char` 别名。
  - **语法/接口格式**：`#include <iostream>` 提供 `std::istream/std::ostream/std::iostream` 与标准流对象；`#include <fstream>` 提供 `std::ifstream/std::ofstream/std::fstream`；`#include <sstream>` 提供 `std::istringstream/std::ostringstream/std::stringstream`。
  - **体系**：`istream` 输入、`ostream` 输出、`iostream` 双向；`<fstream>` 提供 `ifstream/ofstream/fstream`；`<sstream>` 提供内存中的 `istringstream/ostringstream/stringstream`；`<iostream>` 声明标准流对象。
  - **最小例子**：`std::ifstream in("data.txt"); std::ostringstream out;`，分别需要 `<fstream>` 和 `<sstream>`。
  - **常见失败/边界**：仅有 `<iostream>` 不应依赖其间接提供所有文件流完整定义；流对象通常不可复制，文件流和字符串流在 C++11 中可移动。
  - **依赖**：类与继承。

- [ ] `IO-03` **标准流对象** `【C++11·标准库】`
  - **定义与目的**：`cin`/`cout` 对应标准输入输出，`cerr`/`clog` 用于诊断；程序无需手工创建或关闭它们。
  - **语法/接口格式**：包含 `<iostream>` 后直接使用 `std::cin >> value; std::cout << value; std::cerr << error; std::clog << message;`；宽字符对应对象为 `std::wcin/std::wcout/std::wcerr/std::wclog`。
  - **机制**：`cin` 默认与 `cout` 绑定，输入前会刷新相关输出；`cerr` 设置 `unitbuf`，通常每次输出操作后刷新；`clog` 更适合可缓冲日志。
  - **最小例子**：提示信息写 `std::cout << "name? " << std::flush;`，错误写 `std::cerr << "open failed\n";`。
  - **常见失败/边界**：`cerr` 常被口语称为“无缓冲”，更准确是具有自动刷新语义；重定向、终端和实现会影响底层缓冲行为。
  - **依赖**：`IO-01`。

- [ ] `IO-04` **格式化输出** `【C++11·标准库】`
  - **定义与目的**：插入运算符和 `<iomanip>` 操纵器控制对象转换成文本时的进制、精度、对齐、填充和布尔表示。
  - **语法/接口格式**：核心链式形式为 `std::ostream& result = (out << value);`；包含 `<iomanip>` 后可写 `out << std::hex << std::setw(width) << std::setfill(ch) << std::setprecision(n) << value;`，多数操纵器改变流状态。
  - **机制**：`std::hex/dec`、`fixed/scientific`、`setprecision`、`boolalpha` 等格式状态通常持续有效；`std::setw(n)` 只影响下一次格式化字段。
  - **最小例子**：`std::cout << std::hex << 255 << ' ' << std::dec << std::fixed << std::setprecision(2) << 3.5;` 输出类似 `ff 3.50`。
  - **常见失败/边界**：`setprecision` 在默认浮点格式下表示有效数字，在 `fixed` 下表示小数位数；库函数若临时修改流状态，必要时应保存并恢复。
  - **依赖**：运算符重载、`IO-03`。

- [ ] `IO-05` **格式化输入** `【C++11·标准库】`
  - **定义与目的**：提取运算符根据目标类型从字符序列中解析一个值，并通过流状态统一报告格式或设备失败。
  - **语法/接口格式**：核心形式为 `if (in >> value) { /* 成功 */ }`，多个字段可写 `if (in >> a >> b) ...`；空白策略可用 `in >> std::skipws` 或 `in >> std::noskipws` 调整。
  - **机制**：默认 `skipws` 会跳过前导空白；数字按当前进制解析，字符串读取到下一空白；解析失败通常设置 `failbit` 且目标值不能被当作成功结果使用。
  - **最小例子**：`int n; if (std::cin >> n) { use(n); } else { /* 输入不是合法整数或流失败 */ }`。
  - **常见失败/边界**：`operator>>` 不是整行读取；超范围数字也会失败；如需保留空白可用 `std::noskipws` 或无格式输入。
  - **依赖**：`IO-03`。

- [ ] `IO-06` **流状态位** `【C++11·标准库】`
  - **定义与目的**：状态位让 I/O 链在不默认抛异常的情况下记录结果：`goodbit` 无错误，`eofbit` 到达输入末尾，`failbit` 格式/逻辑失败，`badbit` 严重底层错误。
  - **语法/接口格式**：状态类型为 `std::ios_base::iostate`；使用 `stream.rdstate()`、`stream.good()`、`stream.eof()`、`stream.fail()`、`stream.bad()` 查询，`stream.clear()` 清回 `goodbit`，`stream.clear(state)` 设置完整状态，`stream.setstate(bits)` 追加状态位。
  - **机制**：`good()` 仅在状态为 goodbit 时真；`fail()` 在 failbit 或 badbit 时真；`bad()` 只检查 badbit；`eof()` 只检查 eofbit；流的布尔测试等价于“没有失败状态”。
  - **最小例子**：失败恢复常写 `in.clear(); in.ignore(std::numeric_limits<std::streamsize>::max(), '\n');`，分别清状态和丢弃坏输入。
  - **常见失败/边界**：`clear()` 不会删除缓冲区中的非法字符；EOF 往往与 failbit 同时出现；检查 `eof()` 不能替代检查本次读取是否成功。
  - **依赖**：`IO-05`。

- [ ] `IO-07` **正确的输入循环** `【C++11·标准库】`
  - **定义与目的**：应把“读取动作是否成功”作为循环条件，使每次进入循环时都拥有一个有效的新值。
  - **语法/接口格式**：格式化读取写 `T value; while (in >> value) { use(value); }`；按行读取写 `std::string line; while (std::getline(in, line)) { use(line); }`。循环后再根据 `eof()/fail()/bad()` 判断结束原因。
  - **机制**：`while (stream >> value)` 先尝试读取，再根据流状态转换为布尔值；最后一次失败不会执行循环体。
  - **最小例子**：`int n; while (in >> n) sum += n;`；循环结束后根据 `in.eof()` 区分正常结束和格式错误。
  - **常见失败/边界**：`while (!in.eof())` 会在读取失败前多进入一次，并且非 EOF 格式错误可能导致死循环；不要在失败后继续使用旧的 `value`。
  - **依赖**：`IO-05`、`IO-06`。

- [ ] `IO-08` **按词读取与按行读取** `【C++11·标准库】`
  - **定义与目的**：`operator>>` 适合类型化 token，`std::getline` 读取到分隔符并适合保留一行中的空格；选择取决于输入协议。
  - **语法/接口格式**：按词写 `in >> word;`；按行写 `std::getline(in, line);`，自定义分隔符写 `std::getline(in, field, delimiter);`。从格式化读取切到按行前常用 `in.ignore(std::numeric_limits<std::streamsize>::max(), '\n');`。
  - **机制**：`getline(in,s)` 消耗但不存储换行符；前一次 `>>` 通常把终止换行留在缓冲区，紧接的 getline 会读到空行。
  - **最小例子**：读取数字后整行可写 `in.ignore(std::numeric_limits<std::streamsize>::max(), '\n'); std::getline(in,line);`。
  - **常见失败/边界**：`std::getline(in >> std::ws,line)` 会吞掉所有前导空白和空行，只有协议允许时才用；Windows 文本模式的换行转换由流/实现处理。
  - **依赖**：`IO-05`、字符串。

- [ ] `IO-09` **文件流打开和关闭** `【C++11·标准库】`
  - **定义与目的**：文件流把文件资源和流状态封装成 RAII 对象，可在构造时打开或之后调用 `open()`，析构时自动关闭。
  - **语法/接口格式**：包含 `<fstream>`；构造打开写 `std::ifstream in(path, mode);` 或 `std::ofstream out(path, mode);`，延迟打开写 `std::ifstream in; in.open(path, mode);`；用 `in.is_open()`、流布尔状态和 `in.close()` 管理关联与错误。
  - **机制**：打开失败会设置失败状态；`is_open()` 只表示是否关联文件，`operator bool`/`fail()` 表示当前流操作状态；`close()` 解除关联并可能报告刷新或关闭错误。
  - **最小例子**：`std::ifstream in("data.txt"); if (!in) throw std::runtime_error("open");`。
  - **常见失败/边界**：只依赖析构无法方便地获知最终写入/关闭错误，重要输出应显式 `flush`/`close` 并检查状态；C++11 文件名编码受实现和平台约定影响。
  - **依赖**：RAII、`IO-02`。

- [ ] `IO-10` **文件打开模式** `【C++11·标准库】`
  - **定义与目的**：`std::ios_base::openmode` 位标志描述读写方向、追加、初始定位、截断和文本转换方式。
  - **语法/接口格式**：模式类型为 `std::ios_base::openmode`，组合使用按位或：`std::ios_base::openmode mode = std::ios::in | std::ios::out | std::ios::binary; std::fstream file(path, mode);`。可用标志有 `in/out/app/ate/trunc/binary`。
  - **机制**：`in` 读，`out` 写，`app` 使每次写位于文件末尾，`ate` 只在打开后初始定位末尾，`trunc` 打开时截断，`binary` 请求二进制模式；标志可按位或组合。
  - **最小例子**：`std::fstream f("data.bin", std::ios::in | std::ios::out | std::ios::binary);`。
  - **常见失败/边界**：`app` 与 `ate` 不同；默认模式因流类型而异，`ofstream` 默认写入通常会截断既有文件；不受实现支持的模式组合可能打开失败。
  - **依赖**：`IO-09`。

- [ ] `IO-11` **文本模式与二进制模式** `【C++11·标准库/实现相关】`
  - **定义与目的**：文本模式允许实现把外部文本表示转换成程序看到的字符序列，二进制模式尽量按原始字节传输。
  - **语法/接口格式**：文本模式通常省略 `binary`：`std::ifstream text(path);`；二进制模式写 `std::ifstream bytes(path, std::ios::in | std::ios::binary);`。`std::ios::binary` 只控制流模式，不声明数据协议。
  - **机制**：Windows 常见文本模式会在 `'\n'` 与外部 CRLF 间转换，并可能对某些控制字符有特殊处理；POSIX 常见实现中文本与二进制基本相同。
  - **最小例子**：读取图片或自定义字节协议使用 `std::ifstream in(path,std::ios::binary);`。
  - **常见失败/边界**：`binary` 不会规定整数大小、端序、浮点表示、结构体填充或字符编码；这些必须由文件格式另行定义。
  - **依赖**：`IO-10`。

- [ ] `IO-12` **无格式块读写** `【C++11·标准库】`
  - **定义与目的**：无格式操作按字符块传输，不进行数字或空白解析，适合固定字节协议、缓冲复制和二进制数据。
  - **语法/接口格式**：读取写 `in.read(char_buffer, static_cast<std::streamsize>(count)); std::streamsize got = in.gcount();`；写入写 `out.write(char_buffer, static_cast<std::streamsize>(count));`，随后检查 `in/out` 状态。
  - **机制**：`read(char*,n)` 尝试读恰好 n 个字符；不足时可同时置 eof/fail，`gcount()` 返回最近一次无格式输入实际提取量；`write(const char*,n)` 写指定数量。
  - **最小例子**：`char buf[4096]; while (in.read(buf,sizeof buf) || in.gcount()>0) out.write(buf,in.gcount());`。
  - **常见失败/边界**：写后必须检查输出状态；`gcount()` 只描述特定最近无格式输入；把非平凡对象地址直接当字符块读写会破坏对象和格式规则。
  - **依赖**：`IO-06`、`IO-09`。

- [ ] `IO-13` **文件位置** `【C++11·标准库】`
  - **定义与目的**：输入序列和输出序列各有逻辑位置，定位接口用于随机访问、重读或在文件中覆盖指定区域。
  - **语法/接口格式**：输入位置使用 `std::streampos p = in.tellg(); in.seekg(p); in.seekg(offset, std::ios::beg);`；输出位置对应 `tellp()`、`seekp(position)`、`seekp(offset, direction)`，方向为 `beg/cur/end`。
  - **机制**：输入用 `tellg/seekg`，输出用 `tellp/seekp`；可使用绝对位置或相对 `beg/cur/end` 的偏移。返回类型是流位置类型，不应随意假定为普通字节整数。
  - **最小例子**：`in.seekg(0,std::ios::end); std::streampos size=in.tellg(); in.seekg(0,std::ios::beg);`。
  - **常见失败/边界**：到 EOF 或失败后通常需先 `clear()` 再定位；文本模式中的位置和任意字节偏移可受实现限制；双向流切换读写还要遵守定位/同步规则。
  - **依赖**：`IO-09`。

- [ ] `IO-14` **缓冲、刷新与 `std::endl`** `【C++11·标准库】`
  - **定义与目的**：缓冲把多次小写合并以减少系统调用；刷新要求把流缓冲内容交给下层设备。
  - **语法/接口格式**：只换行写 `out << '\n';`；换行并刷新写 `out << std::endl;`；只刷新写 `out << std::flush;` 或 `out.flush();`；自动刷新模式可用 `out << std::unitbuf`，取消用 `std::nounitbuf`。
  - **机制**：`'\n'` 只插入换行字符，`std::endl` 插入换行并调用刷新，`std::flush` 只刷新；正常程序结束和流关闭也会触发相应清理。
  - **最小例子**：普通日志行优先 `out << text << '\n';`；必须立刻显示交互提示时用 `<< std::flush`。
  - **常见失败/边界**：每行 `endl` 会增加同步和系统调用成本；刷新到操作系统仍不等于磁盘持久化，后者涉及平台缓存和 `fsync` 等机制。
  - **依赖**：`IO-03`。

- [ ] `IO-15` **流绑定及与 C I/O 同步** `【C++11·标准库】`
  - **定义与目的**：`tie()` 在输入前刷新关联输出，`sync_with_stdio` 控制八个标准 C++ 流与对应 C 流的同步，以在兼容性和性能间选择。
  - **语法/接口格式**：绑定接口为 `std::ostream* old = in.tie(&out);`，解除绑定写 `in.tie(nullptr);`；全局同步接口为 `bool previous = std::ios_base::sync_with_stdio(false);`，通常必须在任何标准 I/O 之前调用。
  - **机制**：默认标准 C++ 流与 C `stdio` 同步，允许较安全地交错使用；`std::ios::sync_with_stdio(false)` 可减少同步开销，`std::cin.tie(nullptr)` 可解除默认绑定。
  - **最小例子**：批量输入程序常在任何 I/O 之前写 `std::ios::sync_with_stdio(false); std::cin.tie(nullptr);`。
  - **常见失败/边界**：开始 I/O 后再切换同步，其行为由实现规定；关闭同步后混用 `printf` 和 `cout` 的顺序不可凭直觉推断；并发字符输出安全不等于整行输出原子。
  - **依赖**：`IO-03`、`IO-14`。

- [ ] `IO-16` **流异常掩码** `【C++11·标准库】`
  - **定义与目的**：流默认通过状态位报告错误；异常掩码让指定状态出现时抛 `std::ios_base::failure`，适合希望把 I/O 失败纳入异常控制流的接口。
  - **语法/接口格式**：查询写 `std::ios_base::iostate mask = stream.exceptions();`；设置写 `stream.exceptions(std::ios::failbit | std::ios::badbit);`；捕获类型为 `const std::ios_base::failure&`。
  - **机制**：`stream.exceptions(std::ios::failbit | std::ios::badbit);` 设置掩码；此后相应状态被置位时抛异常，状态位仍保留供检查。
  - **最小例子**：`try { in.exceptions(std::ios::badbit); ... } catch (const std::ios_base::failure& e) { ... }`。
  - **常见失败/边界**：设置掩码时若当前状态已命中也可能立刻抛；EOF 是否当异常取决于是否把相关位加入掩码；混合状态判断与异常时要保持一致策略。
  - **依赖**：`EX-02`、`IO-06`。

- [ ] `IO-17` **字符串流** `【C++11·标准库】`
  - **定义与目的**：字符串流把 `std::string` 当作流缓冲，复用格式化输入输出语法完成解析、拼接和测试。
  - **语法/接口格式**：包含 `<sstream>`；读取用 `std::istringstream in(text); in >> value;`，输出用 `std::ostringstream out; out << value; std::string text = out.str();`，双向使用 `std::stringstream`；替换缓冲写 `stream.str(new_text)`。
  - **机制**：`istringstream` 读、`ostringstream` 写、`stringstream` 双向；`str()` 取得或替换内部字符串，状态位机制与其他流相同。
  - **最小例子**：`std::istringstream in("12 3.5"); int n; double d; if(in>>n>>d) ...`；格式化可 `std::ostringstream out; out<<n; auto s=out.str();`。
  - **常见失败/边界**：解析成功一个值不代表整串已经耗尽，应按协议检查剩余字符；复用流时通常既要 `str("")` 也要 `clear()`。
  - **依赖**：字符串、`IO-04`、`IO-05`。

- [ ] `IO-18` **Locale、字符集与编码边界** `【C++11·标准库/工程概念】`
  - **定义与目的**：locale 为数字格式、字符分类、排序和部分编码转换提供可插拔规则；字符编码则定义字节/码元如何表示文本，两者不是同一概念。
  - **语法/接口格式**：包含 `<locale>`；构造环境 locale 可写 `std::locale loc("");`，给流设置写 `std::locale old = stream.imbue(loc);`，访问 facet 写 `std::use_facet<Facet>(loc)`。这些接口不构成完整 Unicode 字符串处理方案。
  - **机制**：流可 `imbue(locale)` 使用 facet；窄流的 `char` 只承载字节，宽流承载 `wchar_t`，其宽度和外部编码均由实现/平台决定。
  - **最小例子**：C++11 的 `u8"..."` 产生 UTF-8 编码的窄字符字面量，但把它写入终端是否正确显示仍取决于终端编码和字体。
  - **常见失败/边界**：`std::locale` 不是完整 Unicode 文本库；大小写转换、字符个数、规范化和路径编码需要明确库与平台策略，不能用 `char` 个数冒充用户字符数。
  - **依赖**：字符类型、`IO-11`。

- [ ] `IO-19` **为什么不能直接把普通结构体写入文件作为通用格式** `【工程概念】`
  - **定义与目的**：内存布局是当前程序的对象表示，文件格式是跨运行、跨编译器或跨机器的数据契约，二者必须分离。
  - **语法边界**：`out.write(reinterpret_cast<const char*>(&object), sizeof object);` 在语法上可编译，却不自动成为可移植格式；ISO C++11 没有“序列化任意结构体”的关键字或通用标准接口，必须逐字段定义外部表示。
  - **机制**：结构体可能含未指定填充，成员宽度、端序、ABI 和浮点表示可不同；指针值只在原进程地址空间有意义；版本增加成员也会改变布局。
  - **最小例子**：`out.write(reinterpret_cast<const char*>(&record),sizeof record);` 最多用于严格受控的同实现临时数据，不能直接称为可移植协议。
  - **常见失败/边界**：即使类型可平凡复制，也只解决对象表示复制合法性，不解决长期格式兼容、安全校验和恶意输入；`memcmp` 同样不是一般值相等。
  - **依赖**：`MEM-24`、`IO-11`、`IO-12`。

- [ ] `IO-20` **显式序列化格式** `【工程概念】`
  - **定义与目的**：显式格式逐字段定义外部表示，使数据能跨版本、平台和语言稳定解析。
  - **语法边界**：C++11 没有标准序列化框架；工程接口可定义为 `bool encode(const Record&, std::ostream&);` 与 `bool decode(std::istream&, Record&);`，但字段宽度、端序、编码、长度上限和版本规则属于协议而非函数签名本身。
  - **机制**：协议应规定魔数、版本、字段标识或顺序、整数宽度与字节序、长度、文本编码、可选字段、边界检查以及完整性校验。
  - **最小例子**：将 32 位无符号长度明确编码成四个大端字节，再写入指定长度的 UTF-8 字节；读取时先验证最大长度再分配。
  - **常见失败/边界**：固定宽度 typedef 是否存在取决于实现，但常见 C++11 `<cstdint>` 可提供 `uint32_t`；序列化库和网络字节序函数不属于 C++11 核心，必须记录依赖和版本策略。
  - **依赖**：`IO-19`。

- [ ] `IO-21` **C 标准 I/O 在 C++ 中的接口** `【C++11·标准库】`
  - **定义与目的**：`<cstdio>` 提供 C 缓冲流接口，便于 C 库互操作、格式字符串 I/O 和块读写；资源句柄类型为 `FILE*`。
  - **语法/接口格式**：包含 `<cstdio>`；核心形式为 `std::FILE* f = std::fopen(path, mode); int rc = std::fclose(f);`、`std::size_t n = std::fread(ptr, size, count, f);`、`std::fwrite(...)`、`std::fprintf(f, format, ...)`，并用 `std::feof/std::ferror` 检查状态。
  - **机制**：`fopen/fclose` 管理流，`fread/fwrite` 传输元素块，`printf/fprintf` 按格式字符串转换；所有返回值和 `ferror/feof` 都应检查。
  - **最小例子**：`std::unique_ptr<FILE,int(*)(FILE*)> f(std::fopen("x","rb"),&std::fclose); if(!f) ...;`。
  - **常见失败/边界**：格式说明符与实参类型不匹配可能未定义；短读短写不能忽略；不要同时让两个包装器关闭同一 `FILE*`。
  - **依赖**：指针、格式字符串、`MEM-19`。

- [ ] `IO-22` **C++11 没有 `std::filesystem`** `【版本边界】`
  - **定义与目的**：C++11 标准文件流能打开文件，但没有统一的路径对象、目录遍历、权限、重命名和文件元数据 API；这些在 C++17 才由 `std::filesystem` 标准化。
  - **语法边界**：严格 `-std=c++11` 代码不能依赖 `#include <filesystem>`、`std::filesystem::path` 或目录迭代器；应把平台/第三方实现隔离在自定义接口如 `std::vector<std::string> list_directory(const std::string& path);` 之后。
  - **机制**：严格 C++11 工程可用 Boost.Filesystem，或在隔离的平台层封装 POSIX/Windows 文件系统接口。
  - **最小例子**：业务层定义 `list_directory(Path)` 接口，Linux 实现调用 POSIX API，Windows 实现调用 Win32；文件解析逻辑不直接依赖平台函数。
  - **常见失败/边界**：编译器即使在 C++11 模式提供实验扩展也不是 ISO C++11 保证；路径分隔符、大小写、权限和编码均有平台差异。
  - **依赖**：`IO-09`。

- [ ] `IO-23` **文件流、`FILE*` 和文件描述符的层次** `【工程/Linux】`
  - **定义与目的**：C++ 流提供类型化格式与 stream buffer，C `FILE*` 提供 C 缓冲流，POSIX 文件描述符是内核打开文件对象的整数句柄；它们处于不同抽象层。
  - **语法边界**：ISO C++11 只标准化 `std::ifstream/std::ofstream` 与 `<cstdio>` 的 `std::FILE*`；整数文件描述符及 `open/read/write/close/fileno/fdopen` 是 POSIX 接口，没有把 `fstream` 可移植转换为 fd 的标准函数。
  - **机制**：文件流和 `FILE*` 通常各自维护用户态缓冲，最终通过平台句柄访问内核；POSIX 的 `fileno`、`fdopen` 等桥接函数不是 ISO C++11。
  - **最小例子**：网络事件循环通常管理 fd，文本配置解析可用 `ifstream`；在模块边界明确谁拥有并关闭底层资源。
  - **常见失败/边界**：多个缓冲包装器指向同一底层 fd 会造成位置、刷新顺序和双重关闭问题；不能把 `FILE*` 强转为 fd 或假定 `fstream` 暴露标准原生句柄。
  - **依赖**：`IO-09`、`IO-21`、`LINUX-11`。

# BUILD：翻译、编译、链接和库

- [ ] `BUILD-01` **源文件、头文件和程序的关系** `【C++11·语言/工程概念】`
  - **命令/文件语法**：`// math.hpp: int add(int,int);`、`// math.cpp: #include "math.hpp"`、`// main.cpp: #include "math.hpp"`；GCC/Clang 驱动可用 `g++ -std=c++11 math.cpp main.cpp -o app`。文件后缀和命令属于工具链惯例，不是 ISO C++11 语法。
  - **定义与目的**：源文件通常作为独立翻译输入，头文件通常保存供多个源文件共享的声明和允许重复出现的定义，多个翻译单元及所需库共同组成一个程序。
  - **机制**：`#include` 是预处理文本包含，不是运行时导入；常见 `.cpp/.cc/.h/.hpp` 后缀帮助工具识别语言，但 ISO C++11 不强制这些名称。
  - **最小例子**：`math.hpp` 声明 `int add(int,int);`，`math.cpp` 包含该头并定义函数，`main.cpp` 包含该头并调用，最终两个目标文件链接。
  - **常见失败/边界**：头文件不是自动只编译一次的独立模块；把普通外部定义复制进头文件会在多个翻译单元产生重复定义。
  - **依赖**：`BASE-01`、`BASE-10`。

- [ ] `BUILD-02` **预处理、编译、汇编、链接** `【语言概念/工具链】`
  - **命令/文件语法**：GCC/Clang：`g++ -E a.cpp -o a.ii`（预处理）、`g++ -S -std=c++11 a.ii -o a.s`（编译）、`g++ -c a.s -o a.o`（汇编）、`g++ a.o b.o -o app`（链接）；具体阶段拆分选项不是 ISO C++11。
  - **定义与目的**：概念流程依次处理预处理指令、C++ 语法语义、汇编表示与机器目标代码、跨目标文件符号和重定位，最终形成可执行文件或库。
  - **机制**：预处理展开 `#include/#define/#if`；编译进行解析、类型检查、模板实例化和代码生成；汇编器生成目标文件；链接器解析定义并布局最终映像。驱动程序可把这些步骤合并。
  - **最小命令**：GCC/Clang 常用 `g++ -E a.cpp` 看预处理结果，`-S` 生成汇编，`-c` 只生成目标文件，`g++ a.o b.o -o app` 链接；这些命令不是 ISO C++。
  - **常见失败/边界**：缺头文件多在预处理阶段，语法/类型错在编译阶段，非法汇编或目标架构问题可能在汇编阶段，未定义/重复符号和缺库多在链接阶段。
  - **依赖**：`BUILD-01`。

- [ ] `BUILD-03` **翻译单元** `【C++11·语言】`
  - **语法边界**：翻译单元没有独立声明语法；它概念上是 `source.cpp` 经 `#include`、宏和条件编译后的结果。GCC/Clang 可用 `g++ -E source.cpp -o source.ii` 近似观察预处理输出，但 `.ii` 仍是工具文件。
  - **定义与目的**：翻译单元是一个源文件经过预处理、包含头文件并处理条件编译后的结果，是常见独立编译边界。
  - **机制**：同一头文件可被文本纳入多个翻译单元；每个单元单独进行名字查找、类型检查和代码生成，链接器之后才组合它们。
  - **最小例子**：`a.cpp` 与 `b.cpp` 都包含 `common.hpp`，会产生两个分别包含该头内容的翻译单元，而不是共享一个“头文件目标文件”。
  - **常见失败/边界**：宏只在当前预处理流程中生效；两个翻译单元因宏不同而看到不同类定义可能违反 ODR，且不一定得到诊断。
  - **依赖**：`BUILD-02`。

- [ ] `BUILD-04` **声明、定义与 ODR** `【C++11·语言】`
  - **命令/文件语法**：对象声明/定义：`extern int total;` / `int total = 0;`；函数声明/定义：`int add(int,int);` / `int add(int a,int b){ return a+b; }`；头文件放声明，恰当的一个 `.cpp` 放普通外部定义。
  - **定义与目的**：声明引入名字及类型信息，定义还建立函数体、对象或完整类型；一个定义规则（ODR）保证程序对实体身份和布局有一致理解。
  - **机制**：`extern int x;` 通常仅声明，`int x=0;` 定义对象；`void f();` 声明函数，`void f(){}` 定义函数。每个 odr-use 的非内联函数或变量通常必须在整个程序有唯一外部定义。
  - **允许例外**：类、模板和 inline 函数等可在多个翻译单元出现满足严格相同要求的定义，这正是部分定义可放头文件的基础。
  - **常见失败/边界**：有声明只保证当前翻译单元能编译，不保证链接时存在定义；部分 ODR 违反不要求诊断，程序可能链接成功却行为错误。
  - **依赖**：`BASE-03`、`BUILD-03`。

- [ ] `BUILD-05` **作用域、内部链接、外部链接和无链接** `【C++11·语言】`
  - **命令/文件语法**：内部链接常写命名空间作用域 `static int local;` 或 `namespace { int local; }`；跨文件对象由头文件 `extern int shared;` 配合一个源文件 `int shared = 0;`；块内普通局部变量无链接。
  - **定义与目的**：作用域回答名字在哪里可见，链接回答不同作用域中的声明能否表示同一实体；内部链接限于一个翻译单元，外部链接可跨翻译单元，无链接的名字不能这样关联。
  - **机制**：命名空间作用域 `static` 名字和匿名命名空间成员具有内部链接；普通外部函数及适当声明的命名空间对象通常有外部链接；局部变量无链接。命名空间作用域非 `extern` 的 `const` 对象默认具有内部链接。
  - **最小例子**：头文件 `extern int total;`，一个 `.cpp` 写 `int total=0;`；另一个 `.cpp` 包含头后可指向同一外部对象。
  - **常见失败/边界**：函数内 `static` 改变存储期而不是赋予跨文件链接；每个 `.cpp` 中各写 `static int x;` 得到不同对象。
  - **依赖**：作用域、`BUILD-04`。

- [ ] `BUILD-06` **头文件放声明、源文件放普通定义** `【工程惯例】`
  - **命令/文件语法**：`api.hpp` 写 `Result run(const Input&);`；`api.cpp` 首先 `#include "api.hpp"`，再写 `Result run(const Input& input) { ... }`；调用方只 `#include "api.hpp"`，不要 `#include "api.cpp"`。
  - **定义与目的**：公共头向使用者提供编译所需契约，单个源文件提供非内联外部实体的唯一实现，缩小重编译和 ODR 风险。
  - **机制**：实现文件也包含自己的公共头，使编译器检查声明和定义一致；使用者只依赖声明，不需要复制函数体。
  - **最小例子**：`api.hpp` 放 `Result run(const Input&);`，`api.cpp` 首行 `#include "api.hpp"` 并定义 `run`。
  - **常见失败/边界**：模板、类定义、inline 函数和某些常量通常需要放头文件；不要把 `.cpp` 当头文件包含来“共享实现”。
  - **依赖**：`BUILD-04`、`BUILD-05`。

- [ ] `BUILD-07` **为什么模板定义通常放在头文件** `【C++11·语言/工程惯例】`
  - **命令/文件语法**：头文件直接写 `template<class T> T max2(T a,T b){ return a<b?b:a; }`；若定义只放 `.cpp`，需显式实例化 `template int max2<int>(int,int);`，调用方可配合 `extern template int max2<int>(int,int);`。
  - **定义与目的**：编译器在实例化模板的翻译单元通常必须看到完整模板定义，才能针对实际模板实参生成代码。
  - **机制**：把模板声明和定义放头文件，使每个实例化点可见；ODR 对满足条件的模板重复定义提供支持。
  - **最小例子**：`template<class T> T max2(T a,T b){ return a<b?b:a; }` 通常完整写在 `.hpp`，调用 `max2<int>` 的源文件包含它。
  - **常见失败/边界**：只在 `.cpp` 定义模板、头里仅声明，其他翻译单元调用新类型时常得到未定义引用；可通过显式实例化集中生成已知类型，但必须维护支持类型集合。
  - **依赖**：模板、`BUILD-03`。

- [ ] `BUILD-08` **`inline` 与 ODR** `【C++11·语言】`
  - **命令/文件语法**：头文件定义形式为 `inline int twice(int x) { return x * 2; }`；类体内 `class C { int f(){ return 1; } };` 的成员定义隐式为 inline。没有“强制机器码内联”的标准命令。
  - **定义与目的**：`inline` 的关键语言作用是允许满足 ODR 条件的同一实体定义出现在多个翻译单元，便于在头文件定义短函数。
  - **机制**：类定义内部定义的成员函数隐式 inline；多个定义必须满足词法和名字查找一致等要求，链接后表示同一实体。
  - **最小例子**：头文件可写 `inline int twice(int x){ return x*2; }` 并被多个 `.cpp` 包含。
  - **常见失败/边界**：inline 不是强制机器代码展开，优化器可不内联；反过来未写 inline 的函数也可优化展开；用不同宏生成不同定义会违反 ODR。
  - **依赖**：`BUILD-04`。

- [ ] `BUILD-09` **头文件保护** `【C++11·预处理器】`
  - **命令/文件语法**：标准形式为 `#ifndef PROJECT_PATH_FILE_HPP`、`#define PROJECT_PATH_FILE_HPP`、正文、`#endif`；`#pragma once` 是常见编译器扩展而非 ISO C++11 指令。
  - **定义与目的**：include guard 防止同一翻译单元经直接或间接路径重复处理同一头文件内容。
  - **机制**：标准写法是唯一宏：`#ifndef PROJECT_FOO_HPP`、`#define PROJECT_FOO_HPP`、正文、`#endif`；第二次包含时条件为假。
  - **最小例子**：每个公共头都使用项目名和路径构造不冲突的保护宏；也常见 `#pragma once`。
  - **常见失败/边界**：`#pragma once` 被主流编译器支持但不是 ISO C++11 要求；保护宏重名会意外跳过另一个头；guard 只防单翻译单元重复，不能修复跨单元普通重复定义。
  - **依赖**：`BASE-10`、`BUILD-03`。

- [ ] `BUILD-10` **编译错误与链接错误** `【工具链】`
  - **命令/文件语法**：GCC/Clang 用 `g++ -std=c++11 -c source.cpp -o source.o` 隔离编译阶段，再用 `g++ source.o dependencies.o -o app` 隔离链接阶段；MSVC 对应 `/c` 编译与 `link`/驱动链接，诊断文字依平台。
  - **定义与目的**：按失败阶段分类能迅速定位责任：源语言问题由编译器诊断，跨文件实体解析由链接器诊断，程序装载失败则发生在运行前的装载阶段。
  - **编译错误**：缺少分号、名字未声明、类型不匹配、访问控制失败、模板实例化失败、歧义重载等；预处理还可能报头文件不存在或条件指令错误。
  - **链接错误**：声明存在但定义缺失、函数签名不一致导致符号不同、普通定义重复、漏链库、库顺序不对、目标架构/格式不兼容或入口点缺失。
  - **常见失败/边界**：动态库缺失或缺导出符号常在装载/运行时才失败；某些 ODR 违反无需诊断，所以“成功编译并链接”仍不证明程序符合标准。
  - **依赖**：`BUILD-02`、`BUILD-04`。

- [ ] `BUILD-11` **名字修饰与函数重载** `【ABI/工具链】`
  - **命令/文件语法**：GNU/LLVM 工具可用 `nm -C file.o` 查看并反修饰，或把修饰名传给 `c++filt`；MSVC 常用 `dumpbin /symbols file.obj`。修饰编码没有 ISO C++11 可移植语法。
  - **定义与目的**：C++ 允许命名空间、类成员和重载，工具链通常把这些类型信息编码进目标符号名，以便链接器区分同名函数。
  - **机制**：源码中的 `ns::f(int)` 和 `ns::f(double)` 会获得不同修饰符号；编码方案由平台 ABI 和编译器决定。
  - **最小例子**：链接器报告中类似 `_ZN2ns1fEi` 的名字可用平台工具反修饰成人类可读签名；具体形式不是 C++ 语法。
  - **常见失败/边界**：不同编译器版本、ABI 或选项可能生成不兼容符号；只看到相同源码函数名不能证明链接签名一致。
  - **依赖**：重载、`BUILD-05`。

- [ ] `BUILD-12` **`extern "C"` 语言链接** `【C++11·语言】`
  - **命令/文件语法**：单个声明：`extern "C" int api(int);`；共享头块：`#ifdef __cplusplus` / `extern "C" {` / `#endif`，C 声明正文，再按相同条件写 `}`。
  - **定义与目的**：`extern "C"` 为函数类型和具有外部链接的名字指定 C 语言链接，常用于声明由 C 实现或供 C 调用的接口。
  - **机制**：可写 `extern "C" int api(int);` 或链接规范块；共享头常用 `#ifdef __cplusplus extern "C" { #endif` 使 C++ 编译器启用、C 编译器跳过。
  - **最小例子**：导出函数只使用固定宽度整数、字节缓冲和不透明句柄，内部捕获所有 C++ 异常并返回稳定状态码。
  - **常见失败/边界**：C 语言链接不支持靠 C++ 重载形成多个同名 C 接口，也不统一类布局、异常、模板、标准库或分配器；接口类型本身必须让双方理解。
  - **依赖**：`BUILD-11`。

- [ ] `BUILD-13` **ABI 的含义** `【工程概念】`
  - **语法边界**：ABI 没有一条 ISO C++11 声明可统一指定；调用约定、导出属性、packing、运行库和符号版本均是平台/工具链接口。跨长期边界常用 `extern "C"` 加不透明句柄，但仍需单独规定数据布局和所有权。
  - **定义与目的**：ABI 是已编译组件之间的二进制契约，覆盖调用约定、参数/返回传递、名字修饰、对象布局、虚表、异常展开、运行库和符号版本等。
  - **机制**：源码 API 相同但 ABI 不同的组件可能链接失败，或更危险地链接成功后按不同布局解释内存。
  - **最小例子**：一个库按 8 字节对齐编译、调用方按打包对齐理解同一结构体，字段偏移不同就会读错。
  - **常见失败/边界**：ISO C++11 主要规定语言语义，不保证跨编译器二进制兼容；稳定插件边界常采用窄 C ABI、不透明句柄、显式版本和同侧分配/释放。
  - **依赖**：`BUILD-11`。

- [ ] `BUILD-14` **目标文件、可执行文件和符号表** `【工具链】`
  - **命令/文件语法**：GCC/Clang：`g++ -std=c++11 -c a.cpp -o a.o`、`g++ a.o b.o -o app`；Linux/ELF 查看符号用 `readelf -Ws a.o` 或 `nm -C a.o`，Windows/COFF 常用 `dumpbin /symbols a.obj`。
  - **定义与目的**：目标文件包含机器代码、数据、未解析引用和重定位信息；链接器组合它们生成可执行文件或共享对象；符号表记录可供解析或调试的名字及属性。
  - **机制**：已定义符号提供实体，未定义符号等待其他目标或库满足，重定位告诉链接器最终地址确定后需要修补的位置。
  - **最小例子**：`g++ -c a.cpp -o a.o` 生成尚不可独立运行的目标文件，`g++ a.o b.o -o app` 完成最终链接。
  - **常见失败/边界**：ELF、COFF/PE、Mach-O 等格式和符号可见性是平台工具链事实，不由 C++11 固定；剥离符号会影响调试但不必然影响所需动态导出。
  - **依赖**：`BUILD-02`。

- [ ] `BUILD-15` **静态库和动态库** `【工程概念】`
  - **命令/文件语法**：Linux/GNU 静态库：`ar rcs libfoo.a foo.o`；ELF 共享库：`g++ -shared -o libfoo.so foo.o`（对象通常以 `-fPIC` 编译）；Windows 常见 `.lib/.dll` 由 MSVC `lib`/`link /DLL` 生成。均非 ISO C++11。
  - **定义与目的**：静态库是目标文件集合，最终链接时把所需代码纳入产物；动态库保留为独立二进制依赖，由装载器在启动或运行中解析。
  - **机制**：静态链接通常增大每个可执行文件但部署依赖少；动态库可由多个进程共享映射并独立更新，但需要稳定搜索、版本和 ABI。
  - **最小例子**：Linux 常见 `.a/.so`，Windows 常见 `.lib/.dll`，但具体格式和导入库机制由平台决定。
  - **常见失败/边界**：静态库更新后必须重新链接程序才能生效；动态库更新后程序重启可能加载新版，但 SONAME/导出符号不匹配会装载失败，ABI 悄然不兼容则可能运行时崩溃。
  - **依赖**：`BUILD-10`、`BUILD-14`。

- [ ] `BUILD-16` **调试、优化和诊断编译选项** `【工具链】`
  - **命令/文件语法**：GCC/Clang 开发构建常用 `g++ -std=c++11 -g -O0 -Wall -Wextra -Wpedantic ...`，发布常从 `-O2` 起验证；ASan 示例需编译和链接都带 `-fsanitize=address`。MSVC 选项不同。
  - **定义与目的**：构建配置控制调试信息、优化、警告、语言扩展、运行时检查和代码生成；应按开发、测试和发布目标组合。
  - **机制/命令**：GCC/Clang 常见开发选项为 `-g -O0 -Wall -Wextra -Wpedantic`，发布常用经验证的 `-O2`；Sanitizer 需编译和链接阶段都带相应 `-fsanitize=...`。
  - **最小实践**：CI 至少建立严格警告构建、普通测试构建和一种 Sanitizer 构建，记录完整编译命令以便复现。
  - **常见失败/边界**：警告集合和含义由编译器版本决定；`-Werror` 适合受控 CI 但第三方头升级可能打断构建；优化会改变调试体验而不应改变符合标准程序语义。
  - **依赖**：`BUILD-02`。

- [ ] `BUILD-17` **指定 C++11 模式** `【工具链】`
  - **命令/文件语法**：GCC/Clang：`g++ -std=c++11 -pedantic-errors source.cpp -o app`；`-std=gnu++11` 允许 GNU 扩展。MSVC 没有完整等价的历史 C++11 模式，应以编译器版本和特性验证为准。
  - **定义与目的**：显式选择语言标准可防止不同机器使用编译器默认模式，确保题库和工程只依赖约定的 C++11 特性。
  - **机制/命令**：GCC/Clang 使用 `-std=c++11`，若还需严格排除 GNU 扩展可配合 `-pedantic-errors`；`-std=gnu++11` 是含 GNU 扩展的方言。
  - **平台边界**：MSVC 没有与 GCC 完全对应的历史 C++11 开关，其 `/std:` 支持与编译器版本不同，应选择满足需求的工具版本并用特性测试构建验证。
  - **常见失败/边界**：编译器接受某语法不等于标准库也完整实现；不要把供应商扩展当 C++11；所有目标和第三方二进制仍需 ABI 相容。
  - **依赖**：`BUILD-16`。

- [ ] `BUILD-18` **链接顺序和依赖闭包** `【工具链】`
  - **命令/文件语法**：GNU 风格静态链接通常写 `g++ main.o -L/path -lfoo -lbar -o app`，让使用者在前、提供定义的库在后；循环归档可由 GNU ld 的 `-Wl,--start-group ... -Wl,--end-group` 处理，但该选项不可移植。
  - **定义与目的**：最终链接必须为所有需要的外部符号找到定义；某些链接器按命令行顺序扫描静态归档，因此库的排列会改变能否抽取成员。
  - **机制**：GNU 风格链接常要求使用者在前、提供定义的静态库在后，如 `g++ main.o -lfoo`；循环静态依赖可用重构或特定链接器 group 选项处理。
  - **最小例子**：若 `main.o` 引用 `foo`，先扫描 `libfoo.a` 再看到引用可能不抽取成员，而把 `-lfoo` 放后面可成功；这是工具链规则。
  - **常见失败/边界**：不同平台、动态库、链接器的扫描和 `--as-needed` 行为不同；更好的工程做法是让构建系统从 target 依赖传播完整链接闭包。
  - **依赖**：`BUILD-10`、`BUILD-15`。

- [ ] `BUILD-19` **标准库与运行库** `【工具链】`
  - **命令/文件语法**：链接 C++ 目标优先使用驱动 `g++ objects... -o app` 或 `clang++ ...`，由驱动加入对应 C++ 标准库/运行库；直接用 `gcc`/`ld` 时必须自行提供准确库项，具体名称依平台。
  - **定义与目的**：编译器前端解析语言；标准库实现容器、线程和 I/O；ABI/低层运行库支持异常展开、整数辅助、启动和线程本地存储，它们是不同组件。
  - **机制**：GCC 常与 libstdc++、libgcc 配合，Clang 可搭配 libc++ 或 libstdc++ 及不同运行库；驱动程序通常自动添加默认库。
  - **最小例子**：用 `gcc` 链接 C++ 目标可能漏掉 C++ 标准库，而 `g++` 驱动通常自动加入正确 C++ 链接项。
  - **常见失败/边界**：能使用同一编译器前端不代表标准库 ABI 相同；跨边界传递 `std::string`、异常或由一侧分配另一侧释放尤其依赖运行库一致性。
  - **依赖**：`BUILD-13`。

- [ ] `BUILD-20` **编译选项和宏必须保持 ABI 一致** `【工程概念】`
  - **语法边界**：没有能自动保证 ABI 一致的 ISO C++11 语法；应让同一构建 target 传播架构、packing、异常/RTTI、运行库和公共宏，并用生成配置头（如 `#define PROJECT_ABI_VERSION 1`）及 CI 工具链矩阵校验。
  - **定义与目的**：所有共享二进制类型和接口必须在调用方与实现方得到相同布局、调用及运行库解释，否则会链接失败或产生难定位的内存破坏。
  - **机制**：目标架构、指针宽度、结构体 packing、调试迭代器、异常/RTTI、字符宽度、运行库选择和改变类定义的条件宏都可能影响 ABI。
  - **最小实践**：把公共 ABI 配置集中到构建 target 和生成配置头中，导出版本/特性标识，并在 CI 用同一工具链矩阵构建调用方和库。
  - **常见失败/边界**：诸如 libstdc++ 双 ABI 宏或 MSVC 运行库选项属于具体工具链，必须查版本文档；不要仅靠“能链接”判断 ABI 一致。
  - **依赖**：`BUILD-13`、`BUILD-16`。

# CMAKE：CMake 工程组织

> CMake **不属于 C++11**。它负责生成构建系统并组织编译、链接、测试和安装。  
> 动态库、编译和链接不是“CMake 的知识”，CMake 只是调用相应工具完成这些工作。

- [ ] `CMAKE-01` **CMake 在工具链中的位置** `【工具链】`
  - **命令/文件语法**：项目入口文件名为 `CMakeLists.txt`；典型驱动命令是 `cmake -S <source-dir> -B <build-dir> -G <generator>`，再执行 `cmake --build <build-dir>`。这些是 CMake CLI，不是 ISO C++11。
  - **定义与目的**：CMake 是跨平台构建系统生成器和项目配置语言，不是编译器；它把 target、依赖和选项转换成 Ninja、Make、Visual Studio 等原生构建系统能执行的规则。
  - **机制**：典型链路是“CMake 读取项目 → 探测工具链和依赖 → 生成构建文件 → 原生构建工具调编译器/链接器 → 得到产物”。
  - **最小例子**：同一份 `CMakeLists.txt` 可在 Linux 生成 Ninja 文件，在 Windows 生成 Visual Studio solution，但具体编译器和 ABI 仍由所选工具链决定。
  - **常见失败/边界**：动态库、编译和链接不是 CMake 发明的概念；CMake 只组织并调用工具。CMake 版本、生成器和平台行为也不属于 ISO C++11。
  - **依赖**：`BUILD-02`。

- [ ] `CMAKE-02` **配置、生成与构建三个阶段** `【工具链】`
  - **命令/文件语法**：配置并生成：`cmake -S . -B build [configure-options]`；构建：`cmake --build build [--config Debug|Release] [--parallel N]`；重新配置仍运行第一条命令。
  - **定义与目的**：配置阶段执行 CMake 语言并探测环境，生成阶段写出原生构建规则，构建阶段才实际编译和链接。
  - **机制/命令**：`cmake -S . -B build` 通常连续完成配置与生成；`cmake --build build` 调用所选生成器；缓存保存编译器路径、选项和探测结果。
  - **最小例子**：多配置生成器构建发布版常写 `cmake --build build --config Release`。
  - **常见失败/边界**：更换编译器、架构或关键工具链设置后沿用旧缓存会产生混乱，通常应使用新的构建目录；构建失败要进一步看实际编译/链接命令。
  - **依赖**：`CMAKE-01`。

- [ ] `CMAKE-03` **最小工程结构** `【工具链】`
  - **命令/文件语法**：最小 `CMakeLists.txt`：`cmake_minimum_required(VERSION 3.16)`、`project(demo LANGUAGES CXX)`、`add_executable(app main.cpp)`；版本号表示该项目选择的 CMake 基线，不表示 C++ 标准版本。
  - **定义与目的**：顶层项目至少声明兼容的 CMake 版本、项目语言和一个构建目标，使配置具有明确策略和产物。
  - **机制/语法**：示例：`cmake_minimum_required(VERSION 3.16)`、`project(demo LANGUAGES CXX)`、`add_executable(app main.cpp)`；这里 3.16 是项目选择，不是 C++11 要求。
  - **最小目录**：源码目录放 `CMakeLists.txt` 和源码，独立 `build/` 保存缓存、生成文件、目标文件及最终产物。
  - **常见失败/边界**：不要省略 `cmake_minimum_required` 后依赖未确定策略；不要在配置阶段硬编码产物的生成器特定路径。
  - **依赖**：`CMAKE-02`。

- [ ] `CMAKE-04` **Target 是核心抽象** `【工具链】`
  - **命令/文件语法**：创建目标用 `add_executable(app sources...)`、`add_library(core [STATIC|SHARED|...] sources...)`；随后用 `target_sources`、`target_include_directories`、`target_compile_*`、`target_link_libraries` 配置同一目标。
  - **定义与目的**：target 表示可执行文件、库或只携带使用要求的逻辑组件，是附加源文件、头路径、编译特性和链接依赖的基本单位。
  - **机制**：每个 target 具有自身属性；通过 `target_*` 命令建立依赖图，CMake 再按图传播编译和链接使用要求。
  - **最小例子**：`add_library(core core.cpp)`；`add_executable(app main.cpp)`；`target_link_libraries(app PRIVATE core)`。
  - **常见失败/边界**：全局修改 `CMAKE_CXX_FLAGS` 或 `include_directories` 会把设置泄漏给无关目标；优先把要求绑定到真正需要它的 target。
  - **依赖**：`BUILD-15`、`CMAKE-03`。

- [ ] `CMAKE-05` **声明 C++11 要求** `【工具链】`
  - **命令/文件语法**：现代 CMake 可写 `target_compile_features(app PRIVATE cxx_std_11)`；严格指定目标属性写 `set_target_properties(app PROPERTIES CXX_STANDARD 11 CXX_STANDARD_REQUIRED YES CXX_EXTENSIONS NO)`。可用性取决于所声明的 CMake 最低版本。
  - **定义与目的**：构建文件应声明目标所需语言级别，让 CMake 为编译器选择合适标准选项并阻止不满足要求的环境。
  - **机制/语法**：推荐 `target_compile_features(app PRIVATE cxx_std_11)`；也可设置 `CXX_STANDARD 11`、`CXX_STANDARD_REQUIRED YES`、`CXX_EXTENSIONS NO` 三个 target 属性。
  - **最小例子**：`set_target_properties(app PROPERTIES CXX_STANDARD 11 CXX_STANDARD_REQUIRED YES CXX_EXTENSIONS NO)`。
  - **常见失败/边界**：`cxx_std_11` 表示“至少具备 C++11”，编译器可能使用更高默认标准；未设 `CXX_STANDARD_REQUIRED` 时某些环境可能回退；特性和可用 meta-feature 依赖 CMake 版本。
  - **依赖**：`BUILD-17`、`CMAKE-04`。

- [ ] `CMAKE-06` **目标源码与包含目录** `【工具链】`
  - **命令/文件语法**：`target_sources(core PRIVATE src/a.cpp src/b.cpp)`；`target_include_directories(core PUBLIC $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include> $<INSTALL_INTERFACE:include> PRIVATE src)`。
  - **定义与目的**：源码列表决定目标编译哪些翻译单元，包含目录告诉编译器去哪里解析头文件；二者都应绑定目标。
  - **机制/语法**：`target_sources(core PRIVATE src/a.cpp)`；`target_include_directories(core PUBLIC include PRIVATE src)`；PUBLIC 头的路径通常向消费者传播。
  - **最小例子**：可用 `$<BUILD_INTERFACE:...>` 与 `$<INSTALL_INTERFACE:...>` 区分源码树构建路径和安装后的公开头路径。
  - **常见失败/边界**：不要把头文件搜索路径误当链接库路径；避免依赖全局 `include_directories`；自动 glob 新源码的重新配置语义需明确，显式列表更容易审查。
  - **依赖**：`BUILD-06`、`CMAKE-04`。

- [ ] `CMAKE-07` **编译定义和编译选项** `【工具链】`
  - **命令/文件语法**：宏写 `target_compile_definitions(core PRIVATE FEATURE_X=1)`（不带 `-D`）；选项写 `target_compile_options(core PRIVATE -Wall -Wextra)`。GCC 选项需用编译器判断或生成器表达式与 MSVC 隔离。
  - **定义与目的**：编译定义产生预处理宏，编译选项传递警告、优化、Sanitizer 等编译器参数，必须区分以便 CMake 正确处理不同工具链。
  - **机制/语法**：`target_compile_definitions(core PRIVATE FEATURE_X=1)` 不写 `-D`；`target_compile_options(core PRIVATE -Wall)` 添加普通选项；作用域控制是否传播。
  - **最小例子**：用生成器表达式按编译器选择警告：`$<$<CXX_COMPILER_ID:GNU,Clang>:-Wall;-Wextra>`，具体可用表达式受 CMake 版本约束。
  - **常见失败/边界**：GCC 参数不能无条件传给 MSVC；改变公共头布局的宏必须作为 PUBLIC/INTERFACE ABI 要求一致传播；链接选项不应塞进编译选项。
  - **依赖**：`BUILD-16`、`CMAKE-04`。

- [ ] `CMAKE-08` **创建不同类型的库** `【工具链】`
  - **命令/文件语法**：`add_library(core STATIC sources...)`、`add_library(core SHARED sources...)`、`add_library(plugin MODULE sources...)`、`add_library(parts OBJECT sources...)`、`add_library(headers INTERFACE)`。
  - **定义与目的**：`add_library` 根据交付方式建立静态、共享、模块、对象或接口 target。
  - **机制**：`STATIC` 产生静态归档，`SHARED` 产生动态库，`MODULE` 是供显式装载且通常不直接链接的插件，`OBJECT` 产生可复用目标文件，`INTERFACE` 只携带使用要求而不编译源码。
  - **最小例子**：`add_library(api INTERFACE); target_include_directories(api INTERFACE include)` 表示仅头文件接口。
  - **常见失败/边界**：省略类型时可能受 `BUILD_SHARED_LIBS` 影响；OBJECT target 不是普通链接库；Windows 共享库还涉及导出符号和导入库等平台机制。
  - **依赖**：`BUILD-15`、`CMAKE-04`。

- [ ] `CMAKE-09` **链接依赖** `【工具链】`
  - **命令/文件语法**：`target_link_libraries(app PRIVATE core)`；优先链接命名 target（本项目 target、Imported Target 或 `Namespace::Target`），而不是手工拼接 `-L`、`-l` 和绝对产物路径。
  - **定义与目的**：`target_link_libraries` 表示某 target 使用另一个库及其使用要求，使 CMake 能按依赖图形成链接命令和下游编译环境。
  - **机制/语法**：`target_link_libraries(app PRIVATE core)`；若链接的是 CMake target，CMake能获得其产物路径、配置和传播接口，而不是只拼 `-l` 字符串。
  - **最小例子**：`core` PUBLIC 依赖 `Threads::Threads` 时，链接 `core` 的消费者可自动获得必要线程使用要求。
  - **常见失败/边界**：链接成功仍可能因运行时动态库搜索失败而启动不了；手工 `link_directories` 和裸文件名容易选错架构或配置，优先使用 target。
  - **依赖**：`BUILD-18`、`CMAKE-08`。

- [ ] `CMAKE-10` **`PRIVATE`、`PUBLIC`、`INTERFACE`** `【工具链】`
  - **命令/文件语法**：统一形式为 `target_<property>(target PRIVATE own_items PUBLIC own_and_consumer_items INTERFACE consumer_only_items)`；例如 `target_include_directories`、`target_compile_definitions`、`target_link_libraries` 均使用这三个作用域关键字。
  - **定义与目的**：三个作用域描述使用要求是仅本目标需要、目标和消费者都需要，还是仅消费者需要。
  - **机制**：`PRIVATE` 写入目标自身属性；`PUBLIC` 同时写自身和接口属性；`INTERFACE` 只写接口属性。规则适用于 include、compile definitions/features/options 和 link libraries 等。
  - **最小判断**：`.cpp` 私有包含目录用 PRIVATE；公共头暴露第三方类型而消费者也需其头路径时用 PUBLIC；纯头文件 target 的要求用 INTERFACE。
  - **常见失败/边界**：并非“库都用 PUBLIC”；过度传播会污染消费者，传播不足会让消费者无法编译或 ABI 不一致，应从公开接口实际需求判断。
  - **依赖**：`CMAKE-06`、`CMAKE-09`。

- [ ] `CMAKE-11` **查找依赖和导入目标** `【工具链】`
  - **命令/文件语法**：`find_package(Foo 2.0 REQUIRED COMPONENTS component)`，成功后按包文档写 `target_link_libraries(app PRIVATE Foo::Foo)`；搜索前缀可在配置命令中以 `-DCMAKE_PREFIX_PATH=<prefix>` 提供。
  - **定义与目的**：`find_package` 查找外部包的配置文件或 Find 模块，Imported Target 把外部库的位置和使用要求封装成可链接 target。
  - **机制/语法**：`find_package(Foo 2.0 REQUIRED)` 后常链接 `Foo::Foo`；Config 模式由包提供配置，Module 模式由 CMake 或项目的 `FindFoo.cmake` 实现。
  - **最小例子**：优先 `target_link_libraries(app PRIVATE ZLIB::ZLIB)`，而不是手工组合头路径、`-L` 和 `-lz`。
  - **常见失败/边界**：找到包不代表版本和架构正确，应声明版本/组件；搜索前缀、toolchain file 和包管理器会影响结果；Imported Target 名称由该包文档规定。
  - **依赖**：`CMAKE-09`。

- [ ] `CMAKE-12` **单配置与多配置生成器** `【工具链】`
  - **命令/文件语法**：单配置：`cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release` 后 `cmake --build build-release`；多配置：配置时不依赖 `CMAKE_BUILD_TYPE`，构建写 `cmake --build build --config Release`。
  - **定义与目的**：单配置生成器的一个构建目录通常对应一个配置，多配置生成器在同一目录中生成 Debug、Release 等多套规则。
  - **机制**：Ninja/Unix Makefiles 常用 `-DCMAKE_BUILD_TYPE=Release` 配置；Visual Studio、Xcode 和多配置 Ninja 通常在构建时用 `--config Release`。
  - **最小例子**：单配置可建 `build-debug/` 与 `build-release/`；多配置执行 `cmake --build build --config Debug`。
  - **常见失败/边界**：多配置生成器通常忽略 `CMAKE_BUILD_TYPE`；不能假定产物总在固定 `build/bin`，路径可能含配置子目录。
  - **依赖**：`BUILD-16`、`CMAKE-02`。

- [ ] `CMAKE-13` **源码外构建** `【工程惯例】`
  - **命令/文件语法**：始终令源码目录与构建目录不同，例如 `cmake -S . -B build/debug -DCMAKE_BUILD_TYPE=Debug`；清理时删除明确的构建目录，而不是源码目录。
  - **定义与目的**：源码外构建把缓存、生成器文件、目标文件和产物集中到独立目录，保持源码树干净并支持多工具链并存。
  - **机制/命令**：在项目根执行 `cmake -S . -B build`，所有生成内容进入 `build/`；另建目录即可选择其他编译器或配置。
  - **最小实践**：版本控制忽略 `/build*/`，但保留源码、CMakeLists、toolchain 和必要生成脚本。
  - **常见失败/边界**：不要把构建目录指向源码根；误提交 CMakeCache 和机器绝对路径会污染协作；删除构建目录可重建，但应先确认没有手工产物。
  - **依赖**：`CMAKE-02`。

- [ ] `CMAKE-14` **测试** `【工具链】`
  - **命令/文件语法**：`CMakeLists.txt` 写 `include(CTest)`、`add_executable(unit_tests ...)`、`add_test(NAME unit COMMAND unit_tests)`；执行 `cmake --build build` 后运行 `ctest --test-dir build --output-on-failure`。
  - **定义与目的**：CTest 是 CMake 配套的测试驱动，可注册命令、传递配置并统一报告，不限定具体单元测试框架。
  - **机制/语法**：`include(CTest)` 提供 `BUILD_TESTING` 并启用测试；`add_test(NAME unit COMMAND unit_tests)` 注册已构建可执行目标。
  - **最小命令**：先 `cmake --build build`，再 `ctest --test-dir build --output-on-failure`；多配置环境加 `-C Debug`。
  - **常见失败/边界**：`add_test` 不会自动编译测试 target；工作目录、环境变量、超时和并行资源要显式配置；CTest 不是断言/Mock 框架。
  - **依赖**：`CMAKE-04`。

- [ ] `CMAKE-15` **安装、导出和包配置** `【工具链】`
  - **命令/文件语法**：典型规则为 `install(TARGETS core EXPORT ProjectTargets ...)`、`install(DIRECTORY include/ DESTINATION include)`、`install(EXPORT ProjectTargets NAMESPACE Project:: DESTINATION lib/cmake/Project)`；执行 `cmake --install build --prefix <prefix>`。
  - **定义与目的**：安装规则把库、可执行文件和公共头复制到规范前缀；导出和包配置让其他 CMake 项目通过 `find_package` 获得可重定位 target。
  - **机制**：常用 `install(TARGETS ... EXPORT ...)`、`install(DIRECTORY include/ ...)`、`install(EXPORT ... NAMESPACE Project:: ...)`，再提供 `<Project>Config.cmake` 和版本文件。
  - **最小实践**：公开包含目录使用 `BUILD_INTERFACE` 与 `INSTALL_INTERFACE`，避免把开发机绝对源码路径写入安装接口。
  - **常见失败/边界**：静态/动态产物目录、RPATH、依赖打包和 Windows 运行时 DLL 都有平台差异；仅能在本机构建不等于包可安装、可重定位。
  - **依赖**：`CMAKE-08`～`CMAKE-11`。

- [ ] `CMAKE-16` **线程库的可移植链接方式** `【工具链】`
  - **命令/文件语法**：`find_package(Threads REQUIRED)` 后写 `target_link_libraries(app PRIVATE Threads::Threads)`；由 CMake 针对 GNU/Linux、Windows 等所选工具链提供适当编译/链接要求。
  - **定义与目的**：线程支持在不同平台可能需要编译标志、链接库或什么都不需要，FindThreads 将这些差异封装成 target。
  - **机制/语法**：`find_package(Threads REQUIRED)` 后写 `target_link_libraries(app PRIVATE Threads::Threads)`，让 CMake按工具链传播适当要求。
  - **最小例子**：使用 `std::thread` 的库若其公共使用者也需要线程链接要求，应根据接口关系选择 PUBLIC，否则通常 PRIVATE。
  - **常见失败/边界**：不要跨平台硬编码 `-pthread` 或 `-lpthread`；在 GNU/Linux 上 `-pthread` 可能同时影响预处理/编译和链接，不等价于单纯库名。
  - **依赖**：`TH-02`、`CMAKE-09`。

# LINUX：Linux C++ 工程基础

> 本模块不是 ISO C++11，但对 Linux C++ 网络、数据库和高并发开发非常重要。

- [ ] `LINUX-01` **GCC、Clang、汇编器和链接器的分工** `【Linux/工具链】`
  - **命令/文件语法**：GNU/Linux 驱动示例：`g++ -v -std=c++11 main.cpp -o app` 或 `clang++ -### ...` 查看子工具；`-E`、`-S`、`-c` 分别停在预处理、汇编文本、目标文件阶段。具体子程序可能是 GNU `as`、`ld`、gold 或 lld。
  - **定义与目的**：`g++`/`clang++` 通常是编译驱动程序，负责按命令选项调用预处理、C++ 前端、汇编器和链接器，并自动加入 C++ 所需运行库。
  - **机制**：前端把 C++ 转为目标相关汇编或中间表示，GNU `as` 等汇编器生成 `.o`，GNU ld、gold、lld 等链接器解析符号并生成 ELF 产物。
  - **最小命令**：`g++ -v main.cpp -o app` 可显示工具链配置和子命令信息；`-E/-S/-c` 分别停在不同阶段。
  - **常见失败/边界**：GCC/Clang、GNU binutils 和链接器是可替换组件，版本组合影响诊断与 ABI；这些名字和阶段实现不是 ISO C++11 的组成。
  - **依赖**：`BUILD-02`。

- [ ] `LINUX-02` **常用编译命令与选项** `【Linux/工具链】`
  - **命令/文件语法**：GCC/Clang 完整示例：`g++ -std=c++11 -Wall -Wextra -Wpedantic -g -O0 -Iinclude src/main.cpp -L/path/to/lib -lfoo -pthread -o app`；通常让目标文件/源码在前、静态依赖库在后。
  - **定义与目的**：命令行同时指定语言方言、诊断、调试/优化、头文件搜索、库搜索、链接依赖和产物名称。
  - **机制/命令**：示例 `g++ -std=c++11 -Wall -Wextra -Wpedantic -g -O0 -Iinclude src/main.cpp -L/path/to/lib -lfoo -pthread -o app`。
  - **选项分工**：`-I` 加头目录，`-L` 加库搜索目录，`-lfoo` 查找 `libfoo`，`-c` 只编译，`-o` 指定输出；库通常放在使用它的目标文件之后。
  - **常见失败/边界**：这些是 GCC/Clang 风格选项；`-L` 不影响运行时共享库搜索；头文件找到不代表链接库版本或架构正确。
  - **依赖**：`BUILD-16`、`BUILD-17`。

- [ ] `LINUX-03` **ELF 文件与节、段、符号** `【Linux/工具链】`
  - **命令/文件语法**：`file app` 识别格式；`readelf -h app` 看 ELF 头，`readelf -S app` 看节，`readelf -l app` 看装载段，`readelf -Ws app` 看符号，`readelf -r app` 看重定位。ELF/readelf 是 Linux/Unix 工具链事实。
  - **定义与目的**：ELF 是 Linux 常用目标文件、可执行文件和共享对象格式；节主要服务链接视图，段由程序头描述并服务装载视图。
  - **机制**：常见节有 `.text` 代码、`.rodata` 只读数据、`.data` 已初始化可写数据、`.bss` 零初始化数据、符号表和重定位节；装载器把若干节按权限映射为段。
  - **最小命令**：`readelf -h app` 看 ELF 头，`readelf -S app` 看节，`readelf -l app` 看程序段，`readelf -Ws app` 看符号。
  - **常见失败/边界**：节与段不能混为一谈；地址、权限和 PIE/共享对象布局由链接器、装载器及 ASLR 决定，不是 C++ 对象布局保证。
  - **依赖**：`BUILD-14`。

- [ ] `LINUX-04` **静态库 `.a`** `【Linux/工具链】`
  - **命令/文件语法**：`g++ -std=c++11 -c foo.cpp -o foo.o`，`ar rcs libfoo.a foo.o`，`ar t libfoo.a` 查看成员，应用链接 `g++ main.o -L. -lfoo -o app`。`.a` 和 `ar` 不是 ISO C++11。
  - **定义与目的**：静态库通常是由 `ar` 管理的目标文件归档，链接器从中抽取满足当前未解析符号的成员并纳入最终产物。
  - **机制/命令**：`g++ -c foo.cpp -o foo.o`，`ar rcs libfoo.a foo.o`，再以 `g++ main.o -L. -lfoo -o app` 链接。
  - **依赖行为**：归档本身通常不把其依赖库代码“自动吸入”；最终可执行目标仍需闭合所有依赖，GNU 风格链接器还常受从左到右扫描顺序影响。
  - **常见失败/边界**：更新 `.a` 不会改变已经链接好的可执行文件；重复符号、循环库依赖、LTO 对象和不同架构归档需相应工具链处理。
  - **依赖**：`BUILD-15`、`BUILD-18`。

- [ ] `LINUX-05` **共享库 `.so`** `【Linux/工具链】`
  - **命令/文件语法**：ELF/GNU 常用 `g++ -std=c++11 -fPIC -c foo.cpp -o foo.o`，再 `g++ -shared foo.o -Wl,-soname,libfoo.so.1 -o libfoo.so.1.0`；应用以 `g++ main.o -L. -lfoo -o app` 记录动态依赖。
  - **定义与目的**：ELF 共享对象把代码保留为独立运行时依赖，可由多个程序在装载时链接，也可通过平台 API 显式动态装载。
  - **机制/命令**：常见流程是 `g++ -std=c++11 -fPIC -c foo.cpp`，再 `g++ -shared foo.o -Wl,-soname,libfoo.so.1 -o libfoo.so.1.0`；应用链接时记录所需动态依赖。
  - **接口设计**：控制导出符号、定义 SONAME 和版本策略，跨长期边界优先采用稳定 C ABI/不透明句柄，或确保同一 C++ ABI 工具链。
  - **常见失败/边界**：`.so`、`-fPIC` 和 ELF 都不是 C++11；能生成共享库不代表 ABI 稳定；卸载仍有对象、函数指针或线程执行库代码时会悬空。
  - **依赖**：`BUILD-13`、`BUILD-15`。

- [ ] `LINUX-06` **PIC、SONAME 和库版本** `【Linux/工具链】`
  - **命令/文件语法**：编译 PIC：`g++ -fPIC -c foo.cpp -o foo.o`；设置 SONAME：`g++ -shared foo.o -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3`；检查：`readelf -d libfoo.so.1.2.3 | grep SONAME`；符号链接用 `ln -s`，布局属发行版惯例。
  - **定义与目的**：PIC 让代码可装载到不同虚拟地址而尽量避免修改共享代码页；SONAME 是依赖者记录的 ABI 主版本名称。
  - **机制**：典型布局为真实文件 `libfoo.so.1.2.3`，其 SONAME 为 `libfoo.so.1`，运行时符号链接 `libfoo.so.1` 指向真实文件，开发链接名 `libfoo.so` 再指向兼容版本。
  - **最小命令**：`readelf -d libfoo.so.1.2.3 | grep SONAME` 检查动态节；`-fPIC` 用于生成位置无关目标。
  - **常见失败/边界**：命名和符号链接布局是发行版惯例，不是自动版本管理；ABI 不兼容变化应提升主 SONAME，只有实现修复且 ABI 兼容才可保留。
  - **依赖**：`LINUX-05`。

- [ ] `LINUX-07` **动态装载器和库搜索** `【Linux/工具链】`
  - **命令/文件语法**：查看依赖/RUNPATH：`readelf -d app`；诊断解析：`ldd app`、受控环境中 `LD_DEBUG=libs ./app`；链接期写相对 RUNPATH 常用 `-Wl,-rpath,'$ORIGIN/../lib'`。优先级受 glibc 与安全执行模式影响。
  - **定义与目的**：ELF 动态装载器在程序启动时映射所需共享对象、按规则搜索文件并完成重定位；运行时搜索路径必须作为部署设计的一部分。
  - **机制**：搜索可能涉及 ELF 中的 DT_RPATH/DT_RUNPATH、`LD_LIBRARY_PATH`、`/etc/ld.so.cache` 和系统默认目录；确切优先级受 glibc、secure-execution 和标签类型影响。
  - **最小实践**：可重定位应用常按策略设置基于 `$ORIGIN` 的 RUNPATH；诊断可用 `readelf -d app`、`ldd app` 或受控环境下 `LD_DEBUG=libs ./app`。
  - **常见失败/边界**：不要把全局 `LD_LIBRARY_PATH` 当稳定发布方案；RUNPATH 与旧 RPATH 的传递语义不同；不要对不可信二进制随意运行可能触发装载行为的检查工具。
  - **依赖**：`LINUX-05`。

- [ ] `LINUX-08` **符号检查工具** `【Linux/工具链】`
  - **命令/文件语法**：`nm -C file.o`/`nm -C libfoo.a`，`readelf -Ws libfoo.so`、`readelf -d app`，`objdump -d -C app`、`objdump -t app`，以及 `c++filt <mangled-name>`；这些选项依 GNU binutils/LLVM 版本。
  - **定义与目的**：二进制工具帮助回答“符号是否定义/导出、依赖了哪个库、调用了什么代码、C++ 修饰名代表什么”。
  - **机制/命令**：`nm -C file.o` 查看并反修饰符号，`readelf -Ws/-d` 看 ELF 符号和动态依赖，`objdump -d/-t` 看反汇编和符号表，`c++filt` 单独反修饰，`ldd` 查看实际解析依赖。
  - **最小诊断**：链接报 undefined reference 时，先在调用目标看未定义符号，再用 `nm -C libfoo.a` 或 `readelf -Ws libfoo.so` 查是否有完全相同签名。
  - **常见失败/边界**：动态符号表与完整调试/静态符号表不同；隐藏或剥离符号可能看不到；工具输出格式与选项依 binutils/LLVM 版本。
  - **依赖**：`BUILD-11`、`LINUX-03`。

- [ ] `LINUX-09` **`-pthread` 的作用** `【Linux/工具链】`
  - **命令/文件语法**：GNU/Linux GCC/Clang 构建线程程序写 `g++ -std=c++11 main.cpp -pthread -o app`，让 `-pthread` 同时参与编译和链接；CMake 跨平台形式是 `find_package(Threads REQUIRED)` + `Threads::Threads`。
  - **定义与目的**：`-pthread` 告诉 GCC/Clang 驱动按目标平台启用 POSIX 线程所需的编译和链接设置。
  - **机制**：它可能定义线程相关预处理宏、选择线程安全运行时模式并把适当链接选项传给链接器；具体效果由工具链和 libc 版本决定。
  - **最小命令**：`g++ -std=c++11 main.cpp -pthread -o app`，CMake 中优先使用 `Threads::Threads`。
  - **常见失败/边界**：不要简单替换成 `-lpthread`，因为后者只表达一个库搜索项；即使现代 glibc 合并了部分线程库实现，也仍应使用工具链推荐方式。
  - **依赖**：`TH-02`、`LINUX-02`。

- [ ] `LINUX-10` **GDB、core dump 和调用栈** `【Linux/工具链】`
  - **命令/文件语法**：构建 `g++ -std=c++11 -g -O0 main.cpp -o app`；交互调试 `gdb ./app` 后常用 `break main`、`run`、`bt`、`info threads`、`thread N`、`frame N`、`print expr`；离线分析 `gdb ./app core`。
  - **定义与目的**：GDB 可控制进程、断点、单步、检查线程和栈帧；core dump 保存崩溃时进程快照，便于离线定位。
  - **机制/命令**：用 `-g` 和适度优化构建；GDB 常用 `break`、`run`、`bt`、`info threads`、`thread`、`frame`、`print`、`thread apply all bt`；离线可 `gdb ./app core`。
  - **最小实践**：保存与 core 完全匹配的可执行文件、共享库和调试符号；先查看崩溃线程栈，再检查其他线程是否死锁。
  - **常见失败/边界**：core 是否产生及位置受 `ulimit`、内核 core_pattern、systemd 和权限配置影响；优化会使变量“optimized out”或调用内联；core 可能含密钥等敏感数据。
  - **依赖**：`BUILD-16`。

- [ ] `LINUX-11` **文件描述符** `【Linux/POSIX】`
  - **命令/文件语法**：POSIX C 接口以 `int fd` 表示描述符；创建/复制/关闭常用 `open(...)`、`dup(fd)`/`dup2(oldfd,newfd)`、`fcntl(fd,F_SETFD,FD_CLOEXEC)`、`close(fd)`，声明来自 `<fcntl.h>`/`<unistd.h>`，不属于 ISO C++11。
  - **定义与目的**：文件描述符（fd）是进程文件描述符表中的非负整数索引，可引用普通文件、管道、终端、套接字、eventfd 等内核对象。
  - **机制**：常见 `0/1/2` 为标准输入/输出/错误；`dup` 或 `fork` 可让多个 fd 引用同一打开文件描述，共享文件偏移和部分状态；fd 自身还可有 `FD_CLOEXEC` 等标志。
  - **最小例子**：成功 `open` 返回 fd，使用完必须由唯一责任方 `close(fd)`；C++ 可写不可复制、可移动的 RAII `unique_fd`。
  - **常见失败/边界**：fd 数值关闭后可很快复用，缓存旧整数会误操作新资源；fd 有进程限制；它不是 C++ 指针，也不能与 `FILE*` 混为一谈。
  - **依赖**：`IO-01`、`IO-09`。

- [ ] `LINUX-12` **`open/read/write/close`** `【Linux/POSIX】`
  - **命令/文件语法**：POSIX 形式：`int fd = ::open(path, flags[, mode]);`、`ssize_t n = ::read(fd, buffer, count);`、`ssize_t n = ::write(fd, buffer, count);`、`int rc = ::close(fd);`；每次检查 `-1` 与 `errno`，短读写需循环。
  - **定义与目的**：这些低层接口直接操作文件描述符，适合网络、事件循环和需要精确控制的系统代码；它们不提供 C++ 流格式化与 RAII。
  - **机制**：`open` 返回 fd 或 `-1`；`read/write` 返回实际字节数，`-1` 表示错误并设置 `errno`，`read` 返回 `0` 通常表示 EOF；成功传输也可能少于请求数。
  - **最小循环**：对未完成字节持续调用，遇 `EINTR` 按接口语义重试，非阻塞 fd 遇 `EAGAIN/EWOULDBLOCK` 返回事件循环等待；每次都更新缓冲偏移。
  - **常见失败/边界**：`O_CREAT` 时还要传权限 mode；短写不是只在错误时发生；Linux 上 `close` 错误后的 fd 处理有复用风险，不能盲目按普通读写方式重试，需遵循平台文档。
  - **依赖**：`LINUX-11`。

- [ ] `LINUX-13` **阻塞、非阻塞和 I/O 多路复用** `【Linux/POSIX】`
  - **命令/文件语法**：POSIX 非阻塞常用 `fcntl(fd, F_SETFL, old_flags | O_NONBLOCK)`；`select`/`poll` 是 POSIX 接口；Linux 专有 epoll 典型为 `epoll_create1(EPOLL_CLOEXEC)`、`epoll_ctl(epfd,EPOLL_CTL_ADD,fd,&event)`、`epoll_wait(epfd,events,maxevents,timeout)`。
  - **定义与目的**：阻塞调用可等待资源就绪；非阻塞调用立即返回；I/O 多路复用让一个线程等待多个 fd 的就绪事件，支撑高并发连接。
  - **机制**：`fcntl` 可设置 `O_NONBLOCK`；`select` 使用 fd 集合且有常见容量限制，`poll` 使用数组并线性扫描，Linux `epoll` 在内核维护关注集合并返回就绪事件。
  - **最小流程**：把 fd 设非阻塞，注册读事件；收到可读通知后循环 `read` 直到 `EAGAIN`，解析完整消息，再更新关注事件。
  - **常见失败/边界**：`epoll` 是 Linux 专有，`select/poll` 属于 POSIX；“就绪”不保证一次操作完成全部数据；边沿触发若不排空会丢失推进机会，业务协议还需处理半包、背压和关闭。
  - **依赖**：`LINUX-11`、`TH-01`。

- [ ] `LINUX-14` **`std::thread` 与 pthread 的关系** `【实现/平台】`
  - **语法边界**：可移植层使用 `std::thread worker(function); worker.join();`；平台扩展需从 `worker.native_handle()` 取得实现句柄，再调用如 Linux `pthread_setaffinity_np(...)`。native handle 类型和互操作保证必须查所用标准库文档。
  - **定义与目的**：ISO C++11 提供可移植线程语义，Linux 上 libstdc++/libc++ 实现通常借助 POSIX pthread，但该映射不是语言保证。
  - **机制**：标准接口负责创建、join、互斥和内存模型；`native_handle()` 可在确需亲和性、调度或名称等平台能力时取得实现句柄。
  - **最小实践**：业务并发使用 `std::thread/std::mutex`，把 `pthread_setaffinity_np` 等扩展封装在 Linux 适配层并提供失败处理。
  - **常见失败/边界**：直接 `pthread_cancel` 标准线程可能破坏 C++ RAII 和库假设；混用两套锁/条件变量必须明确同步关系；不同实现的 native handle 类型不同。
  - **依赖**：`TH-02`、`TH-23`。

- [ ] `LINUX-15` **进程接口** `【Linux/POSIX】`
  - **命令/文件语法**：POSIX 基本形式：`pid_t pid = fork();`，子进程调用 `execl/execve/...`，父进程 `waitpid(pid,&status,0)`；管道 `int ends[2]; pipe(ends);`，退出状态用 `WIFEXITED(status)`/`WEXITSTATUS(status)`。
  - **定义与目的**：`fork` 复制当前进程执行环境，`exec` 用新程序映像替换当前进程，`wait/waitpid` 回收子进程并取得退出状态，pipe 提供单向字节流。
  - **机制**：常见模式是父进程先建 pipe，`fork` 后子进程重定向 fd 并 `exec`，父进程关闭不用的管道端并 `waitpid`；exec 成功不会返回。
  - **最小例子**：检查 `fork()` 的 `-1/0/>0` 三种结果；退出状态用 `WIFEXITED/WEXITSTATUS` 等 POSIX 宏解释。
  - **常见失败/边界**：多线程进程 fork 后，子进程在 exec 前只能安全调用受 POSIX 允许的 async-signal-safe 操作，继承的互斥量可能由已消失线程持有；使用 `O_CLOEXEC` 防止无意 fd 泄漏。
  - **依赖**：`TH-01`、`LINUX-11`。

- [ ] `LINUX-16` **信号边界** `【Linux/POSIX】`
  - **命令/文件语法**：POSIX 安装处理器用 `struct sigaction action = {}; sigemptyset(&action.sa_mask); action.sa_handler = handler; sigaction(signum,&action,nullptr);`；线程 mask 用 `pthread_sigmask`。Linux `signalfd` 是专有扩展。
  - **定义与目的**：信号是异步通知机制，处理器可在几乎任意指令点打断线程，因此能安全执行的操作远少于普通函数。
  - **机制**：POSIX 规定 async-signal-safe 函数集合；常见设计让处理器只设置受允许的简单状态或向 self-pipe 写一个字节，由正常事件循环完成日志、锁和资源处理。Linux 还可在适当架构中使用 `signalfd`。
  - **最小实践**：用 `sigaction` 安装处理器并明确线程信号 mask；在正常线程中恢复复杂控制流。
  - **常见失败/边界**：处理器中不得随意使用 `new/delete`、iostream、普通 mutex、条件变量或大多数标准库；`std::atomic` 也不能一概当作 POSIX async-signal-safe API。
  - **依赖**：`AT-15`、操作系统基础。

- [ ] `LINUX-17` **`mmap`、`msync`、`fsync` 与持久化边界** `【Linux/POSIX】`
  - **命令/文件语法**：`void* p = mmap(nullptr,length,prot,flags,fd,offset);` 并与 `MAP_FAILED` 比较；同步/释放为 `msync(p,length,MS_SYNC)`、`fsync(fd)`、`munmap(p,length)`，逐次检查返回值。接口来自 POSIX/Linux 头文件而非 C++11。
  - **定义与目的**：`mmap` 把文件或匿名对象映射到虚拟地址空间；`msync` 协调映射脏页回写；`fsync` 请求把文件数据和必要元数据同步到持久存储层。
  - **机制**：`MAP_SHARED` 修改可回写并被其他共享映射观察，`MAP_PRIVATE` 通常写时复制；映射成功后关闭原 fd 不会立即撤销映射，最后用 `munmap`。
  - **最小流程**：检查 `mmap` 是否返回 `MAP_FAILED`，只访问映射长度内地址，需要持久化时按文件格式提交顺序调用相应同步，并检查返回值。
  - **常见失败/边界**：内存写完成不等于介质持久化；`msync/fsync`、文件系统、存储设备缓存和崩溃一致性协议是不同层；映射字节也不会自动建立 C++ 对象或跨进程原子同步。
  - **依赖**：`LINUX-11`、虚拟内存基础。

- [ ] `LINUX-18` **Linux 内存与并发诊断工具** `【Linux/工具链】`
  - **命令/文件语法**：Memcheck：`valgrind --leak-check=full ./app`；ASan/UBSan：编译和链接都加 `-fsanitize=address,undefined -fno-omit-frame-pointer`；TSan 单独构建用 `-fsanitize=thread`；性能采样 `perf record -g ./app` 后 `perf report`。
  - **定义与目的**：不同工具观察不同错误面：Valgrind Memcheck 查非法内存和泄漏，ASan/UBSan 用编译插桩查内存/部分未定义行为，TSan 查数据竞争，`perf` 采样 CPU、缓存和调度性能。
  - **机制/命令**：`valgrind --leak-check=full ./app`；Sanitizer 构建使用对应 `-fsanitize=`；`perf record -g ./app` 后 `perf report` 查看热点调用栈。
  - **最小实践**：使用带调试符号的独立构建，固定复现输入，先修正确性报告再测性能，并保存工具、编译器和内核版本。
  - **常见失败/边界**：工具会改变时序和性能；TSan 与 ASan 通常分开构建；perf 可能受权限、采样频率和缺失符号影响；没有报告不等于没有问题。
  - **依赖**：`MEM-27`、`AT-21`、`BUILD-16`。

- [ ] `LINUX-19` **可移植层与平台层隔离** `【工程设计】`
  - **命令/文件语法**：目录可分 `core/` 与 `platform/linux/`；平台头只出现在实现 target，CMake 依次分行写 `if(CMAKE_SYSTEM_NAME STREQUAL "Linux")`、`target_sources(platform PRIVATE platform/linux/...)`、`endif()` 选择实现。该条件是 CMake 语法，不是 C++11。
  - **定义与目的**：把 ISO C++11 业务逻辑与 Linux/POSIX 系统调用分层，可控制依赖、便于测试并为其他平台保留替换空间。
  - **机制**：在窄接口后封装 fd RAII、事件循环、路径、动态库和错误转换；头文件尽量暴露平台无关类型，Linux 头和条件编译集中在实现文件。
  - **最小结构**：`core/` 只依赖标准 C++11，`platform/linux/` 实现 `FileHandle/EventLoop/Process` 接口，CMake 根据平台选择实现 target。
  - **常见失败/边界**：抽象不能假装所有平台语义完全相同，应显式记录支持能力、阻塞/关闭和错误契约；不要让 `int fd`、`errno` 或 Linux 宏扩散到全部业务代码。
  - **依赖**：全部 BUILD、CMAKE 和基础 Linux 节点。

- `std::shared_timed_mutex`：C++14。
- `std::shared_mutex`、`std::scoped_lock`：C++17。
- `std::filesystem`：C++17。
- `std::byte`：C++17。
- 标准对齐版 `operator new`：C++17。
- 并行 STL 算法：C++17。
- `std::uncaught_exceptions()`：C++17。
- `std::atomic<std::shared_ptr<T>>` 特化：C++20。
- `std::jthread`、`stop_token`、信号量、闩锁和屏障：C++20。
- `atomic_wait`/`atomic_notify`：C++20。
